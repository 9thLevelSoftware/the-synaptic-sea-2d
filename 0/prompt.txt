  ## 1. Movement feel

  | Carry-walk (propose) | 2 (run disabled) | 120 | 2.5 | — | — |
  | Stagger (propose) | 1 | 60 | 1.25 | 1.13 | 10.7 s |
  | Rejected: walk 1 | 1 | 60 | 1.25 | 1.13 | 10.7 s — 58 % repeated frames at 144 fps (render D.17); too slow to cross a frame |
  | Rejected: run 4 | 4 | 240 | 5 | 4.5 | passes the 266 check but **breaks the inner box** (below) |
  
  I cannot source Project Zomboid's speeds, so I state pacing in tiles/s and body-heights/s: 2.26 heights/s is faster than a real walk (~0.8) but is the normal pixel-game walk; "deliberate" here is carried by instant stops, no bounce and the 12 fps cadence, not by a crawl. Step 13 decides between walk 2 and the slower 1.5 average (see accumulator).
  
  ### Camera checks — there are TWO inequalities, not one
  
  1. Render G check: `v_max < LAG_CUT / τ_follow = 48 / 0.18 = 266 px/s`. Run 180 passes.
  2. **Render C4 inner box (the tighter bound, not currently in the G check)**: `v_max·τ_follow + L_MAX ≤ 108` (vertical half-extent). Run 3 px/tick: `180×0.18 = 32.4 + 72 = 104.4 ≤ 108` — passes with 3.6 px to spare. Run 4 px/tick: `43.2 + 72 = 115.2` — **fails**. General: `v_max ≤ (108 − 72) / 0.18 = 200 px/s = 3.33 px/tick`, so 3 px/tick is the integer ceiling at the default `L_MAX`. Pan ceiling becomes `1.25 × 180 = 225 px/s`.
  
  Routing: the render GDD's placeholders (1.5 / 2.5 px/tick = 90 / 150 px/s) violate its own PR-4 rule 3 (whole px per tick); when this GDD sets 2 / 3, render Section D (D.6, D.10, D.17 worked examples) and G must be updated, and the G check should gain inequality 2.
  
  ### Acceleration and stopping
  - **Walk: instant** (0-tick ramp). At 2 px/tick a ramp would be one tick of 1 px — invisible. Stiff-weighted (5.2) wants the body to start when told.
  - **Run from standing: `RUN_RAMP_TICKS = 6` (100 ms) at walk speed, then 3 px/tick.** Walk→run while already walking: instant. This is the "forward lean" cost in motion rather than in deformation. Safe range 0–12.
  - **Stop: instant, accumulator cleared, no grid snap, no decel slide.** A decel slide is overshoot by another name (5.2 forbids overshoot); tile-snapping moves the body without input — uncaused motion, the thing PR-4 exists to forbid. Knob `STOP_DECEL_TICKS` default 0, safe 0–3 (1 px/tick for N ticks from run) if testers call the run stop "mechanical".
  
  ### Diagonals on a pixel grid — this is also a camera bug if done wrong
  Un-normalised diagonals are not merely fast: run (3,3) = 254.6 px/s **exceeds the pan ceiling (225)**, so the follow term would exceed it for longer than `T_PAN` and the camera would **cut every time the player runs diagonally**. Diagonals must be normalised to the cardinal magnitude. Three whole-pixel options:
  
  | Option | Per-axis steps (walk diag, target 1.414) | Avg magnitude | Cadence |
  |---|---|---|---|
  | **(a) Bresenham-style sub-pixel accumulator (recommend)** | 1,1,2,1,1,2,… (run: 2,2,2,3,2,2,2,3…) | exact (2.000 / 3.000) | irregular — a 1-then-2 step visible at 144 fps; step 12 measures it |
  | (b) Alternate (2,1)/(1,2) | 2,1,2,1 | walk 2.12 (+6 %); run needs (2,2)/(3,2) | regular but biased |
  | (c) Fixed (1,1) walk / (2,2) run | 1,1,1,1 | walk 1.41 (−29 %), run 2.83 (−6 %) | regular; walk diagonals noticeably slow |
  
  Mechanism for (a): the block stores `pos: Vector2i` (base px, ship-local) and `sub: Vector2i` in **fixed-point 1/256 px** (integers only — no floats in the block, so snapshot hashes and replay are exact). Per tick: `want = dir_unit_fixed[octant] × speed_px × 256` (an 8-entry integer table, diagonal entries = `round(256/√2) = 181`); `sub += want`; `step = sub / 256` (integer division toward zero); `sub -= step × 256`; then the collision sweep moves `step`. `sub` resets to zero on stop (otherwise the first step after a stop could be 2 px from a stale remainder — uncaused-feeling). This also makes `v_walk` a free knob in 1/256 px/tick (so 1.5 is representable as 1,2,1,2) — but only integer values give a regular cadence, which is why the defaults are integers.
  
  ### 8-way input, 5 drawn facings
  - **Octant** from the left stick / WASD: `octant = floor((angle + 22.5°) / 45°) mod 8` with a **radial deadzone 0.30** (safe 0.15–0.40) and **5° hysteresis** at sector edges so a stick resting on a boundary does not flicker between octants (each flicker is a `set_move_intent` command). Keyboard gives octants directly. **Run** = hold button (toggle option for accessibility), or stick magnitude ≥ `RUN_STICK_MAGNITUDE = 0.9` [the second is a knob; default off].
  - **Facing** (the drawn sprite) is **derived from aim, not from movement** — see §5. The movement octant and the facing are independent; mirrored facings are `flip_h` on E/NE/SE → W/NW/SW.

  ## 2. Collision
  
  ### Position type decides everything
  `CharacterBody2D.move_and_slide` produces **float** positions on the first wall contact (the slide response is not integer), which breaks the whole-pixel invariant at the first wall, puts the engine's non-deterministic 2D physics inside the avatar's position (kernel G3 limit), and ties the avatar to a Node — untestable headless (H10). **Recommendation: the avatar is kinematic-by-hand on an integer position, and does not use a physics body at all.**
  
  Proposed shape:
  - The owning block holds `pos: Vector2i` (ship-local base px, the **foot-centre** = sort origin), `sub`, `facing`, `octant`, `run`, `odometer: int`.
  - **Collision is an AABB sweep in pure GDScript** against a list of integer rectangles published by the Layout `PROJECTOR` (kernel C.3 #6/#5): wall footprints (**24 px deep × 48 wide** per PR-5's up-screen convention — the 72 px face is *not* collision; if the art-director confirms 8.2's literal reading instead, the rectangle grows to 96 rows from the south and nothing else here changes), prop footprints (cap = footprint depth, 8.2), door leaves when closed, machinery 96×96 footprints.
  - **Avatar footprint: 16 wide × 8 deep base px, centred on the foot line** (safe 12–24 × 6–12). A small foot box is what lets a 24-px-wide figure stand close to a wall base and pass through a 96 px doorway with slack; the sprite overlapping a wall face visually is correct in 3/4 oblique.
  - **Per tick: axis-separated 1-px sub-steps**: for each of `|dx|` unit steps on x, test the box; stop that axis on the first hit; then the same on y. **Sliding along walls falls out of axis separation** (the blocked axis stops, the other continues). Cost ≤ 6 rectangle tests × N nearby rects per tick — trivial. Order x-then-y every tick (deterministic; no alternation).
  - This satisfies G3 for the avatar with **no recorded physics observations** — the avatar's position becomes a pure function of the command stream and the layout. Engine physics is left for what needs it (debris, the ship body itself).
  
  If the team prefers engine queries anyway, the same structure works with `PhysicsServer2D.body_test_motion` per sub-step — but that API is **NOT SOURCEABLE** in the pinned reference and re-admits the G3 limit; I would not choose it for a first-timer.
  
  ### The moving ship (kernel C.3 #6, render C2)
  Render C2 makes the world canvas *the body's frame* ("ship motion through the void never appears in the interior view"), and OQ 3's proposal has Ship Body owning ship-local position. Together these mean the simplest shape is: **the interior is static in ship-local space; the ship's motion is numbers in the Ship Body block (void position/velocity), never a transform applied to the interior.** The avatar never experiences a moving platform because, in its coordinate system, nothing moves. Routed to the Ship Body GDD as the recommendation; it is also the only shape under which `pos: Vector2i` survives — a float ship transform would re-introduce fractional offsets PR-4 rule 2 forbids.
  
  - **Docked bodies**: two frames with one integer offset (PR-4 rule 2 already requires "one floored offset shared by all their items"). Crossing a dock threshold = subtract one body's offset and add the other's (integers), and the frame-ownership field changes — the camera cuts (C5), which the render GDD already accepts.
  - **Detach**: the section containing the avatar's foot box becomes the avatar's body; position rebased by the integer offset.
  - **Door thresholds**: a closed leaf is one rectangle in the collision list; opening removes it. Edge case to route to Interaction/Layout: closing a door whose leaf rectangle overlaps an actor's foot box must be rejected in `validate` (`PRECONDITION`), never applied — otherwise the actor is inside collision and the sweep would freeze them.
  - **Carrying a module**: no collision change (collision is the feet; the module breaks the outline *upward*, 5.2). Speed drops to carry-walk and run is disabled (knob). A dropped module becomes a prop footprint — Item/Interaction's.
  
  ### Position ownership (OQ 3) — my vote
  Controller owns `pos/sub/facing/intent` **as one block** with the integration step as a Controller hook (`divisor 1`, `after: layout.projection`), reading the Layout's collision list as a read view. Reason: the velocity rule (one handler + one registration line per verb) and testability — one pure step function with everything it writes in one block. Ship Body owns body frames and offsets. If the TD rules the other way (Body owns position), the same pure function runs inside Body's hook reading the Controller's intent view; nothing in §1–§5 changes except the block ID.

  ## 3. Aim
  
  ### Two aim values, two owners
  | Value | Owner | Lives in | Updated | Consumers |
  |---|---|---|---|---|
  | **Local raw aim** | input adapter (presentation side, `INPUT_SURFACE`) | a plain `Vector2` on the adapter, not a block | every render frame, unquantised | the camera host (C4/D.7 look-ahead — "no tick latency, no quantisation"); the presenter's beam-cone preview if any |
  | **`set_aim` intent** | Controller block via command | block field `aim_angle: int` (0–4095 = 1/4096 turn, 0.088°) | on change beyond threshold, coalesced | facing derivation, Emitter State's beam direction, Interaction targeting, replication |
  
  "Local raw aim" is the direction from the **floored hand point** (the same integer the sprite and `PointLight2D` use, PR-4 rule 2) to the cursor's body-space position, or the stick vector itself. It is the camera's input *only*; the sim never sees it. In VS-B a guest's camera still reads its own raw aim; the host sees only the command — the two are allowed to disagree by one threshold and one tick, by design.
  
  ### Mouse
  - World position comes **only** from the pipeline root's inverse of `world_to_hud` (render C11): the controller never re-derives k, letterboxing, zoom or the `1/k` container offset. The pipeline root exposes `screen_to_body(screen_px) -> Vector2` (float, base px, body frame); the adapter calls it once per frame.
  - `SubViewportContainer.mouse_target` / `Viewport.get_mouse_position()` on the world SubViewport are `[BIN]` members but their behaviour under pass B, zoom-out and letterboxing is **NOT SOURCEABLE** — render spike step 11 checks it; until then, compute from the root viewport's mouse position through the published transform rather than trusting the SubViewport's own mouse state.
  - Mouse gives a **point**; the beam is a **direction** from the hand point (5.6). Whether Interaction targets the cursor *point* (mouse) vs nearest-in-cone (stick) is Interaction's — but the controller GDD must say which it publishes: I propose it publishes direction only (`aim_angle`), plus a local-only cursor point the Interaction prompt code may read as `INPUT_SURFACE`. **Flag for game-designer.**
  
  ### Gamepad right stick
  - Radial deadzone `AIM_DEADZONE = 0.25` (safe 0.15–0.35), rescaled so the edge of the deadzone is magnitude 0; **no angular snapping, no aim assist** (C9 forbids framing-based assist; this GDD should forbid input-side assist too, because an assisted aim is a lie about where the hand points — Pillar 1).
  - Inside the deadzone the aim **holds its last direction** (render D.7 already keeps the previous `û` for a zero aim; the sim does the same — a released stick never points the beam at (0,0)).
  - Active source = last device that produced an aim event: `InputEventMouseMotion` → mouse; `InputEventJoypadMotion` on the right-stick axes beyond the deadzone → stick. Decide by event type (4.7 `[REF]`).
  
  ### Hand point
  `HAND_POINT[facing] : Vector2i` offset from the foot-centre origin for the 5 drawn facings; mirrored facings use `(−x, y)`. Beam `PointLight2D.position = floor(interp_pos) + HAND_POINT[facing_drawn] × (−1 if mirrored else 1, 1)`. On a mirror the beam origin jumps by `2·x` (the tool swaps hands — accepted by 5.6); I recommend the art keep `|x| ≤ 6 px` so the jump is under an eighth of a tile.

  ## 4. Intent plumbing
  
  ### Sampling point (this is what makes movement need no pre-play)
  The adapter samples input **in the same physics callback, immediately before `Kernel.step()`** (the driver node calls `adapter.sample()` then `kernel.step()`; or `process_priority` orders them — behaviour `[UNV]`, step 12). Then: submit → P0 freezes the queue with the command inside → P2 applies the intent → **P3 integrates the first pixel in that same tick** → P4 commits → the presenter interpolates toward it from the next frame. Input-to-first-pixel ≤ 1 tick + one frame. If input were sampled in `_process` after physics it would cost one extra tick; say so in the GDD.
  
  ### `set_move_intent`
  - Payload `{octant: int 0..8 (0 = stop), run: bool}`; `coalesce = LATEST_PER_ACTOR_PER_TICK`; `max_age_ticks = 30`; `actor_binding = OWNED_BY_ISSUER`; `allowed_origins = {PLAYER}`.
  - **Sent only when `(octant, run)` changes** — with the deadzone and hysteresis of §1 that is a few per second; a held key sends nothing. Intent is level-triggered state in the block, so no heartbeat is needed locally (G5: nothing is lost). Expected rate: < 10/s in normal play, < 60/s in the worst case (a wiggling stick), far under `PER_ISSUER_CAPACITY`.
  - Facing is **derived** in the block from `aim_angle` (§5); I would not register a separate `set_facing` command (CR-4 lists "facing" — propose dropping it; one fewer type, no way for facing and aim to disagree).
  
  ### `set_aim`
  - Payload `{angle: int 0..4095}`; same coalescing and age as move intent.
  - **Send when the quantised angle differs from the last sent by ≥ `AIM_SEND_THRESHOLD = 57` units (5.0°)**, OR the aim source changed, OR a **settle** condition: the raw aim has been inside the threshold for `AIM_SETTLE_TICKS = 6` (100 ms) and differs at all from the last sent (so the final resting angle is exact, not 4.9° off). **Rate limit: at most one per `AIM_MIN_INTERVAL_TICKS = 3`** (20/s). A full-speed mouse sweep then costs ~20 commands/s; a 360° flick ~72 commands spread over the interval — bounded.
  - A 5° threshold at the far end of an 8-tile cone (384 px) is 33 px of lateral slop between what the camera leans toward and what the sim lights; invisible against the cone's width, and the settle send removes it at rest.
  
  ### Edge-triggered actions
  - `toggle_beam`, `interact`, `pickup`, `drop`, `begin_*`, `cancel_channel` are Interaction's / Emitter's / Suit's types; the controller's adapter **submits** them as the local `INPUT_SURFACE` with `coalesce = NONE`, `max_age 120`. Press and release are separate commands where a hold matters (`begin_cut` / `cancel_channel`).
  - **Input buffer**: a press that arrives while the adapter knows the actor is busy is held for `ACTION_BUFFER_TICKS = 6` (100 ms) and submitted when the busy flag clears, else dropped locally (never submitted — so no honest-rejection oracle is created, P4 cost rule). Buffer lives in the adapter, not the sim.
  - **Immediate local acknowledgement** (CR-4): on submit the presenter pre-plays **only body and sound** — the first frame of the work loop (hand raise), the tool's click — never the *effect*: the beam light turns on when the Emitter block changes (≤ 1 tick, 17 ms — invisible), a cut's progress ring starts on the Interaction block's channel state, not on the press. Pre-playing a light that could be rejected would be a one-frame lie (Principle 1 / "light is a decision").
  - **Rejection**: on `Rejected` for a pre-played action, the presenter returns to idle on the next frame (no flinch animation of its own — the controller surfaces nothing; the *reason* belongs to Interaction/HUD under the P4 cost rule). A rejected **intent** (`ACTOR_NOT_OWNED`, `PAUSED`, `STALE`) is a defect or a pause and is logged to diagnostics only; intents never pre-play. The adapter keeps a `seq → pre-play token` map so a late result can cancel the right pre-play; entries expire after `max_age`.

  ## 5. Animation (stiff-weighted, no procedural deformation)
  
  The presenter writes exactly three things per frame: **frame index, `flip_h`, integer position** (plus overlay sprite visibility and the light position). No `scale`, no `rotation`, no `skew`, no tweened offsets — PR-4 rules 4–5 forbid them and 5.2 wants none; "no squash/overshoot" is then enforced by lint, not by discipline.
  
  ### Cadence: distance-driven, per-state stride
  8 frames at 12 fps = 5 ticks per frame = 40 ticks per cycle. At walk 2 px/tick a cycle is 80 px → **`STRIDE_WALK = 10 px per frame`**; at run 3 px/tick, **`STRIDE_RUN = 15 px per frame`** keeps run at 12 fps too. The frame index is `floor(odometer / stride) mod 8`, where `odometer` is an integer the step function accumulates from the *actual* pixels moved (post-collision, so feet never slide against a wall). Reading committed state satisfies PR-8 rule 6 (animate on `present_time`, never on the tick counter); the presenter reads `odometer` prev/curr, interpolates with `tick_alpha`, floors, and indexes. Frames change only at whole boundaries — no blending. **Flag for art-director**: fixed 12 fps with a longer run stride (feet cover 15 px/frame — a run) vs speed-scaled 18 fps at run; I recommend the former.
  
  - **Idle**: the pack's 2–3 px breath on `present_time` at ~0.5 Hz, as frames (not an offset tween) so the figure never leaves the grid.
  - **Run lean**: in the drawn frames, never a runtime skew.
  - **Carry-walk**: the walk cycle with a module sprite child at a per-facing `CARRY_POINT[facing]` (mirror rule as the hand point); same stride.
  
  ### Facing selection
  - Facing = aim angle → 8 sectors with **`FACING_HYST = 5°`**: the facing changes only when the aim leaves the current sector by more than the hysteresis, so an aim held at 22.5° does not flicker between S and SE (each flicker is a sprite swap *and* a beam-origin jump).
  - The body faces the aim, not the movement (5.2: "expression lives in where the beam points"; 5.6: the sprite is 8-way, the light 360°). **Consequence that needs a design decision**: moving away from the aim is a backpedal. Options: (i) play the walk cycle **reversed** when `dot(move_dir, facing_dir) < 0` (zero extra frames; stride logic unchanged — sign the odometer delta); (ii) facing follows movement while moving and aim only when stationary or the beam is lit (lose "look where the hand points" while walking); (iii) authored backpedal cycles (8 × 5 more frames). I recommend (i) for MVP. **Flag for game-designer and art-director.**
  - Gamepad with the right stick released: facing holds (aim holds). Keyboard+mouse: cursor sets it.
  - Mirrored facings: `flip_h` only; tool sprite is a child so it flips with the body (tool swaps hands — 5.6 accepts).
  
  ### Stagger / down
  Not controller state — **Suit's `SIM` read view** carries the vital thresholds; the controller's step reads a `locomotion_cap` (NORMAL / STAGGER / DOWN) from Suit (`after: suit.vitals`) and clamps speed (stagger 1 px/tick, down 0) and animation state; rime and visor-fog overlays are separate overlay sprites the presenter toggles from the same view (5.3: "overlays are always true"). Stagger is the one state where exaggerated frames are permitted (5.2), still as drawn frames.
  
  ### Locomotion state table (explicit, in the GDD)
  `IDLE ↔ WALK ↔ RUN`, `IDLE/WALK → CARRY_WALK` (on carry flag), `* → STAGGER` (Suit cap), `* → DOWN` (Suit cap), `* → CHANNELLING` (Interaction busy flag: movement blocked — or slowed; **flag for Interaction GDD**: does a cut lock the feet?). Transitions are evaluated in one `match` per tick from `(intent, suit_cap, busy, carry)`; no state-machine framework.

  ## 6. Testing — what the controller must expose
  
  Mirror the render GDD's `CameraSolver` shape: **`LocomotionStep.step(state, intent, collide: Callable) -> state`** as a pure `RefCounted`, no Node, no `Input`, no scene tree (H10). `collide(rect: Rect2i) -> bool` is injected (a list of `Rect2i` in tests; the Layout view in the game). `state` is the block's data (`pos: Vector2i, sub: Vector2i, octant, run, aim_angle, facing, odometer, cap`).
  
  Headless tests (gdUnit4 6.2.x runs on 4.7.2 `[REF]`; a Node-free step avoids the orphan-node exit 101):
  1. **Intent → position**: octant E, walk, N = 60 ticks → `pos.x += 120`, `pos.y` unchanged; run → +180.
  2. **Diagonal**: octant NE, walk, 40 ticks → each axis moved 56 or 57 px (`40 × 1.414 = 56.6`), magnitude within 1 px of 80; no tick moved more than 2 px on an axis.
  3. **Run ramp**: from idle, run E: first 6 ticks move 2 px each, then 3.
  4. **Stop clears `sub`**: walk NE 1 tick, stop, walk E 1 tick → exactly 2 px, never 3.
  5. **Wall**: rect at x ∈ [100,124): walking E from x = 90 ends at the largest x where the foot box does not overlap and stays there; NE against the same wall keeps moving north (slide).
  6. **Door**: leaf present → blocked; leaf removed → passes.
  7. **Whole-pixel invariant**: type-enforced (`Vector2i`) plus a snapshot round-trip test (CR-8) asserting every position field is int.
  8. **Determinism**: the same intent trace through two fresh kernels → identical snapshot hashes at tick N; the command-log replay (G3) reproduces `pos` and `odometer` with **no physics observations recorded**, because the avatar uses none.
  9. **Config invariants** (fail the build): `v_run < 266`; `v_run × 0.18 + L_MAX ≤ 108`; `v_run ≥ v_walk ≥ 1`; strides and speeds are integers; `FACING_HYST < 22.5°`.
  10. **Aim plumbing**: a synthetic raw-aim trace sweeping 0→90° over 30 frames produces ≤ 10 `set_aim` commands and a final command equal to the quantised 90°; a trace that jitters ±2° produces none.
  11. **Immediate acknowledgement**: pre-play token created on submit; cleared on `Applied`; reverted on `Rejected`; expired after `max_age`.
  12. **Two-local-instance check** (TD-FEASIBILITY: "periodically run two local instances"): two `Kernel` instances in one headless test, seats 1 and 2 bound to actors A and B; seat 2 submitting `set_move_intent` for actor A → `Rejected(ACTOR_NOT_OWNED)` and A does not move; identical traces on both instances → identical hashes. Plus a dev launch configuration that starts two windows (host + a second local seat on the same kernel in MVP; a `MIRROR` in VS-B) so the authority path is exercised by hand monthly.
  
  The presenter needs one test of its own: given `prev`, `curr`, `tick_alpha` → the written position equals `floor(prev + (curr − prev) × alpha)` and the light position equals that plus the hand point (render step 12's "zero render-px disagreement").

  ## 7. Risks for a solo first-timer, and the simplest shape
  
  **Risks, in order of likelihood**
  1. **Reaching for `CharacterBody2D.move_and_slide`** because every tutorial does — float positions after the first wall, engine physics in the sim, untestable. Name it as forbidden for the avatar in the GDD.
  2. **Reading `Input` in the presenter** or in `_process` — splits the sampling point and costs a tick; only the adapter touches `Input`, only in the physics callback before `step()`.
  3. **Turning on Godot's 2D physics interpolation** "to smooth it" — two interpolators (PR-4 rule 8 forbids it).
  4. **`round` vs `floor`** between sprite, light and camera → 1 px disagreement; one shared helper, `floor` only.
  5. **Angle wrap bugs** at ±180° in the threshold and hysteresis code — do the math in integer 1/4096 turns with modular distance.
  6. **Mouse projection under letterbox / pass B / zoom** — do not derive it; call the pipeline root (and expect step 11 to change it).
  7. **AnimationTree / state-machine plugin** for 6 states — overkill; a frame index into a `Sprite2D` sheet (`hframes/vframes`, row per `(state, facing)`) and a `match` are enough.
  8. **Hardcoding the speeds** — they are provisional until step 13 and must live in a config resource.
