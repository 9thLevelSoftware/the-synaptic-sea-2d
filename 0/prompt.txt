  ## Findings that change the brief (read first)
  
  1. **Peer ID is the wrong key for persistent per-player state.** The index says Sanity writes perception state "keyed by peer ID". To my knowledge, Godot ENet clients get randomly assigned peer IDs per connection and only the host is always 1 (not covered by `networking.md`, so verify). A save keyed by peer ID breaks the second time a guest joins.
     - **(proposal)** Persistent per-player state is keyed by a stable `PlayerId` (a seat). The kernel holds the live `peer_id → PlayerId` binding. In single-player, PlayerId 1 is bound to peer 1.
     - This touches Sanity, Suit, Save/Load and the VS-B Host-Owned World (guest carry-over) system.
  2. **"Presentation never writes" collides with UI that issues commands.** The Chart Table (pick a target) and menus must submit commands on behalf of the player.
     - **(proposal)** Distinguish *render presentation* (no submit access) from *input surfaces* (submit access as the local player's seat). Both are barred from mutating blocks. Needs creative-director and technical-director confirmation that this reading of the rule is intended.
  3. **There is a third subscriber class the constraints don't name: projectors.** Layout data must be projected onto physics shapes and bodies (Ship Section & Layout Data Model, Ship Body). Those are not CanvasItem/Material/Light2D writes. **(proposal)**: a `PROJECTOR` class owned by the block owner. It writes engine-side derived objects only and never writes blocks. Needs a technical-director ruling.
  4. **One-owner-per-block vs atomic multi-block commands.** Weld writes Graph, Layout and Body. Resolved in CR-9: owners expose mutators, and the kernel guarantees atomic apply. This is the single most load-bearing design decision in the kernel.
  5. **The index's "12 dependents" list is incomplete.** Interaction, Attention, and the Ship Section & Layout Data Model all register blocks or commands and so depend on the kernel but don't list it in `Depends On`. Item & Module Database is static definitions and probably needs no kernel edge. The Perception Filter's real kernel edge is as a PRESENTATION subscriber (it lists none today). The Life-Support Graph's edge on Save/Load is satisfied by the registry contract and may be redundant. Recommend an index correction.
  6. **Determinism has to be scoped honestly.** Godot physics is not deterministic and floats are not guaranteed across CPUs. The guarantee is: same build and platform, same command stream, same physics-observation stream gives the same kernel-owned state. Host-authoritative co-op does not need cross-machine lockstep, so this is sufficient (see CR-14).

  ## C.1 Core Rules
  
  ### Vocabulary
  
  - **Tick**: one fixed-step iteration of the authoritative simulation. Tick number `T` is a monotonically increasing integer.
  - **State block**: a named, versioned, single-owner container of domain state, registered with the kernel.
  - **Command**: a serializable request to change state, carrying issuer identity.
  - **Owner**: the domain system that is the only writer of a block's contents.
  - **Read view**: the read-only accessor an owner publishes for a block.
  - **Step hook**: owner-registered code that runs in the derived/propagation phase.
  - **Mode**: HOST (authoritative; the only mode in MVP) or MIRROR (VS-B guest: receives state, runs no authoritative tick). The kernel's public API is identical in both.
  
  ### Rules
  
  **CR-1. Fixed tick, decoupled from frame rate (proposal: 60 Hz).** The simulation advances in steps of exactly `1 / TICK_RATE` seconds of *simulated* time, independent of render frame time.
  
  - All simulation durations are expressed in ticks, never wall-clock seconds (the Attention tell window of 10–30 s is 600–1800 ticks at 60 Hz).
  - The kernel does not read wall-clock time anywhere in the simulation path.
  - *Alternatives considered:*
    - (a) Variable timestep: rejected, because it breaks replay, tests and save equivalence.
    - (b) 30 Hz kernel tick: cheaper, and friendlier to a future network. But it adds up to 33 ms input-to-effect latency and sits at an awkward ratio to Godot's 60 Hz physics tick.
    - (c) 60 Hz kernel tick with per-hook step divisors (chosen): input and physics-adjacent systems run every tick, while the Graph, Attention and Suit vitals run at 10–20 Hz via divisors (CR-3). This costs nothing extra and keeps one clock.
  - Tick-source mechanism (physics callback vs custom accumulator) → ADR.
  
  **CR-2. Tick phase order.** Each tick executes these phases, in this order, to completion, with no interleaving:
  
  | # | Phase | What happens | Who may write blocks |
  |---|-------|--------------|----------------------|
  | P0 | Begin | Tick counter increments; the intake queue is *frozen* (commands arriving now wait for T+1) | nobody |
  | P1 | Intake | Frozen queue sorted by the ordering key (CR-13), truncated to the per-tick budget; overflow stays queued in order | nobody |
  | P2 | Dispatch | For each command in order: authority check → validate → apply or reject (CR-5) | the command handler, inside APPLY only |
  | P3 | Step | Registered step hooks run in fixed declared order; each hook runs when `T mod divisor == offset` | the hook's own block, plus owner-declared public mutators of other blocks (CR-9) |
  | P4 | Commit | Dirty sets finalised; the "tick committed" marker advances; interpolation baseline captured | nobody |
  | P5 | Notify | Batched change notifications delivered to subscribers (CR-10) | nobody (writes disabled) |
  | P6 | Boundary services | If pending: snapshot (Saving), state-change requests, command-log append | the kernel only |
  
     - P2 commands see the effects of earlier P2 commands in the same tick.
     - P3 sees all of P2's effects.
     - Subscribers in P5 and all presentation only ever see the post-P4 state, never a half-applied tick.
  
  **CR-3. Step hooks and ordering.** Domain systems register step hooks with `(hook_id, owner, divisor, offset, after: [hook_ids])`.
  
  - The kernel resolves a total order by topological sort of the declared `after` edges. Ties break by registration order, then hook_id lexicographically.
  - A cycle or an unknown hook_id in `after` is a boot-time failure (CR-6).
  - Sim-to-sim data flow within a tick is "reader declares `after` writer". Example: Suit vitals declare `after: graph.propagate` because they read compartment atmosphere.
  - The order is data, so it is testable and printable (Debug Overlay).
  - Hooks may not call the submit API with PLAYER origin. They may submit SYSTEM-origin commands (CR-4).
  
  **CR-4. Command anatomy and origin.** A command is plain serializable data:
  
  | Field | Meaning |
  |-------|---------|
  | `type` | Registered command type ID (owned by a domain system) |
  | `issuer_peer` | Peer ID, stamped by the kernel's ingress, never taken from payload |
  | `origin` | `PLAYER` or `SYSTEM` (stamped by ingress, never from payload) |
  | `actor` | The entity the command acts as (opaque ID), or none |
  | `seq` | Per-issuer monotonically increasing integer |
  | `payload` | Plain data (primitives, arrays, dictionaries, packed arrays), with no object references, node paths or callables |
  | `queued_tick` | Stamped on enqueue |
  
     - In single-player, the local input adapter is the only ingress, stamping `issuer_peer = 1, origin = PLAYER`. SYSTEM origin is used only by host-side code (step hooks, Save/Load control).
     - **Serializability test:** in debug builds every command is round-tripped through serialization before dispatch, even locally. A command that cannot survive the round trip is a defect. This is the cheapest guarantee that a future RPC ingress needs no command-type rewrites.
     - **Submit is fire-and-forget.** The only return is a result event keyed by `(issuer_peer, seq)` (CR-5). There is no synchronous "did it work" return, because a remote client could never provide one. UI that needs the answer waits for the result event.
  
  **CR-5. Command lifecycle.** Every command passes through these stages and reaches exactly one terminal state with exactly one result event delivered to the issuer (the "exactly-one-result" guarantee):
  
  1. **Issued**: submit called.
  2. **Admission** (at submit, before queueing): kernel state accepts commands (C.2); type registered; queue not full; not a duplicate or out-of-order `seq`; issuer rate limit. Failure goes straight to Rejected.
  3. **Queued**: waits for the next tick's P1.
  4. **Authority check** (P2, kernel):
     - (i) `origin` is in the type's `allowed_origins`;
     - (ii) if the type declares `actor_binding = OWNED_BY_ISSUER`, the kernel's binding table says `issuer_peer` controls `actor`;
     - (iii) the command's age `T − queued_tick` does not exceed the type's `max_age_ticks`.
  5. **Validate** (P2, owner handler, read-only): the owner's `validate(cmd, read_views)` returns OK or a domain reason code. It must be side-effect free and may not write.
  6. **Apply** (P2, owner handler): `apply(cmd, mutation_scope)`. By contract apply cannot fail once validate passed (CR-9).
  7. **Terminal.** The command ends in exactly one of:
  
  | Terminal state | Meaning |
  |----------------|---------|
  | Applied | Effects are in state as of tick T |
  | Rejected(reason) | No effect |
  | Dropped(reason) | Never evaluated: kernel reload or shutdown flushed it |
  | Superseded | Coalesced away by a newer command of a coalescing type |
  
  **Reject reasons (kernel-defined, closed set):** `NOT_ACCEPTING` (kernel state), `PAUSED`, `UNKNOWN_TYPE`, `QUEUE_FULL`, `RATE_LIMITED`, `DUPLICATE_SEQ`, `ORIGIN_NOT_ALLOWED`, `ACTOR_NOT_OWNED`, `STALE`, `MALFORMED` (fails the payload schema check), `VALIDATION_FAILED(domain_code)`. Domain codes are namespaced strings or ints owned by the registering system, which keeps the kernel from defining other systems' semantics. Reasons are for logs, UI feedback and QA, never for deciding whether the world lies.
  
     - Coalescing: a type may declare `coalesce = LATEST_PER_ACTOR_PER_TICK` (movement intents). Edge-triggered inputs (press, release, confirm) must declare `coalesce = NONE` or taps are lost.
     - The kernel never retries a rejected command. Retry is the issuer's decision.
  
  **CR-6. Registration happens at boot, then freezes.** Block registration, command-type registration and hook registration are only legal in Booting. After Booting → Running the registries are immutable until shutdown.
  
  - Registration is an explicit declaration at boot, not discovered via the scene tree.
  - Reason: a frozen registry gives a stable block set for snapshots and a stable hook order for determinism, and means no late registration can surprise a replication adapter.
  - Violations (duplicate IDs, unknown command type in a handler, missing owner) fail boot loudly in all builds.
  
  **CR-7. Authority model (behaviour).**
  
  - **The host is the sole authority.** Only the host's kernel (mode HOST) runs the tick and applies commands. A MIRROR kernel never applies commands.
  - **Who may issue what** is declared per command type by its owner:
    - `allowed_origins ⊆ {PLAYER, SYSTEM}` and `actor_binding ∈ {NONE, OWNED_BY_ISSUER}`.
    - A PLAYER command that acts on an entity requires the issuer to control that entity.
    - SYSTEM commands never arrive from the network. Remote ingress always stamps PLAYER.
  - **Binding table (kernel-held identity data, not domain state):** `peer_id → PlayerId` and `PlayerId → {entity IDs controlled}`. Mutated only through a host-only kernel API called by the session owner (in MVP, a boot step; in VS-B, Co-op Session). It is not saved: sessions rebuild it, since peer IDs are per-session. Alternative considered: Player Controller owns the binding as a state block. Rejected because the kernel can then not authority-check without calling a domain system, and tests of the kernel in isolation need a binding. **(proposal; → ADR)**
  - **Single-player is not a special case.** The local player's input is PLAYER-origin peer 1, acting on an entity that peer 1 is bound to. The authority path is exercised on every command from day one. The TD risk "authority discipline lapsing" is mitigated structurally: there is no way to apply a command without passing the authority stage.
  - The kernel authority-checks *who*; owners validate *whether the world allows it*. The kernel never encodes game rules.
  - **Friendly-harm commands:** the kernel checks only issuer→actor ownership. The "attacker is below the sanity threshold" gate lives in Interaction's validate calling Sanity's query. Any such gate evaluates the *actor's* authoritative sanity from a SIM block, never the victim's or the attacker's perception.
  
  **CR-8. State-block registry contract.** To register, an owner provides:
  
  | Element | Contract |
  |---------|----------|
  | `block_id` | Unique, namespaced (`graph.state`). One owner per ID |
  | `owner` | The registering system; the only party permitted to mutate |
  | `schema_version` | Integer, bumped by the owner on any serialized-shape change |
  | `class` | `SIM` or `PERCEPTION_OUT` (CR-12) |
  | `persist` | bool. false = derived or transient, rebuilt after load |
  | `scope` | `SHARED` or `PER_PLAYER` (keyed by PlayerId). Recorded now for VS-B; unused in MVP |
  | `repl_hint` | `HOST_ONLY`, `SHARED_SUMMARY` or `OWNER_PRIVATE`. Mandatory declaration, unused in MVP, so no block is ever shipped without a decision |
  | `snapshot()` | Returns plain data for *canonical* state only. Pure, deterministic container ordering, no object references (entity references by stable ID), no derived caches |
  | `restore(data, stored_version)` | Replaces the whole block. The owner performs any migration from `stored_version` to current; an unsupported version is a reported failure, never a silent default |
  | `default_state()` | Used when a save lacks the block |
  | `post_restore()` | Called after all blocks restored: resolve cross-block IDs, rebuild derived caches, check invariants |
  | `read_view()` | The read-only accessor handed to other systems and subscribers |
  
     - **Restore order** is dependency order (blocks declare `restore_after`); `post_restore` runs for all blocks only after all `restore` calls complete.
     - **Entity IDs** are allocated by the owning block from a counter stored inside that block. The kernel allocates none.
     - **RNG:** no global `randf()` in simulation. Each system draws from a named stream whose counter state lives in the owner's block; the kernel supplies only a pure stream-derivation helper from `(world_seed, stream_name, counter)`. → Section D / ADR
     - **The kernel's own clock is the one kernel-owned registered block** (`kernel.clock`: tick counter plus world seed): other blocks hold absolute-tick timestamps that must survive a save. It contains no domain facts.
  
  **CR-9. Write discipline and atomicity.**
  
  - A block can be written only by its owner's mutators, and mutators only work inside a `WriteScope` the kernel issues during P2 apply or P3 step. Outside those phases (including in validate, P5 subscribers, and presentation) mutators assert in debug builds and are rejected in release.
  - **Cross-block commands (weld, cut, module install, pod hop):** the handler's `apply` may call *public mutators* that other owners explicitly publish. The kernel guarantees that the whole `apply` is atomic with respect to every other command, hook and snapshot. No tick phase interleaves with it, and one notification batch follows.
  - **Failure model: validate-then-apply, no rollback (chosen).** `validate` must prove everything via read-only queries (for weld: the Graph's pure join-validation query), and `apply` is infallible by contract. A failure inside apply is a *defect*: it moves the kernel to Faulted (C.2) and halts the tick.
    - Alternative considered: copy-on-write rollback of touched blocks. Rejected for MVP (cost, complexity). Revisit if validate/apply drift proves a recurring bug source.
    - Alternative considered: event sourcing, where state is a fold over the command log. Rejected as the primary store (log growth, migration pain). The kernel keeps a bounded command log for diagnostics and replay tests only.
  - In step hooks, effects on other systems take one of two forms: (a) an owner-declared unconditional mutator call (for example, a horror writing a footprint into the Graph's footprint channel); (b) a SYSTEM-origin command, validated by the target owner and processed at T+1 intake when the target may reject. Two paths is a complexity cost I accept; gameplay-programmer may want to collapse it.
  - The kernel enforces *phase*, not *caller*. "Only declared mutators are called by declared callers" is enforced by lint and the control manifest, not at runtime. → ADR
  
  **CR-10. Change notification contract.**
  
     - Notifications are emitted once per tick in P5, after commit, batched per block: `(block_id, tick, change_keys)`.
     - `change_keys` is an owner-supplied set of changed entity or field keys; if more than `MAX_DIRTY_KEYS` changed, it collapses to `ALL`.
     - Notification payloads carry **no state**. Subscribers fetch through the block's read view. This keeps notifications identical whether state arrived by command (HOST) or by replication (MIRROR), so presentation code never changes between modes.
     - **Subscriber classes**, declared at subscribe time:
  
  | Class | May do | Examples |
  |-------|--------|----------|
  | `PRESENTATION` | Read SIM and PERCEPTION_OUT views. Write only CanvasItem/Material/Light2D/particles/audio nodes | Failure & Trail, Instruments, HUD, Lighting, Perception Filter, Audio |
  | `PROJECTOR` | Same reads. Write engine-side derived objects owned by its block owner (physics shapes/bodies). Never writes blocks | Layout→physics projection **(proposal; needs TD ruling)** |
  | `REPLICATION` | Read all views marked for replication; send | Co-op adapter (VS-B) |
  | `DIAGNOSTIC` | Read everything, including kernel internals | Debug Overlay |
  | (none for SIM) | Simulation systems do **not** subscribe to notifications | Sim-to-sim is commands or ordered step reads (CR-3, CR-9) |
  
     - Subscriber handlers run with writes disabled, and are not given the submit API.
     - **Sim never calls presentation.** The flow is always state → notification → presentation. Horror "light disturbance" and Attention flicker are state the Lighting system reads, not calls into Lighting.
     - **Render interpolation:** the kernel exposes `tick_alpha` (fraction of the way to the next tick) and owners that need smooth motion expose previous and current committed values in the read view. → Section D / ADR
  
  **CR-11. Time model for presentation.** Presentation runs at render rate and reads "last committed tick" state. It never causes a tick, and pausing presentation effects (reduced motion) never pauses the sim.
  
  **CR-12. Perception isolation, enforced by block class.**
  
     - `SIM` blocks are readable by simulation code (validate, apply, step hooks) and by presentation.
     - `PERCEPTION_OUT` blocks (Sanity's per-player "what lies to show" output) are *write-only to simulation*: sim code, including the owner's own hooks, obtains no read view of them. Presentation and the replication adapter do.
     - Sanity's friendly-harm gate and drift read the sanity *level* (a SIM block), never the perception block.
     - In debug builds an attempted sim-side read of a PERCEPTION_OUT view asserts. In release it returns nothing.
     - Perception state is `persist = false` by default (reproducible from the sanity level and a seed); Sanity may override.
     - In VS-B, PERCEPTION_OUT is `OWNER_PRIVATE`: it replicates only to the owning peer.
  
  **CR-13. Determinism and ordering guarantees.** The following hold in HOST mode, same build and platform:
  
     - **G1 Order:** commands are applied in ascending `(queued_tick, host_order)` where `host_order` is a host-assigned enqueue index. In single-player this is submission order.
     - **G2 Single timeline:** every command applies at exactly one tick; no command applies partially across ticks.
     - **G3 Replay:** given an initial snapshot, the same command stream (with `queued_tick`s) and the same recorded physics observations, kernel-owned and block state at tick N is identical, compared via a canonical snapshot hash.
     - **G4 Save equivalence:** snapshot at tick T, restore, and continue gives a state identical to uninterrupted play (hash-compared), for `persist` blocks. This is the key regression test for the registry contract.
     - **G5 Exactly-one-result** per command (CR-5).
     - **G6 Atomic ticks:** observers never see a partially applied tick.
     - Physics-derived facts (positions after collision, contact events, raycast results used in step) are *inputs* from the engine. For G3 they must be recorded and replayed, or the replay test excludes physics-coupled blocks. This is a stated limit, not a defect. → ADR
  
  **CR-14. Hard rules (non-negotiable; each should become a lint or test).**
  
     - **H1 No domain state in the kernel.** Kernel-owned data is exactly: tick counter and seed (`kernel.clock`), the command queue, the registries, the peer/binding tables, the command log, kernel state, diagnostics. Any proposed addition fails review unless it is infrastructure.
     - **H2 No kernel-defined domain commands.** The kernel registers no gameplay command types. Its control plane (pause, save/load request, shutdown) is a host-local API, not remote commands. In VS-B a guest's pause or save request is a command defined by Session or Save/Load, validated on the host, which then calls the control API.
     - **H3 One owner per block; writes only via the owner's mutators inside a WriteScope.**
     - **H4 Presentation never writes simulation.** Render presentation gets no submit API and no mutators. Input surfaces (CR-4) submit commands only as the local seat.
     - **H5 No simulation system reads perception state** (CR-12).
     - **H6 Peer identity on every command**, kernel-stamped, never payload-borne.
     - **H7 Everything that crosses the kernel boundary is plain data** (commands, results, snapshots, notifications keys). No Object references, Callables or node paths.
     - **H8 No networking code in MVP.** The only ingress is local input; the only egress is local presentation. No ENet, RPC or Synchronizer usage.
     - **H9 Simulation never reads wall-clock or global RNG.**
     - **H10 Kernel logic is scene-tree independent** (runs headless, testable without a scene). Whether the kernel is an autoload or a node → ADR.
  
  **CR-15. Control plane (host-local, not commands).** `request_pause`, `request_resume`, `request_snapshot`, `request_restore`, `request_shutdown`. Callers are Save/Load, the Chart Table/pause UI (via a host-local call, not a command), and the boot code. Requests are honoured at tick boundaries (P6).
  
  **CR-16. Pause semantics.**
  
     - Paused stops the tick (no P0–P5) but not rendering.
     - While Paused, submit accepts only types flagged `allowed_when_paused` by their owner (menu actions, save, resume); everything else is rejected `PAUSED` immediately rather than queued, so there is no burst on resume.
     - **Pause is single-player only.** In co-op, a menu cannot stop a shared sim: VS-B will treat "pause" as a UI overlay and the kernel state stays Running. This must be settled before the Chart Table GDD, since "pick a target" may be assumed to happen while paused.
     - Pausing does not stop the engine scene tree's process modes. Relationship to scene tree pause → ADR.
  
  **CR-17. Bounds and overload behaviour.**
  
     - Intake budget: at most `MAX_CMDS_PER_TICK` processed per tick; the remainder wait in FIFO order.
     - Queue capacity: `QUEUE_CAPACITY` total and `PER_ISSUER_CAPACITY` per issuer; beyond that, `QUEUE_FULL` at admission. Never silent drop, never unbounded growth.
     - Catch-up: if a frame is late, the kernel runs at most `MAX_TICKS_PER_FRAME` ticks, then lets simulated time lag rather than spiral. A lag counter is exposed to diagnostics.
     - Step overrun: P3 exceeding `STEP_BUDGET_MS` logs a diagnostic naming the slowest hooks. The tick still completes (correctness over frame time).
     - A command older than its type's `max_age_ticks` when reached is rejected `STALE`, so a hitch cannot unleash a second of stale movement intents.
  
  **CR-18. Snapshot semantics (Save/Load and future guest transfer).**
  
     - A snapshot is taken only at a tick boundary (P6), covers all `persist` blocks at the same tick T, and records `(T, per-block schema_version)`.
     - Capture is synchronous and in-memory; the tick does not advance during capture (state Saving). File I/O is Save/Load's concern and happens off the kernel's critical path → ADR.
     - Restore replaces *all* persisted blocks atomically; partial restore is not supported. Failure at any block aborts and leaves the kernel in Faulted with the pre-restore state intact if possible. Save/Load decides user messaging.
     - **VS-B reuse:** with join-in-progress deferred, guests still need the world at session start. The same snapshot/restore contract is the transfer mechanism, so it must be complete and cheap.
  
  ### Alternatives considered, summarised
  
  | Decision | Chosen | Rejected and why |
  |----------|--------|------------------|
  | Tick | 60 Hz fixed + step divisors | Variable timestep (no replay); 30 Hz (latency, ratio to physics) |
  | Command return | Async result event | Synchronous bool (impossible for remote issuers) |
  | Multi-block write | Owner mutators + atomic apply, validate-first | Rollback (cost); event sourcing (migration) |
  | Notification | Batched, key-only, post-commit | Signal-per-write (mid-tick inconsistency, spam); state in payload (differs HOST vs MIRROR) |
  | Authority binding | Kernel-held table | Controller-owned block (kernel can't check without a domain call) |
  | Per-player key | PlayerId | Peer ID (unstable across sessions) |

  ## C.2 States and Transitions
  
  ### Kernel states
  
  | State | Meaning | Tick advancing | Accepts submit |
  |-------|---------|----------------|----------------|
  | `BOOTING` | Registries being populated (CR-6); nothing loaded | No | No (`NOT_ACCEPTING`) |
  | `LOADING` | Restoring a snapshot or building a new-game state (also entered mid-session for reload, including the MVP death-stub reload) | No | No (`NOT_ACCEPTING`) |
  | `RUNNING` | Normal ticking | Yes | Yes |
  | `PAUSED` | Single-player pause | No | Only `allowed_when_paused` types |
  | `SAVING` | Snapshot capture at a tick boundary. Transient: returns to the prior state | No | Queues normally (it is expected to be brief); no tick runs until capture completes |
  | `FAULTED` | Invariant violation, apply failure, restore failure, or boot failure after registration. Not requested by anyone | No | No |
  | `SHUTTING_DOWN` | Teardown | No | No |
  
  `FAULTED` is an addition to the requested list. Without it, an infallible-apply violation (CR-9) has nowhere to go but undefined behaviour. In FAULTED the kernel never writes or autosaves over an existing save. A dev build halts with diagnostics; release returns to the menu.
  
  ### State transitions
  
  | From | Trigger | To | Notes |
  |------|---------|----|-------|
  | (start) | Process start | BOOTING | |
  | BOOTING | Registries valid and frozen | LOADING | A new game also passes through LOADING, populating blocks from `default_state()` |
  | BOOTING | Duplicate ID, hook cycle, unknown dependency | FAULTED | |
  | LOADING | All blocks restored, `post_restore` passes | RUNNING | Initial state is RUNNING (or PAUSED if the caller requested it) |
  | LOADING | Restore or `post_restore` fails | FAULTED | Previous state preserved if possible |
  | RUNNING | `request_pause` | PAUSED | Honoured at the next tick boundary |
  | PAUSED | `request_resume` | RUNNING | |
  | RUNNING / PAUSED | `request_snapshot` | SAVING | Remembers the return state |
  | SAVING | Capture complete | prior state (RUNNING or PAUSED) | |
  | SAVING | Capture error | FAULTED | |
  | RUNNING / PAUSED | `request_restore` (reload, load game, death stub) | LOADING | Queue is flushed; every flushed command receives `Dropped(RELOAD)` |
  | RUNNING / PAUSED / FAULTED | `request_shutdown` | SHUTTING_DOWN | Queue flushed with `Dropped(SHUTDOWN)` |
  | RUNNING | Apply failure, step invariant failure | FAULTED | |
  | FAULTED | `request_restore` (explicit user action) | LOADING | The only way out other than shutdown |
  | SHUTTING_DOWN | Teardown complete | (end) | |
  
  Every other (state, trigger) pair is invalid. The kernel ignores it and reports it to diagnostics. It is never a silent state change. In particular: no transition from SAVING except to its return state or FAULTED; no restore request during SAVING (it waits for the boundary); no RUNNING from BOOTING directly.
  
  ### Per-command states
  
  | State | Entered when | Next |
  |-------|--------------|------|
  | `ISSUED` | submit called | ADMITTED or REJECTED |
  | `ADMITTED` | passes admission | QUEUED |
  | `QUEUED` | enqueued | AUTHORIZING, or DROPPED on reload/shutdown flush, or SUPERSEDED by a coalescing successor |
  | `AUTHORIZING` | reached in P2 | VALIDATING or REJECTED |
  | `VALIDATING` | authority passed | APPLYING or REJECTED |
  | `APPLYING` | validate OK | APPLIED (or kernel FAULTED on apply failure) |
  | `APPLIED` (terminal) | | result event emitted |
  | `REJECTED(reason)` (terminal) | any failing stage | result event emitted |
  | `DROPPED(reason)` (terminal) | flush | result event emitted |
  | `SUPERSEDED` (terminal) | coalesced away | result event emitted |

  ### Rules for consumers (to carry into Dependencies and the control manifest)
  
     - A system that wants state to persist registers a block; it never talks to Save/Load directly.
     - A system that wants to change another system's state publishes a command or a mutator; it never reaches into another's block.
     - A system that wants to *show* state subscribes and reads; it never calls into the simulation.

  ## Expected disagreements
  
  **From gameplay-programmer (feel/latency):**
  
     1. **Input latency.** Queue-then-apply means input waits for the next P2: up to 16.7 ms plus render-frame alignment, versus immediate application. They may ask for local immediate application or client-side prediction. My position: single-player cost is below one frame; prediction is a VS-B problem and the command `seq`/`queued_tick` fields leave room for it. I'd defend not special-casing the local player.
     2. **Coalescing loses taps.** Mitigated by requiring edge-triggered types to use `coalesce = NONE`; they may still want input buffering windows.
     3. **Async results.** UI that wants an immediate "did it work" (hold-to-confirm destructive actions) must wait a tick for the result event. They may want a synchronous local fast path; I'd refuse because it would not survive a remote issuer.
     4. **Step-hook cross-writes.** Two mechanisms (declared mutator vs SYSTEM command with T+1 latency) may be seen as a needless fork; one-tick latency on system-to-system effects may break tell-timing logic.
     5. **Two-phase handlers** are more code per command than a single function. Typed command objects vs dictionaries in GDScript (cost and ergonomics) will be argued.
     6. **Interpolation:** previous/current values in read views is extra work for every moving block.
     7. **60 Hz Graph** is a non-issue only because of divisors; they may want different cadences per system, which the model already allows.
  
  **From engine-programmer (Godot integration):**
  
     1. **Tick source** (physics callback vs accumulator), and determinism with Godot's non-deterministic physics. They will say G3 is unachievable with physics-coupled blocks; I've scoped it, but they may want the claim reduced further.
     2. **Replication shape.** MultiplayerSynchronizer syncs node properties; data blocks are not nodes. They may push for a node-centric model, which conflicts with "Graph as pure data off the scene tree". I'd hold the data-block model and let the adapter be a thin node layer.
     3. **Command payloads over RPC.** Plain data only (Objects not sent by default; verify); strong typing vs dictionaries.
     4. **Peer IDs:** the per-session random client ID assumption needs verification on 4.7.2 (not in the engine reference).
     5. **Read-only views in GDScript** have no const references; enforcement means debug-build copies or frozen wrappers, with performance cost.
     6. **Signals vs custom dispatch** for notifications (ordering, cost, headless testing). The kernel must run without SceneTree (H10), which affects autoload vs node.
     7. **Pause semantics** vs `SceneTree.paused` and process modes.
     8. **PROJECTOR class** and when engine objects may be created or freed relative to the physics step.
     9. **Snapshot data types** (Variant serialization vs JSON vs resource), and the main-thread restriction on capture.
