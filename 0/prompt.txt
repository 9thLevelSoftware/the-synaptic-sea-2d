  ## Section C input: feasibility and feel for the Command & Simulation Layer
  
  Basis: `game-concept.md` (two rhythms, MVP item 7, Technical Considerations, TD risks) and the systems-index rationale for system 1. That rationale says: thin kernel, no domain state, peer id on every command, ADR-first. I did not write any files. Numbers below are engineering judgment, not measured. The tick-rate numbers need confirming in the spike phase.
  
  ### 1. Input latency and feel
  
  **Tick rate.**
  - Run the simulation at **20 Hz (50 ms)** by default. Make it a config constant, and test at 30 Hz.
  - Run physics and character movement on Godot's `_physics_process` at 60 Hz. Do not run the kernel at 60 Hz.
  - Why 20 Hz is enough:
    - The life-support graph (O2, heat, power propagation) and Attention are slow systems. Their visible changes take seconds, and Pillar 2 wants a 10-30 s tell. Even 10 Hz would be fine for them.
    - The breach rhythm is frantic because of the player's own movement and the hull-failure event, not because the sim reacts every 16 ms.
  - A command issued mid-tick waits on average 25 ms and at worst 50 ms before the sim applies it. A 3/4 top-down game with channelled actions (cutting a hatch, patching a leak, which take seconds) does not need the sim to react faster than that.
  - Do not go below 15 Hz. At 10 Hz, worst-case latency is 100 ms, which makes discrete clicks and button presses feel mushy. I would push back on any proposal of 10 Hz or lower.
  - Do not go above 30 Hz. The cost buys nothing for this design.
  
  **Make acknowledgement immediate, not the result.**
  - The interact press should produce a local response in the same frame: a tool sound, a hand animation start, and a progress ring starting. The sim then confirms on the next tick.
  - Hatch cutting and leak patching are timed channels. They are "command start, sim accrues progress per tick, sim completes". The progress value is sim state and the ring renders it.
  - The 50 ms ack delay is invisible when something starts animating immediately. The only visible effect is a ring that begins a tick later.
  
  **Movement: continuous intent, not a command per tick.**
  - Sample the move vector and aim in `_physics_process`. Do not send a command every tick.
  - The player body is a kinematic body on the ship's composite body. The Ship Body and Interior Physics system (12) is moving-platform territory, which makes this harder than a plain top-down controller.
  - Movement should stay on the physics side, with the sim seeing position as a read.
  - Position is a state block, written by a movement step, and the authority check applies to the intent. Concretely:
    - `set_move_intent(peer, vec)` is a command sent only when the quantized vector changes. At 8 directions plus analog magnitude that is a few per second, not 20 per second.
    - The sim's tick applies the latest intent.
    - In single-player, the local body can integrate movement directly in `_physics_process` from the same intent, so the sprite never waits for a tick.
  - This is the classic problem of local-feel movement versus authoritative movement. Single-player does not need to solve it, but the shape must allow solving it later.
  - Recommended MVP shape: **intent is a per-peer state record that the kernel stores**. Movement code reads the intent and moves the body. A later co-op version replicates the intent and reconciles position.
  - Do not route 60 Hz movement through a command queue. That adds latency and dispatch cost for no benefit in single-player.
  
  **Where prediction is unnecessary now and must be designed for later.**
  
  | Area | Single-player MVP | Design-for-later requirement |
  |---|---|---|
  | Own-player movement | Direct, local integration; no prediction | Movement is a pure function of (state, intent, delta) so it can be re-run for reconciliation. No `randf()` or scene-tree reads inside it. |
  | Channel start (cut, weld, patch) | Immediate local feedback, sim confirms next tick | The local "pending" visual state is separate from the confirmed sim state. This is a 2-state UI, not prediction. |
  | Interact results (door, switch) | Wait for the tick; at 50 ms nobody notices | Commands carry a client sequence number so replies can be matched. Cheap to add now. |
  | Graph, Attention, Sanity | No prediction ever; clients only render | Nothing. These are host-only. |
  | Hallucination filter | Presentation only; reads true values | Nothing. |
  
  Two things to build in now, because they cost almost nothing and are painful to retrofit: a `seq` field on every command, and a tick number stamped on every state change notification.
  
  ### 2. Command granularity
  
  **Discrete commands** (a player decision with a start, a target and a result):
  - `begin_cut(target)`, `begin_weld(target)`, `begin_patch(target)`. Each starts a channel.
  - `cancel_channel()`.
  - `install_module(slot, item)`, `remove_module(slot)`.
  - `toggle_beam(on)`, `toggle_device(id)`.
  - `interact(target)`.
  - `pickup(item)`, `drop(item)`, `use_item(item)`.
  - `pod_hop(destination)` (the abstracted transit).
  
  **Continuous intents** (a state the player holds, not a decision):
  - Move vector.
  - Aim or facing (the beam direction, 5-facing sprite).
  - Hold-to-channel inputs. The *button hold* is an intent, but the *start* and *cancel* are commands.
  - Sprint or crouch, if they exist.
  
  **Rule of thumb.** If the sim must log, validate, save or replay it, it is a command. If it is "what is the stick doing right now", it is an intent.
  
  **Pitfalls of over-granular commands for a solo first-timer.**
  1. **One command class per verb.** Twenty small `Command` subclasses with a validate/apply/serialize method each is a lot of boilerplate. Use a plain `Dictionary` or a small shared command object `{type, peer, seq, args}` and register a handler function per type.
  2. **Per-tick commands for things that are really state.** Beam direction every tick floods the queue and the log. Make it an intent.
  3. **Commands for things only the presentation cares about.** UI opening, camera, tooltips, and the hallucination filter are never commands.
  4. **Commands that duplicate domain logic.** A command should say what was requested. The domain system decides if it is valid. Do not put the repair rules in the command object.
  5. **Undo and replay machinery up front.** Do not build it. Log commands in debug builds only.
  6. **Generic "set property" commands.** `set_value(path, value)` is tempting and it silently bypasses the whole authority idea. Every mutation should name a domain verb.
  
  ### 3. Rejection UX
  
  The kernel must return a structured result and emit a signal. It must know nothing about UI.
  
  **What presentation must receive**, for every command:
  - `seq` and the issuing `peer`, so the caller can match the reply.
  - `ok: bool`.
  - `reason`: a stable enum (not a string). A starting set:
    - `OUT_OF_RANGE`
    - `INVALID_TARGET` (it no longer exists, or it was changed)
    - `NOT_AUTHORIZED` (peer lacks authority; unreachable in single-player but must exist)
    - `PRECONDITION` (missing tool or item, no power, wrong state)
    - `BUSY` (already channelling)
    - `STALE` (state changed since issue)
  - `subject`: the target id the rejection refers to, so presentation can highlight the right thing.
  - `detail`: an optional small dictionary for numbers the domain wants shown (for example `{needed: "cutter"}`), never text.
  - `tick`: the tick on which it was decided.
  
  **Honest feedback rules.**
  - Presentation maps `reason` to a sound, a shake, a tooltip, or nothing. The kernel never carries display strings (that also keeps localization and accessibility captions in the UI layer).
  - Pillar 1 and 4 interaction: rejection reasons come from true state. If the filter is lying about a scrubber being fixed and the player tries to repair it, the rejection must be honest, because it is one of the "channels of truth". The kernel must not apply the hallucination filter to a rejection. Say that in the spec. Without it, the "no lie is unfalsifiable" check gets weaker.
  - Make rejection a first-class signal: `command_resolved(result)`. The same signal carries success. Presentation does not have to poll.
  - Also distinguish *rejected at issue* from *aborted mid-channel*. For example, a hatch cut is accepted, then power drops and the channel stops. The channel owner reports it through state change (`channel_state = ABORTED, reason`), not through the command result.
  
  ### 4. Testing
  
  **What makes headless testing work.**
  - The kernel and every state block are plain `RefCounted` objects with no `Node`, no `get_tree()`, no autoload references, and no `Time` or `randf()` calls inside simulation code.
  - Keep one explicit time source: the tick counter. Provide `kernel.step(n)` that advances n ticks synchronously, with no `_process` involvement. A test then looks like: build a graph, submit a command, `step(100)`, assert on the state block.
  - Randomness comes from a seeded RNG object owned by the kernel and passed in. Same seed gives the same result in tests.
  - Domain systems register state blocks and handlers with the kernel through a plain method call. Tests can construct a kernel and register only the Life-Support Graph and Attention blocks, with no other system.
  - Dependency injection: the kernel does not find systems itself. The composition root (a single scene or script) builds the kernel and wires systems. Tests build a smaller wiring.
  - Autoloads are the main danger. A global `Kernel` singleton makes every test share state. Use an autoload only as a thin holder of the instance, and have all code accept the kernel as a parameter.
  
  **For gdUnit4 specifically.**
  - Test suites extend `GdUnitTestSuite` and can run without a scene when the code under test is `RefCounted`.
  - Life-Support Graph test examples: a leak propagates along edges at the expected rate over N ticks; welding joins nodes; a save round-trip produces the same state hash.
  - Attention test examples: light plus noise inputs over N ticks cross the threshold on the expected tick; restraint lowers it.
  - Provide a `state_hash()` over all registered blocks. It makes "same inputs gives same state" a one-line assertion and doubles as the desync check later.
  
  **What the kernel must expose for a two-local-instance check later.**
  - A `peer_id` on the kernel and on every command (single-player = 1).
  - Command submit that works for a remote peer id (`submit(cmd)` where `cmd.peer` is set by the transport, never by the caller's own claim). Add the authority check now, even if it is trivially true.
  - Serialization of a command to a `Dictionary` of primitives, so a transport can send it.
  - Per-block `serialize()` and `apply_snapshot()`. Save/Load (system 25) needs these anyway, and co-op reuses them for the join snapshot.
  - Per-block change notification carrying `(block, key, tick)`, so a replicator can later send deltas without the block knowing.
  - `state_hash(tick)` for comparing two instances.
  - Rule for the control manifest: nothing outside a command handler may write a state block. A cheap enforcement is a debug-only assertion that a "write window" is open during handler execution.
  
  Caveat: listen-server means the host runs this kernel and clients run a thin copy. I have not designed that part. It is VS-B work and should stay out of the MVP kernel spec beyond the hooks listed above.
  
  ### 5. Risks for a solo first-timer
  
  **The three ways this kernel becomes a drag on velocity.**
  1. **Ceremony per command.** If adding "toggle the beam" requires a command class, a validator, a serializer, a handler, a signal and a registry entry in five files, every feature costs a day and you stop respecting the layer. The temptation then is to bypass it, which is exactly the authority-lapse risk TD named.
  2. **Premature generality.** Replay, undo, rollback, delta compression, a command bus with middleware, a generic schema system. None of it is needed for the MVP, and each is easy to start and hard to finish.
  3. **Block and signal sprawl.** Every domain system registering many small state blocks with fine-grained change signals produces a web of connections that is hard to debug in a first project, and presentation code ends up subscribing to dozens of things.
  
  **Simplest shape that avoids them.**
  - One `SimKernel` class (RefCounted), about 200 lines. Fields: tick counter, `Dictionary` of handlers by command type, `Dictionary` of state blocks by name, a command queue, a seeded RNG.
  - Commands are Dictionaries (`{type, peer, seq, args}`). One line registers a handler: `kernel.register("begin_cut", life_support.on_begin_cut)`. The handler validates, mutates its own block, and returns `ok` or a reject reason. That is the whole per-verb cost.
  - State blocks are plain objects with `serialize()`, `apply_snapshot()` and a `changed` signal. Coarse blocks: one per domain system, not one per entity.
  - Presentation connects to one or two signals per block and reads the block. It never calls a handler directly; it calls `kernel.submit(cmd)`.
  - The tick loop is `_physics_process` accumulating delta, running 0 to N sim steps with a cap (for example max 5 steps per frame) so a hitch cannot cause a spiral.
  - Authority check is a single function, `can(peer, cmd) -> bool`, trivially true for peer 1 now.
  - Defer everything else: replay, undo, snapshots beyond what save needs, network transport.
  
  **Things I would push back on in a pure-architecture proposal.**
  - A tick rate at or below 10 Hz, or a movement-through-commands-every-tick design.
  - Treating every mutation, including hold inputs and aim, as a logged command.
  - A strict "presentation never writes" rule enforced with heavy machinery. A convention plus the debug write-window assertion is enough.
  - Full client-side prediction and rollback designed in the MVP. Hooks (`seq`, tick stamps, snapshot and hash) are cheap and enough.
  - A global singleton kernel that tests cannot replace.
  - Requiring a state block per entity. Use coarse blocks.
  - Anything that makes a feature cost more than a handler function plus a registry line. That is the velocity test I would put in the acceptance criteria: adding a new verb touches at most two files.
  
  **Suggested acceptance criteria to feed Section C.**
  - A headless test advances 1,000 ticks with only the Life-Support Graph and Attention registered, with no scene tree, and produces an identical `state_hash` on two runs with the same seed.
  - Every rejected command yields a `reason` enum and `subject`, and no display strings.
  - Movement intent updates at no more than 10 commands per second per peer in normal play.
  - A new command verb can be added by editing one handler and one registration line.
  - Debug builds assert if a state block is written outside a handler.
  
  Open points for the owning designers: the exact tick rate (20 versus 30 Hz) should be fixed after the spike on the moving-ship weld, and the exact `reason` enum should be reviewed once the Interaction System GDD exists.
