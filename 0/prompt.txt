  ## Detailed Design
  
  ### Core Rules
  
  *Specialists this draft expects at the table: ux-designer (comfort, rebinding, gamepad), gameplay-programmer (feel, physics), systems-designer (vitals thresholds), creative-director (pillar alignment). Where they will disagree is listed at the end. Items tagged **→ ADR** are engine-integration choices deliberately left out of this behaviour spec.*
  
  **Vocabulary.** *Input Adapter*: the presentation-side object that reads devices and **submits** commands as the local seat — kernel subscriber class `INPUT_SURFACE` (CR-10). *Controller Sim*: the simulation system that **owns** the block `controller.state` (per controlled actor: intent, gait, facing, locomotion state, carry/channel references) and runs step hook `controller.step` at divisor 1. *Avatar Presenter*: the `PRESENTATION`-class node that draws any crewmate body (local or remote) from read views; it is not part of this system's simulation and never submits. *Facing*: one of 8 octants (S, SE, E, NE, N, NW, W, SW), five drawn, three mirrored (art bible 5.6). *Aim*: a direction in the body frame; *raw aim* is the Adapter's local, un-quantised, per-frame value; *committed aim* is the quantised value last applied to `controller.state`. *Gait* ∈ {WALK, RUN}. *Body frame*: the ship-local coordinate frame of the body the actor is on (pipeline C2). *Channel*: a multi-tick action (cut, weld, patch) owned by another system whose progress accrues in that owner's block.
  
  **PC-1. Three parts, and the control-manifest lines that separate them.** (a) The **Input Adapter** reads devices, quantises, and submits `PLAYER`-origin commands as peer 1 acting on the entity the binding table binds to PlayerId 1 (CR-7). It writes no block, ever; it may write only its own local state (raw aim, last-acknowledged intent, hold timers, active device). (b) The **Controller Sim** registers `controller.state` (`SIM`, `persist = true`, `persist_scope = WORLD`, `scope = PER_PLAYER` keyed by PlayerId for the local seat's actor record, `repl_hint = SHARED_SUMMARY`), the command types `set_move_intent`, `set_aim`, and the hook `controller.step` (divisor 1, `after: suit.vitals`). It writes its block only in `apply` and inside its hook (CR-9); it may not submit `PLAYER`-origin commands (CR-3) — only the Adapter submits. (c) The **Avatar Presenter** reads `body.state` (position prev/curr), `controller.state` (facing, gait, locomotion state, hand point), `emitter.state` (beam lit, shape), and `tick_alpha`; for the *local* avatar only it also reads the Adapter's raw aim. It writes CanvasItem / Light2D / AnimatedSprite properties and nothing else. *Rationale.* The brief's manifest line "controller submits via `INPUT_SURFACE` only; never writes blocks" is true of the Adapter and false of the Controller Sim; naming both "the controller" would read as "this system has no block", and then facing and gait would end up as presentation state that co-op cannot replicate and a save cannot restore. *Alternative rejected:* fold the Controller Sim into Ship Body (one "character" block) — rejected because intent and facing are seat semantics (what the player asked for, readable by Interaction, Attention and the HUD) while position is a physics fact (kernel G3's determinism limit); keeping them apart lets the replay test exclude physics without losing the input record.
  
  **PC-2. Input model: actions, intents, commands.** The game reads **named actions** (`StringName`, rebindable, Settings & Input Rebinding), never raw keys or `device == 0` (4.7: `InputEvent.DEVICE_ID_MOUSE` / `DEVICE_ID_KEYBOARD`; identify by event type). **→ ADR** (InputMap actions vs a custom binding layer; edge detection by event vs polling).

  | `move_up/down/left/right` | continuous | WASD / left stick | part of `set_move_intent` |
  | `run` | hold (toggle offered in Settings) | Shift / L3 | part of `set_move_intent` (`gait`) |
  | aim | continuous | mouse cursor / right stick | `set_aim` (quantised); raw aim kept locally |
  | `beam_toggle` | press | F / Y | `toggle_beam` (owner: Emitter State) |
  | `interact` | press; hold for destructive verbs | E / A | `interact {target}` or the verb Interaction names; hold-to-confirm runs locally (PC-6) |
  | `tool_use` | hold = channel | LMB / RT | `begin_cut` / `begin_weld` / `begin_patch` on press, `cancel_channel` on release (owner: Interaction or Assembly) |
  | `tool_1..4`, `tool_next/prev` | press | 1–4, scroll / LB, RB, d-pad | `equip_tool` (owner: Suit & Equipment) |
  | `drop` | press | G / B (held while carrying) | `drop` (owner: Interaction) |
  | `inspect` | press | R / X | Interaction's inspect verb (HR-14 mirror card) |

  *Intents vs commands (CR-4).* Two types are **intents** with `coalesce = LATEST_PER_ACTOR_PER_TICK`, `max_age_ticks = 30`: **`set_move_intent {dir: 0..7 | NONE, gait}`** and **`set_aim {angle_q: int}`**. Everything else is a **command** with `coalesce = NONE`, `max_age_ticks = 120`, `actor_binding = OWNED_BY_ISSUER`. The Adapter sends an intent **only when its quantised value changes**: the 8-way direction (stick dead-zone `STICK_DEADZONE` = 0.25 of full deflection, then octant with ±`DIR_HYSTERESIS_DEG` = 4°), the gait, or the aim angle quantised to `AIM_QUANTUM_DEG` = 5°. At rest that is zero sends; during a mouse sweep at most one `set_aim` per tick (coalescing makes more impossible), which is inside the kernel's budget (`MAX_CMDS_PER_TICK` 128) and is the kernel's stated design. There is **no input buffering** of commands in the Adapter: a tap during a channel is submitted and Interaction answers `BUSY`; nothing is queued for "after". *Rationale:* buffering hides the sim's answer behind a presentation guess; Zomboid's immediacy is the model.
  
  *Immediate acknowledgement (CR-4).* The Adapter plays the hand's acknowledgement in the same frame (tool click, run footstep cadence, a prompt pressed look); the sim confirms at T+1 (≤ 17 ms). The one exception is the beam — PC-5.
  
  *Resync rule (unifies three kernel-routed cases).* The Adapter keeps `last_acked` per intent type. It must **resend its current quantised value, bypassing the change filter once**, whenever: (i) an intent result arrives `Rejected(STALE)` (kernel Edge Cases: a stale "stop" otherwise leaves the actor moving); (ii) the kernel leaves `PAUSED` (CR-16 rejects intents immediately while paused, so a release made during a pause was lost); (iii) `LOADING → RUNNING` (the block was restored; the keys may still be down). For commands held during a pause (`tool_use`), the Adapter re-evaluates the actual button state on resume and submits `cancel_channel` if it is up. **Window focus loss** submits `set_move_intent {NONE}` and, if channelling, `cancel_channel`, and marks every held action released; regaining focus runs the resync. *Rationale:* one rule, three triggers — fewer special cases for the gameplay-programmer, and the invariant "the sim's intent equals the player's hands within one tick of the kernel being `RUNNING`" becomes testable.
  
  **PC-3. Movement: ship-local, 8-way, two gaits, whole base pixels per tick.** Movement is in the **body frame** (pipeline C2): the interior never shows ship motion, so the actor's velocity is relative to the deck. Input is **8-way** (no analog speed: stick deflection selects direction only; gait is the `run` action). *Rationale for no analog speed:* the noise cost of running (PC-10) must be a deliberate input, not a thumb slip — Sirlin's test for a healthy choice is that the player knows they made it; and an analog speed would be a continuum of non-integer px/tick, which PR-4 rule 3 forbids at camera quantum 1.
  
  *Speeds — derivation.* The pipeline routes "whole base px per tick when the quantum is 1" (PR-4 rule 3) and asserts two build invariants on `v_max` (its knob table): `LAG_CUT > v_max·τ_follow` → `v_max < 48 / 0.18 = 266 px/s`, **and** `0.30·L_h > v_max·τ_follow + L_MAX` at the default field → `108 > 0.18·v_max + 72` → **`v_max < 200 px/s`**. The second binds, and the brief's 266 is therefore not the operative bound. At `TICK_RATE` = 60 the whole-px/tick ladder is 60 / 120 / 180 / 240 px/s; the fastest legal gait is **3 px/tick = 180 px/s** (lag 32.4 px; 32.4 + 72 = 104.4 < 108). The pipeline's placeholders 90 / 150 px/s are 1.5 / 2.5 px/tick — non-integer under its own routed rule — and are superseded here (routed correction, below).
  
  | Knob | Value | px/s at 60 Hz | tiles/s | Why |
  |---|---|---|---|---|
  | `v_walk` | **2 px/tick** | 120 | 2.5 | Deliberate but not tedious: a 13-tile default field crosses in ≈ 5 s; the boarding rhythm's pace is set by doors and reading, not by a slow walk. 1 px/tick (1.25 tiles/s) recorded as the alternative for the MVP playtest if the boarding rhythm reads as hurried |
  | `v_run` | **3 px/tick** | 180 | 3.75 | The maximum the inner-box invariant allows; 1.5× walk is a readable contrast (forward lean, 5.2) without the camera clamping |
  | `v_carry` | **1 px/tick** | 60 | 1.25 | A module at chest height halves the walk: extraction under rising Attention is the sortie's tension ("weigh a module against the noise of taking it") and the slowdown is *seen* (carry-walk cycle), never a hidden stat |
  | `v_max` | = `v_run` = 3 px/tick | 180 | — | Read by the pipeline's G check |
  
  All three are expressed in px/tick and are invalidated if `TICK_RATE` changes (kernel Open Question 12). Values live in `assets/data/` (Section D).
  
  *Acceleration, stopping, turning.* **Instant** start, instant stop, instant facing change: `ACCEL_TICKS` = 0, `DECEL_TICKS` = 0 at MVP. *Rationale:* any ramp passes through non-integer px/tick (1→2→3 over three ticks is the one integer-only ramp and is offered as the fallback knob `RUN_RAMP_TICKS` ∈ {0, 3}); stiff-weighted bodies (5.2) do not ease; and Pillar 2's escape — "a horror enters the cone, I leave" — must cost zero ticks of wind-up. Walk ↔ run switches at the next tick. Positions are always integer base px at commit, so a stop is always *on the pixel grid*; there is **no tile snapping** on stop (a snap is an uncaused motion the player did not make, and C-R's "never reverses unless the player did" extends to the body).
  
  *Diagonals.* Cardinal moves are exactly `v` px/tick per axis. For diagonals the Body integrates `v/√2` per axis with a **sub-pixel residue held in Body's block** (Bresenham-style; position is committed as integers each tick), so diagonal speed equals cardinal speed and the per-axis step pattern is a regular 7-of-10. The residue is zeroed in `post_restore` together with `previous := current` (pipeline C5, routed to every owner of a moving read view — Body is that owner). *Alternatives rejected:* √2-inflated diagonals (the classic diagonal-sprint exploit, and a 41 % speed bonus for free); integer diagonal pairs ((1,1) is 71 % of walk, (2,2) is 141 % — neither is honest).
  
  *Collision contract (Body's to implement, this GDD's to require).* The actor is a kinematic capsule at the feet (≈ 20 × 12 base px, foot-centred, placeholder for Body's GDD); walls, closed doors, props and other actors block; sliding along a wall is permitted; no pushing of actors by actors at MVP. The actor is carried with the deck: welds, detaches and body transfers are Body's and never produce an uncaused interior motion in the frame the player is in (pipeline C2 ii).
  
  **PC-4. Facing: five drawn, three mirrored, derived from aim when the beam is lit.** "Beam held" in the brief means **lit** (`toggle_beam` is a toggle command, CR-4), not a button held. Rules, in priority order:
  1. **Staggered / downed / dead**: facing frozen.
  2. **Channelling**: facing locked to the target's octant for the channel's duration (the work loop is two-handed and tool-forward, 5.2); aim may still move and the beam follows it from the locked hand point.
  3. **Running**: facing = movement direction regardless of the beam. *Rationale:* the run cycle is a forward lean of the whole figure; a lean sideways to its motion reads as the horror's asymmetry (3.2 negation rule). The beam is engine light rotating 360° from the hand point (5.6), so a runner's light may trail behind them — honest and tense.
  4. **Beam lit, walking or stationary**: facing = aim octant (with `FACING_HYSTERESIS_DEG` = 4° at the 22.5° boundaries). The body translates in any of the 8 directions while facing the aim; the single walk cycle plays for the facing (side-steps and back-steps use the same cycle — accepted; the art budget has no strafe sets, 5.7). Back-pedal speed is full `v_walk` (`BACKPEDAL_FACTOR` = 1.0; any other value breaks whole-px cadence, so if the gameplay-programmer wants a penalty it must be "walk only" or an integer).
  5. **Beam unlit, moving**: facing = movement direction.
  6. **Beam unlit, stationary**: facing holds its last value.
  
  Mirroring: SW, W, NW are the SE, E, NE sheets x-flipped; the hand point's x is negated; the tool changes hands (accepted, 5.6). *Alternative rejected:* facing always from aim (Zomboid-style) — in the dark the player's aim is meaningless to anyone else and the body turning toward nothing visible invites the "where is it looking" misread; the beam-lit rule makes *looking* and *lighting* the same act (5.2: "looking at something is lighting it").
  
  **PC-5. Aim and the beam.** *Sources.* Mouse: raw aim = direction from the actor's **floored hand point** to the cursor's world position obtained through the pipeline's mouse-to-world (C11), so zoom level never changes aim; inside `AIM_MOUSE_DEADZONE_PX` = 8 base px of the hand point the aim holds its last value. Gamepad: raw aim = right-stick direction beyond `STICK_DEADZONE`; when the stick is released the aim **holds** (the beam does not swing to the movement direction — a sweep is a decision the player makes, Pillar 3; ux-designer may offer "aim follows movement when idle" as an option, default off). *Two consumers of aim:* the **raw aim** is read locally by the Avatar Presenter (beam `Light2D` rotation, continuous — lights may rotate off-grid, PR-4 rule 5) and by the camera look-ahead (pipeline C4, regardless of lit state); the **committed aim** (5° quantum, ≤ 1 tick late) is what Emitter State orients the beam emitter by for the exposure query, what Interaction uses for target preference, and what co-op replicates. A ≤ 5° / ≤ 1-tick divergence between the drawn and simulated cone is accepted; the identity channel (Pillar 1) is shape and colour, which come from the replicated loadout, never from aim.
  
  *Beam shapes are a loadout, not an input.* The four shapes (wide, narrow, split, fan — art bible 3.2, 8.3) are a per-player `Suit & Equipment` loadout fact; the Adapter has no "change shape" action. One `beam_toggle` action submits **`toggle_beam`** (owner: Emitter State; actor = the player's beam emitter ID, bound to the seat). The beam is an emitter like any other for Attention (Emitter State's exposure query), which is what makes "go dark" a real strategy.
  
  *Acknowledgement vs the anchor (resolves a CR-4 / Pillar 1 collision).* The beam is a human-channel anchor that may never lie. If the local `Light2D` lit on the press and the sim then rejected (`beam charge empty`), the beam would have flickered once on the one object that may not. Rule: **the toggle's sound and the hand's switch animation play immediately; the light itself changes only on the committed state** (≤ 17 ms later, imperceptible against a 3-screen-px cone edge). The Avatar Presenter never predicts beam state.
  
  *Hand point.* The beam's origin is `floor(pos) + hand_offset[facing][animation]` — per facing **and per animation** (carry-walk holds the module at chest height and the lamp hand rises; work and stagger move it too), tabulated from the sheets in Section D, using the same floored position as the sprite (PR-4 rule 2) so light origin and sprite never disagree. The Controller Sim publishes the current hand point in its read view so that when the Perception Filter substitutes a horror rig for a crewmate (class c, art bible 5.0) the beam still originates at the *true* hand point.
  
  **PC-6. Interaction reach, targeting, prompts, hold-to-confirm.** *Reach* is a sector from the actor's foot origin: radius `REACH_PX` = 72 base px (1.5 tiles — covers the adjacent ring including diagonals at 68 px) and half-angle `REACH_HALF_ANGLE_DEG` = 70° about the **facing** (which is the aim when the beam is lit). Objects behind the player are never candidates. *Targeting:* a candidate must be in reach, in the arc, and **lit** (Emitter State's exposure query above the technical-artist's threshold); mouse picks the candidate under the cursor if any, else the nearest in the arc; gamepad uses **proximity focus** — one candidate, chosen by angular distance to the committed aim then by distance — and one contextual action (HR-14). Prompts (`E · Cut`) are drawn only for the candidate, only when lit (art bible 7.0), by the HUD through `world_to_hud`; an off-screen candidate has no prompt (C9). **Decision (art bible 7.0 leaves it to the game-designer): an action is possible only on a lit object.** Interaction's `validate` calls the same exposure query the prompt uses, so the prompt never lies by omission. *Rationale:* "what you light, you can read" must also be "what you light, you can touch", or working in the dark becomes a free Attention dodge and "go dark" degenerates into the dominant strategy (Sirlin); light has to cost Attention to make darkness a trade. Exceptions: `drop` of the module you carry, `toggle_beam`, and the inspect card of an instrument already lit. *Hold-to-confirm* (HR-14, destructive verbs: section cut, module removal, drop into void — the list is Interaction's): a **local** hold of `HOLD_CONFIRM_TICKS` = 36 (0.6 s) measured in render time by the Adapter, then one command; the sim never sees a partial hold; the HUD draws the linear bar (7.3). It is distinct from a channel (PC-7): short, local, and completes into a single command rather than accruing in the sim.
  
  **PC-7. Channels (cut / weld / patch).** Press `tool_use` on a valid candidate → the Adapter submits `begin_<verb> {target}` (`coalesce = NONE`; owner Interaction, with Assembly behind it for weld/cut). The owner's `validate` requires: candidate lit and in reach, `controller.state.dir == NONE`, not carrying, not staggered/downed. **Progress is sim state in the owner's block**, accrued per tick by the owner's hook; the Controller Sim only records `channel_ref` and locks facing (PC-4 rule 2). *Interrupts:* (i) **release** → the Adapter submits `cancel_channel`; (ii) **movement** — the owner's hook reads `controller.state.dir` and aborts when it becomes non-`NONE` (sim-side, so identical in `MIRROR`; the 8-way dead-zone already filters stick drift); (iii) **stagger / downed** — the Controller Sim clears `channel_ref` and the owner aborts on seeing it; (iv) **target invalidated** (power drops mid-cut, the section detaches) — the owner aborts and reports it through state change, never through the command result (CR-5). The player keeps control of the body at all times: a channel never locks movement, movement cancels the channel. *Rationale:* Dread Before Chaos needs "I can leave now" to be true in every state; a locked weld with a horror entering the cone is a cheap death. **Pause:** the tick stops, progress freezes, the hold survives if the button is still down on resume (PC-2 resync). Whether progress persists on the target after an abort is the owner's rule; this GDD recommends a short persistence (Assembly/Interaction to set; placeholder reference durations only for feel validation, not owned here: cut 4 s = 240 ticks, weld 6 s = 360, patch 3 s = 180).
  
  **PC-8. Carrying.** `pickup` (Interaction) on a module → `controller.state.carry_ref` set; `drop` clears it. While carrying: gait forced to `v_carry` (**no run while carrying** — there is no carry-run cycle in the sheet budget and a sprinting module is the wrong image); `tool_use` and `interact` channels are rejected `BUSY` (hands full) — `drop` first; the beam **stays available** (recommended; the hand point shifts to the carry table). The alternative — beam off while carrying, so extraction is blind — is a strong Pillar 3 lever and is recorded as an open question for the user rather than decided here, because it changes the sortie's difficulty curve more than any other single rule in this section. Stagger does **not** drop the module (stagger is brief); downed does.
  
  **PC-9. Honest body states: stagger, downed, dead — driven by the sim, never by a stat.** The Controller Sim consumes one value from Suit & Equipment's read view (`after: suit.vitals`, divisor 6 — a read up to 5 ticks old is tolerated): `vitals.state ∈ {OK, STRAINED, CRITICAL, FAILED}`, derived by Suit from O₂, temperature and suit integrity (thresholds are Suit's / systems-designer's). Rules: **OK / STRAINED** — no locomotion effect (rime and visor fog are Suit-driven overlays the Presenter draws; they are information, not penalties). **Entering CRITICAL** → one **stagger** (`STAGGER_TICKS` = 30 = 0.5 s; input ignored; channel cleared; no displacement — a stagger is animation plus input lock, not a physics impulse), then **walk only** until the state clears (the `run` action does nothing; the HUD breath/warmth reading and the visor fog are the readable reason). **FAILED** → **downed** (`down` 6-frame animation, input ignored, carry dropped); in MVP solo, downed → **dead** after `DOWN_TO_DEATH_TICKS` = 1800 (30 s) unless `vitals.state` leaves FAILED; dead hands the actor to Save/Load's MVP death stub (`request_restore` — the controller never calls the control plane). In VS-B a crewmate's revive verb (Interaction) returns downed → idle. External stagger sources (a venting loop's recoil, art bible 5.2) arrive as a `SYSTEM`-origin `stagger` command from the owning system at T+1 (CR-9 path b). *Why no continuous speed penalty:* the concept's secondary design test (−10 % move speed vs a false gauge → the gauge) is explicit that invisible stat debuffs are the wrong tool; a state the body *shows* — fog, rime, stagger, walk-only — is a channel of truth a crewmate can read in their beam (5.3).
  
  **PC-10. The two rhythms in the controller.** Nothing in this system changes between boarding, the Tell and breach: no adrenaline, no speed buff, no reduced noise, no "panic" input changes. **The breach is frantic because of what moves, not because the body changes** (art bible 2.8). Running is allowed everywhere and is **noisy**: the Controller Sim's hook pushes a noise stimulus to Attention's intake each tick the actor moves — `NOISE_WALK` = 1, `NOISE_RUN` = 4, `NOISE_CARRY` = 1 (placeholder stimulus units; Attention's intake is undesigned, kernel C.3 #4). Running is 1.5× faster and 4× louder per tick, so ≈ 2.7× louder per tile: running never dominates walking for stealth and is a real trade in a retreat. Tool noise belongs to the tool (Suit / Interaction). The beam's exposure is Emitter State's.
  
  **PC-11. The human channel; the controller never renders.** The crewmate sprite and its beam (shape and colour) are inviolable anchors (Pillar 1; art bible 5.0). This system draws nothing: the Avatar Presenter is a `PRESENTATION` node reading committed state, and the Perception Filter may substitute the whole body for a horror rig (5.0) but never edits pixels, never moves the hand point, never touches the beam. Remote crewmates are drawn by the same Presenter from `MIRROR` state (PC-17), so a friend's body is the same object on every client.
  
  **PC-12. What the player cannot do.** No jump, no dodge-roll, no vault, no lean/peek (camera C9), no melee or attack input (anti-pillar: not a combat game — the friendly-harm act is an Interaction verb on a crewmate target under Sanity's gate, reached through `tool_use`, never a dedicated button), no auto-aim or aim assist of any kind, no acrobatics, no acceleration tricks. **No crouch (decided).** *Rationale:* restraint in this game is *light and noise* (Pillar 3), not posture; a crouch with lower noise would be a free dodge that every player holds permanently (Sirlin: a dominant strategy that is not a decision); the sheet budget has no crouch set; and a curled crewmate drifts toward the horror grammar 5.2 forbids. Walking and turning the beam off *are* the quiet stance. No sprint-by-stick-deflection (PC-3).
  
  **PC-13. Input device switching.** The **last device that produced an event is active**; prompts and the hand rail switch glyph sets on the HUD. Godot merges devices per action, so a `tool_use` held on a pad survives touching the mouse. Switching aim source never jumps the beam: a mouse move takes aim from the cursor; a stick deflection takes it from the stick; a stick release holds. The cursor is hidden while the pad is active (ux-designer confirms). Every flow in the core loop is **gamepad-complete** (HR-14): move, run, aim, beam, interact, tool use, tool select, drop, inspect (mirror card), zoom, pause, chart table (snap-to-node is Chart Table's); text chat is the only keyboard-only item (VS-B).
  
  **PC-14. Position ownership — recommendation (provisional, kernel Open Question 3 / pipeline Open Question 3).** **Adopt the proposal: Ship Body owns ship-local kinematic position; the Controller Sim owns intent, gait, facing, locomotion state, carry and channel references.** Contract: `controller.step` writes `dir`, `gait_effective`, `facing`, `loco_state`; `body.integrate` (`after: controller.step`) reads them, integrates `v(gait_effective) × unit(dir)` with collision and the diagonal residue, and commits integer `pos_prev / pos_curr` in the body frame; it also exposes `blocked` (moved less than requested) for the Presenter's footstep audio, nothing more. *Why Body:* the composite welded ship and the moving-platform problem are Body's (systems index high-risk row); an actor must transfer between bodies (pod hop, detach) which Body already tracks; physics-derived positions are *inputs* under G3 and keeping them in Body's block lets the replay test exclude exactly one block. *Why not Controller:* it would duplicate the physics projection and put a `PROJECTOR` concern inside an input system.
