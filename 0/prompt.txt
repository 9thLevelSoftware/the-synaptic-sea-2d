  ## Flags for the orchestrator (trade-offs the art direction must hear)
  
  1. **Ambient floors of 0–3 % cannot carry the "dark has a floor" rule in 8-bit SDR output.** Ambient as a canvas multiply (`CanvasModulate` `[BIN]`) gives Graphite mid `#2A303A` × 0.02 ≈ 0.8/255 and Void Steel `#0B1018` × 0.02 ≈ 0.2/255 — both quantise to black. 4.1's "hull still darker than true black" exists only where ambient is high enough to separate them (≈ 6–8 % for a 2-step gap). Nuance: with `hdr_2d` on, the multiply happens in linear space and is re-encoded to sRGB on output `[UNV-4.3]`, which lifts darks a step or two — the conclusion is directional, and spike step 7's histogram decides. The arithmetic assumes SDR output; `display/window/hdr/request_hdr_output` exists (default `false` `[BIN]`) and should stay off through the spike. Options: raise the floors; keep the floors but add a material-level `max(albedo × ambient, floor_tint)` on hull materials so unlit hull never drops below Void Steel; enable `rendering/viewport/hdr_2d` (default `false` `[BIN]`) plus `use_debanding` (default `false` `[BIN]`). The AD chooses which; I recommend option 2 plus HDR 2D.
  2. **"Many tungsten fixtures" (2.3) with true occlusion is the state most likely to break the frame.** Shadow cost scales with shadow-casting lights × occluder polygons (mechanism `[UNV-4.3]`, number NOT SOURCEABLE). The bible already describes stable-state shadows as "soft, nearly directionless" — that is the licence to make fixtures **non-shadow** lights and reserve shadow-casting for beams (≤ 4), the alarm beacon and at most one deployable in view. This matches the direction rather than cutting it. If the spike shows even that over budget, Section 1 says cut emitters before occlusion — see item 1's budget shape.
  3. **Glow is a per-viewport post pass; no single CanvasItem can be excluded from it.** Consequences: (a) the violet fringe must stay below `glow_hdr_threshold` (default `1.0` `[BIN]`) or it blooms and reads as emission — a principle 3 violation; (b) "HUD excluded from glow" requires either HUD luminance below threshold or the world rendered in a `SubViewport` `[BIN]` with the HUD in the root viewport. I recommend the SubViewport (it also gives integer-scale control, item 3). Also: glow was reworked in 4.6 — it now runs before tonemapping with screen blending `[REF]` — so no 4.3-era glow tuning transfers; the threshold test in spike step 8 is the only number to trust.
  4. **Base-resolution choice is a 9× lighting-cost lever, not only an art choice.** If the world renders at base resolution (640×360 = 1/9 of 1080p pixels), lights, shadows and the beam edge are computed there and the beam's hard edge becomes a 3-px stair-step at 1080p. If the world renders at window resolution with integer-scaled sprites, the beam edge is smooth and lighting costs 9× the pixels. Whether Light2D is evaluated at the viewport's render size (so that a 640×360 SubViewport lights at 640×360) is `[UNV-4.3]`; it is the first thing the spike must confirm, because the whole budget hangs on it. Integer-scale table in item 3: only 640×360 scales to integers at 1080p, 1440p and 4K.
  5. **"Normal maps are generated, not drawn" (5.7) is half true.** A flat albedo has no height; a Sobel on albedo yields garbage normals. Each sheet needs a painted height/mask pass (2–4 grey levels, fast but not zero) from which normals are generated by tool. Budget it as roughly 20–30 % of the albedo drawing time, not 0 %.
  6. **The 2-px fringe "outside the contour" needs 2 px (at sprite resolution) of transparent padding in every frame cell** or the outline clips at the cell edge. This is an atlas-packing rule (item 7) and a tool-pipeline rule (padding must survive trim-on-import).
  7. **Two REF-vs-BIN conflicts to verify on line one of the spike.** (a) `rendering/rendering_device/driver.windows` default is `"vulkan"` `[BIN]` while REF says D3D12 is the Windows default since 4.6 — print `RenderingServer.get_current_rendering_driver_name()` `[BIN]` at startup. (b) `display/window/stretch/mode` default is `"disabled"` and `aspect` `"keep"` `[BIN]` while REF says new 4.7 projects default to `canvas_items` / `expand`; `D:\the-synaptic-sea-2d\project.godot` has no `[display]` block, so write the stretch settings explicitly rather than inheriting a default nobody can name.

  ## 2. Texture memory and atlas limits

All three sheets must share one identical layout (same cell positions), because the normal and specular are sampled with the albedo's UVs. `Sprite2D.region_enabled` / `hframes` / `vframes` `[BIN]`, `AtlasTexture.atlas` (typed `Texture2D`, so a CanvasTexture is assignable) `[BIN]`, `TileSetAtlasSource.texture` (typed `Texture2D`) `[BIN]`.   ## 4. Per-client hallucination filter and the 5.5 fringe shader
  
  **Constraint / feasibility.**
  - Unlit pass: `CanvasItemMaterial.LIGHT_MODE_UNSHADED` `[BIN]` or `render_mode unshaded` in a `canvas_item` shader (`Shader.MODE_CANVAS_ITEM` `[BIN]`; the render-mode keyword is `[UNV-4.3]`). An unshaded CanvasItem receives no Light2D contribution and, not being a Light2D, emits none — "casts no light" holds by construction.
  - Per-viewer: the fringe is a material/uniform on the *local* client's view of the crewmate, driven by `CanvasItem.set_instance_shader_parameter` `[BIN]` from a presentation-only script that reads replicated sanity state and never writes it. Rule for Section 8 and the control manifest: **presentation scripts may read simulation state and may only write to CanvasItem / Material / Light2D properties; they never call into gameplay or networking.** A player never sees their own fringe because the local script skips the local avatar.
  - Outline shader: sample the albedo alpha at ±1, ±2 texels and paint `#B07BE6` where own alpha is 0 and a neighbour is opaque — hence the 2-px padding rule (flag 6). Breathing 4–6 s via `TIME` on alpha only, never on width or position (2.9: no tempo change). Width is "2 px at sprite resolution": in the base-res SubViewport that is automatic; in pass B the shader needs the integer scale as a uniform.
  - Beam-edge fringe: the beam is a Light2D texture, not a CanvasItem, so it has no edge to outline. Author one edge-mask sprite per beam shape (4 small unshaded textures) drawn at the hand point with the beam's rotation. Cost: 4 textures, one extra draw per fringed crewmate.
  - Glow interaction: keep fringe luminance below `glow_hdr_threshold` (flag 3). Order: fringe sprite drawn as a child **behind** the body (`show_behind_parent` `[BIN]`) so it never covers the sprite's own pixels.
  - Own-sanity filter (stages 1–3): a `canvas_item` shader on the `SubViewportContainer` (it already holds the world as a texture), or — if the world is not in a SubViewport — a full-screen pass on a `CanvasLayer` above the world and below the HUD reading the screen via `BackBufferCopy` `[BIN]` (or the screen-texture hint, `[UNV-4.3]`). Stage-2 "false reach" is an unshaded additive cone sprite, not a Light2D — it tints but reveals nothing because unlit geometry is already black. Stage-2 "shadow with no occluder" is an unshaded dark polygon. None of these touch `LightOccluder2D`, `Light2D` or simulation nodes.
  - Shader count: fringe, iridescence-per-segment, full-screen filter, pipe-flow scroll, ambient-floor material. Enable the Shader Baker (4.5 `[REF]`; "not using it" is listed as a common mistake in `current-best-practices.md`) so these do not hitch on first use.
  - Multiplayer scope: up to four clients each run their own filter; there is no server-side rendering so "per-client" is free. NOT SOURCEABLE — anything about the networking model; this is presentation only.
  
  **What it limits.** One extra unshaded draw per fringed crewmate and one full-screen pass for the filter — negligible against the 1000-draw budget. The real constraints are flag 3 (glow) and flag 6 (padding).
  
  **Recommendation.** Build the fringe first in the spike (it is the cheapest proof that unshaded-per-viewer works), then the filter as a SubViewportContainer shader. Write the "presentation never writes simulation" rule into the control manifest.
  
  ## 5. Horror segment rigs — quantised rotation, stepped playback
  
  **Constraint.**
  - `Skeleton2D`, `Bone2D`, `SkeletonModificationStack2D` and the `SkeletonModification2D*` set (CCDIK, FABRIK, LookAt, Jiggle, TwoBoneIK, PhysicalBones, StackHolder) all exist in 4.7.2 `[BIN]`. There is **no** `SkeletonModifier2D` `[BIN]`; the 4.6 IK rework in REF (`SkeletonModifier3D`) is 3D-only. `Skeleton2D` exposes `execute_modifications`, `set_bone_local_pose_override` `[BIN]`.
  - Skeleton2D is built for `Polygon2D` mesh skinning (`Polygon2D.skeleton`, bone weights `[BIN]`), which deforms textures — the opposite of a grid-snapped look. Plain `Sprite2D` children under a `Node2D` hierarchy need no skeleton at all.
  - Rotation of a nearest-filtered sprite in the base-res SubViewport lands on the base pixel grid (stair-stepped edges, which *is* the grid-snapped look); at window resolution it leaves the grid. `[UNV-4.3]` for the mechanism; spike step 2 confirms it.
  
  **What it limits.** Stepped playback is a script decision, not an engine feature: pose only every N physics ticks (12 fps = every 5th tick at 60 Hz) and quantise each segment angle to 360/24 = 15° (or 360/16). IK modifications run continuously, so if Skeleton2D IK is used, call `execute_modifications` manually on the stepped tick and write the quantised result back — more plumbing than it saves.
  
  **Recommendation.** Manual rig: a `Node2D` per limb chain with `Sprite2D` segments (tapering, round joint caps for overlap), a GDScript procedural animator (creep / unfold / snap signatures, per-instance seed) stepped at 12 fps with 15° quantisation, segments ordered by `z_index` for joint overlap, the iridescence band as a `ShaderMaterial` on each segment with a per-instance phase uniform (`set_instance_shader_parameter` `[BIN]`). Reserve Skeleton2D + FABRIK only for the filament-rider type if a limb must reach a world point; even then, quantise after solving. If pass B (window-res lighting) wins, pre-rotate segment sprites at import into 24 angle variants (tool step; at T=32 that is ≈ 60 cells × 24 × 4096 × 12 ≈ 70 MB, still fine) or keep horrors in a base-res SubViewport. Silhouette test per 5.4 on rest / reach / move poses captured from the rig, not from sheets.
  
  ## 6. Draw-call shape — TileMapLayer, Y-sort, HUD layer
  
  **Constraint.**
  - `TileMapLayer.rendering_quadrant_size` default `16` `[BIN]`: tiles are grouped into 16×16-cell quadrants, each quadrant drawn as a batch per material/texture `[UNV-4.3]`. A 20×11-tile view touches ≈ 4 quadrants → ≈ 4 draws for a floor layer.
  - Y-sort: `CanvasItem.y_sort_enabled` (default `false`) `[BIN]`, `TileMapLayer.y_sort_origin`, `TileData.y_sort_origin` `[BIN]`. Enabling Y-sort on a TileMapLayer makes it sort per cell with its siblings and is known to break quadrant batching `[UNV-4.3]` — potentially one draw per cell (≈ 220 for a full view). NOT SOURCEABLE as a 4.7.2 number; spike measures `RENDER_INFO_DRAW_CALLS_IN_FRAME` with Y-sort on and off.
  - 2D batching: `rendering/2d/batching/item_buffer_size = 16384`, `uniform_set_cache_size = 4096` `[BIN]`. Batching merges consecutive items that share texture, material, blend mode and light state `[UNV-4.3]`; a CanvasTexture page is one such texture, so three-sheet pages batch exactly as single textures do.
  - `CanvasLayer` (`layer`, `follow_viewport_enabled`) `[BIN]`; `RenderingServer.CANVAS_LAYER_MIN/MAX` `[BIN]`. Light2D and CanvasModulate act on their own canvas, so a HUD CanvasLayer is unlit and un-ambiented `[UNV-4.3]`. Glow is not per-canvas (flag 3) — hence the SubViewport in item 3.
  - `z_index` range ±4096 `[BIN]`.
  
  **What it limits.** 3/4 oblique needs actors to sort against wall faces and props, which forces Y-sort on the layer containing those — the single largest draw-call multiplier in the scene. Floors never sort against actors and must stay off Y-sort.
  
  **Recommendation (target shape against the 1000 budget).**
  
  | Layer | Node | Y-sort | Expected draws |
  | --- | --- | --- | --- |
  | Floor | `TileMapLayer` (CanvasTexture page: dialect floor) | off | ≈ 4 |
  | Floor trails/stains | `TileMapLayer` or sprites, shared page | off | ≈ 4–20 |
  | Wall faces, props, actors, horror rigs | one Y-sorted `Node2D` parent containing a `TileMapLayer` (walls/props) plus actor scenes | on | measure: 50–300 |
  | Wall top caps | `TileMapLayer`, `z_index` above actors | off | ≈ 4 |
  | Pipes + emissive overlay | `TileMapLayer` (shared pipe page) + unshaded additive sprites | off | ≈ 10–40 |
  | Lights | `PointLight2D` nodes | — | 0 extra draws, shadow passes extra (measure) |
  | Fringe / hallucination | unshaded sprites + 1 full-screen pass | — | ≤ 10 |
  | Particles (dust, mist, venting) | `GPUParticles2D` (`fixed_fps` default 30 `[BIN]`) | — | 1 per emitter, ≤ 12 emitters |
  | HUD | `CanvasLayer` in the root viewport (world in SubViewport) | off | ≈ 20–60 |
  
  Plenty of headroom if Y-sort stays confined to one layer. If the measured Y-sorted layer exceeds ~300, split wall faces into a non-sorted layer with per-row `z_index` bands (tile rows become z bands; actors pick the band by their feet). Particle LOD: `GPUParticles2D.amount_ratio` `[BIN]` scaled by distance from the beam, `visibility_rect` set tightly; proposed caps: dust-in-beam ≤ 300 total, mist ≤ 64 per trail, venting ≤ 128 per vent, ≤ 12 live emitters.
