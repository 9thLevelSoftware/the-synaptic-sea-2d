  ## B. Engine-specific risks (does any of this argue against Godot?)
  
  No. Godot 4.7 is a reasonable fit for a 2D co-op simulation, and its high-level multiplayer API fits a small-session listen-server game. Caveats to carry forward:
  - **D3D12 is the default rendering driver on Windows since 4.6** (it used to be Vulkan). You are Windows-first, so test 2D lighting and shaders on D3D12 early and know how to switch to Vulkan as a fallback if driver problems appear.

  ## C. Risks solo developers commonly underestimate
  
  1. **NAT traversal and lobbies.** "Co-op works on LAN" and "co-op works for Steam friends" are separate milestones.
  2. **Save-format versioning.** A game with no win state and many sessions will break saves every time a module's data changes. Version saves and write migrations from the first save file.
  3. **Debugging desync.** Divergent hallucinations (Risk 4) and authoritative state that has actually drifted out of sync look the same to a tester. You need a debug overlay that shows the true values, from the start.
  4. **Readable procedural content.** Making generated content readable takes far longer than the generator itself.
  5. **Art throughput.** Detailed HD pixel art for modular derelict sections is probably the largest time sink of the project, larger than the code.
  6. **Testing a multiplayer game alone.** Plan for running several local instances (Godot's debug run supports several instances) and scripted bot clients.

  ## Per-risk assessment
  
  **1. Multiplayer netcode / authority: MEDIUM-HIGH, manageable with B2.** The host simulates the whole life-support graph at a fixed tick. Clients send requests through any_peer RPCs, the server validates them and broadcasts the result. This matches the server-authoritative pattern in networking.md. Replicate the graph's summary state (per-compartment O2/heat/power plus edge states) at low frequency, not every node every frame. Use reliable RPCs for structural events (weld, breach, module destroyed) and unreliable sync for positions. Host plus a few peers on ENet is well within the API's design envelope. Main open items: NAT traversal and lobbies, plus join-in-progress (deferred).
  
  **2. Modular welded ship / composite body: MEDIUM.** Known pattern: one physics root body for the ship, with each section's collision shapes and life-support nodes reparented under it when welded and split off into a new body when detached. Keep the life-support graph as a pure data model (resources or plain objects) that the scene nodes register with, not something you get by walking the scene tree. That lets you test it headlessly and serialize it, and it turns hull integrity into graph properties. Spike first: weld and detach two sections, mid-flight, with the graph recomputing.
  
  **3. Procedural derelicts: MEDIUM.** Avoid pure noise. Use hand-authored room "kits" (TileMapLayer chunks with tagged sockets) joined by a graph or grammar generator, then place salvage according to rules. Readability comes from authoring, not the algorithm. Generate from a seed so the host can send seed plus parameters and clients regenerate locally, which cuts bandwidth. Then send only changes from the seed (looted, damaged, opened). The 2D oblique perspective adds wall-occlusion and draw-order work; prototype it with one kit before scaling.
  
  **4. Per-player divergent misinformation: LOW-MEDIUM technically, if one rule is followed.** **The hallucination must never touch the simulation.** Every client receives the true authoritative value. A per-client presentation filter, driven by that player's own sanity, corrupts only what is drawn: gauges, sprites, audio. Hallucination state is never sent as game state and never feeds back into requests the server accepts as fact. Sanity itself is server-authoritative per player, and the corruption seed can be per-client and local. Combine with the true-value debug overlay (C3). Done this way, the feature is cheap and safe. Done wrong, it is an endless source of desync bugs.
  
  **5. HD pixel art plus 2D lighting and particles: MEDIUM, must be measured.** I am deliberately not quoting light or shadow cost numbers for 4.7. The pinned reference doesn't document them, so budgets must come from a profiling spike on the target minimum-spec PC under D3D12: N lit sprites, M shadow-casting lights, particle counts, at the target resolution. Expect shadow-casting 2D lights to be the main cost. Standard mitigations: few shadow casters, baked or atmospheric light where possible, and limiting active lights to nearby ones. Setting the art spec (sprite resolution, atlas size, texture memory) is part of this spike. Hand off to technical-artist and performance-analyst once the spike exists.
  
  **6. Persistence of the composite ship and world: HIGH as written, MEDIUM after B1.** Feasible once one save owner is defined. Serialize the data models (section list with transforms and weld graph, life-support graph state, world seed plus changes, web Attention state, per-player progression), not scene trees. Version the format from v1 (C2). Live persistence across a host change is the blocker. See B1, including the design question about who owns the save, escalated to game-designer and creative-director.
  
  **7. Solo first-time developer: HIGH as written, manageable after B2.** The deciding factor is the order of work, not talent. Learn the engine on the single-player slice. Write the data-model systems (life-support graph, save) to be testable without the editor running. Add networking only after the slice is fun. Expect a long open-ended timeline; with no fixed deadline this is acceptable, but the risk is losing motivation, not missing a date.
