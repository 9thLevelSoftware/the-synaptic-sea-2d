  ## The gate's five questions
  
  **1. Clean boundaries, minimal overlap?** Mostly. The overlaps are in the four clusters you named, all detailed below: propagation/atmosphere, the gauge needle, the section/socket schema, and writes to Light2D.
  
  **2. God Object risks**
  - **Command & Simulation Layer (#1).** This is a real system, not just a rule, but only if it stays a thin kernel. It owns:
    - the fixed tick
    - command dispatch and the authority check
    - a registry of state blocks
    - change notification to presentation
    - peer/authority identity on every command from day one (single-player is peer 1)
  
    It must not own domain state or define other systems' command types. Each domain system owns its own state block and command handlers, and registers them with the kernel. If its GDD says it owns "the simulation", it becomes the God Object. Write it ADR-first ("Authority model", already on the concept's ADR list) with a short technical spec. The 8-section player-facing GDD template fits it poorly (no Player Fantasy, no tuning knobs).
  - **2D Lighting & Occlusion (#5).** Mixes simulation (emitters as a spent resource, "is X lit") with rendering (Light2D, occluders, glow). Split it; see cluster 4.
  - **Suit & Equipment (#9).** A grab bag: vitals, inventory, four beam shapes, four tools and deployables. The tools' effects belong to other systems: the cutter/welder to Interaction/Assembly, the scanner to Sanity falsification, the suppressant to Attention/Horror. Suit should own vitals, loadout and tool slots, and say that each tool's effect is defined by the system it acts on.
  - **Life-Support Graph (#2).** 11 dependents is acceptable for the core sim, provided it stays at five loops and Failure & Trail does not also claim propagation (cluster 1).

  - **Derelict Authoring (order 10)** comes before **Modular Ship Assembly (order 12)**, with no edge between them, yet kits must carry the sockets and seams that Assembly consumes. See cluster 3.
  - **Save/Load (order 11)** comes before Assembly (12), Attention (14) and Sanity (17), yet its scope lists their state. See the inversion note under Q5.

  ## The four named clusters
  
  **1. Life-Support Graph vs Failure & Trail vs In-World Instruments.** Two owners of propagation, and one data item without a home.
  - Row 2 claims "failure propagation". Row 8 claims "propagation along seams" and "the P1 consequences (cold, thin air)".
  - Ruling:
    - **Graph** owns failure state, propagation (seams are graph edges whose properties Assembly sets at weld time), and per-compartment atmosphere (temperature, pressure, O2). These are the P1 consequences, and they are simulation state.
    - **Failure & Trail** becomes a pure reader. It maps graph state and footprint sources to trail visuals, writes only CanvasItem/Material/particles, and drops its Lighting dependency except for emissive materials.
  - Failure & Trail is the honest channel, yet nothing marks it immune to the filter. Class (b) says "the lie extends from the gauge to the sprite", so the Filter needs a **truth-channel / corruptible tag contract** on presentation nodes. Trails, the light radius you actually walk into, crewmate beams, character sprites and the HUD frame are immune. Gauges and machine sprites are corruptible.
  - Instruments (#19) should own the gauge nodes (see cluster 2 for how they get the displayed value).
  
  **2. Sanity & Hallucination Rules vs Perception Filter.**
  - The split is right: Sanity is authoritative and writes per-player perception state; the Filter presents it.
  - Fix the two-writers problem: the Filter is a **perceived-value query/decorator service** plus screen-wide effects (violet fringe, palette leak, stage drift). It does not own instrument or HUD nodes. Instruments and HUD ask it "displayed value of X for local peer P" and draw the result themselves.
  - Sanity's GDD must state:
    - No simulation system ever reads perception state. The friendly-harm gate reads the sanity *level*, not perception.
    - Perception state is keyed by peer ID from MVP.
    - Falsification checks (second scanner, field checks) reach Sanity as commands from Interaction/Suit. Row 16 is missing those dependencies.
  - Adaptive Audio (#21) depends on Sanity, which means audio either never lies (state this) or audio corruption joins the Filter's write set under the same rule. The voice channel must never be faked in either case.
  
  **3. Modular Ship Assembly vs Derelict Authoring vs Procedural Derelict Generation.** Nobody owns the shared schema: the runtime **section data model** (tile layer, collision shapes, sockets, seams, graph-node references, salvage/module slots).
  - Authoring is content production, Procgen is a producer, Assembly is the runtime consumer, and Save serializes it. Without an owner, three GDDs will each define "a socket".
  - Either add a Foundation/Core row, **"Ship Section & Layout Data Model"**, or explicitly give schema ownership to Assembly and make Authoring and Procgen depend on Assembly. The new row is cleaner.
  - Assembly must own a pure-data ship layout (sections, transforms, welds) that is projected onto the scene tree. Otherwise Save ends up serializing a scene, against the TD rule.
  - **Module install/uninstall** (cut a scrubber free, install it at home) is a graph mutation separate from section welding. No system currently owns it. Assign it to Assembly or the Graph.
  
  **4. Attention vs Horror Entities vs Lighting.** This is the blocking item.
  - As drafted, Attention reads Lighting's "emitter registry" and the Filter writes Light2D. If that registry comes from Light2D nodes, a hallucination can change a simulation input. Also, the listen-server host cannot compute it for remote players' lights, and headless graph/attention tests cannot run.
  - The split is clean:
    - **Emitter state** (fixtures, beam on/off, power draw, cone shape) is simulation data, written through commands and owned by Graph, Suit and fixtures. It comes with a **simulation-side light-exposure query** (geometric cone test plus occluder raycasts on physics shapes).
    - **Light rendering** reads emitter state.
  - After the split, Attention, Horror Entities, and Interaction's "act only on lit" rule (if it is a rule and not just a UI hint) use the query, never Light2D.
  - Light2D writers need a **modifier contract**: Lighting owns the final value; Attention flicker, horror disturbance and Filter effects submit layered modifiers. The Filter adds decoy visuals ("the cone reaches further") and must never change the real reveal radius, which is a pillar anchor.
  - **Noise:** Attention's GDD should own a stimulus-input API (light, noise and power stimuli pushed in by Graph, Suit, Interaction, Assembly and Horrors). It must not read Audio.
  - **Horror Entities (#15)** write footprints (frost, hull stress, light disturbance) into the Graph/footprint channel, so a dependency on the Graph is missing.
  - **Adaptive Audio** should depend on the Graph and Horror Entities directly, not on Failure & Trail. Pillar 2 needs audio tells to lead visuals, which is impossible if audio sits downstream of the trail renderer. The Horror Entities dependency is missing.

  ## The three soft cycles: are the one-way resolutions real?
  
  - **Attention to Lighting: not real as written, real after the emitter split.** With emitter state in the simulation, Attention reads simulation state, Lighting renders, the filament renderer reads both, and nothing in the simulation reads presentation.
  - **Sanity to Filter: real**, with two conditions: falsification arrives as commands from Interaction/Suit (not Filter callbacks), and no simulation system reads perception state.
  - **Graph to Assembly: real**, provided join-validation is a pure query on the Graph, Assembly owns the pure-data layout, and the weld command is atomic within one tick across graph join and layout change. The physics/tilemap projection follows from the data.
