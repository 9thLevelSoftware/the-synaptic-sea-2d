  ## 1. Tick
  
  **What the reference says**
  - `_physics_process(delta)` is the idiom shown for movement in physics.md, input.md and navigation.md. Nothing there describes tick rate, catch-up behaviour or ordering.
  - 2D physics is unchanged since 4.3 ("still Godot Physics 2D"). Jolt is a 3D-only change, so it is irrelevant to this 2D project.
  - The only interpolation entry is "3D physics interpolation rearchitected (4.5): moved from RenderingServer to SceneTree." It is 3D-only. NOT SOURCEABLE: 2D physics interpolation status or API on 4.7, and any interaction between interpolation and a moving parent body carrying child characters.
  
  **Constraints for the GDD to record**
  1. The kernel tick must be a fixed step independent of frame rate. It must be the only place simulation state mutates.
  2. Lean: drive the kernel from a single node's `_physics_process`, with the tick rate equal to the project physics rate. The recommendation is general Godot practice, not reference-backed.
     - Physics 2D bodies (ship body, characters inside it) step on that same cadence.
     - Command application, state-block mutation and physics reads then share one ordered timeline. A custom `_process` accumulator would create two clocks (render and physics) that can disagree about ship and character positions.
     - Counter-case: a custom accumulator is justified only if the sim tick rate must differ from the physics rate, or must be pausable or steppable independently. Headless tests can get this independence more cheaply by calling `kernel.step()` directly (see point 6).
  3. Separate the tick function from its driver. `Kernel.step(commands) -> void` is a plain method with no `delta` dependency. A thin Node calls it from `_physics_process`. Tests and a future server then drive it directly.
  4. The kernel must never read wall-clock time or `delta`. Time is the tick index.
  5. Presentation interpolates, because the sim tick and the render rate differ. This is a presentation-side CanvasItem concern. Whether to use the engine's interpolation is an ADR matter; NOT SOURCEABLE for 2D on 4.7.
  6. The ship-body and interior-physics GDD (#12) must state who writes the body transform into the state block and when in the tick order. This is the highest integration risk: characters inside a moving body, with physics results feeding sim state. The Section C GDD should reserve a fixed phase order: commands applied, then domain systems step, then physics reads or writes, then notifications flush. Whether to read physics results back into blocks is an ADR.
  7. Record the tick rate as a single constant in the kernel spec. Changing it later invalidates tuned simulation values and any recorded replays.
  
  ## 2. State blocks as pure data
  
  The reference has nothing on Resource, RefCounted or Dictionary for saving. The following is general practice or reasoning.
  
  | Option | Headless/no scene tree | Typing and versioning | Serialization | Diffing | Main risk |
  |---|---|---|---|---|---|
  | Resource subclass (`class_name FooState extends Resource`, `@export` fields) | Works without a tree | Typed fields; a `schema_version` field is easy | `ResourceSaver` writes `.tres`/`.res`, and `var_to_bytes` / JSON need custom handling | Needs a hand-written `to_dict()` or compare | A `.tres` can embed a script path. Renaming a class or moving a file breaks old saves, and loading a file can instantiate scripts. Do not load untrusted saves this way |
  | RefCounted subclass | Works without a tree; lightest | Typed fields | Must write `to_dict()` / `from_dict()` yourself | Same | Hand-written serializers drift from the fields unless tests enforce parity |
  | Dictionary / packed arrays | Trivially headless | Untyped; typos produce silent nulls | `var_to_bytes` / `JSON` direct | Easy | Fields become stringly-typed. A solo developer will find bugs late |
  
  **Recommendation (an ADR picks the final form).**
  - Each block is a typed RefCounted or Resource class with an explicit `to_dict() -> Dictionary` and `from_dict(d)`.
  - The dictionary form carries `schema_version` (int) and uses only JSON-safe primitives, so it works with either `JSON` or `var_to_bytes`.
  - That dictionary is the one canonical interchange form. Save/Load (#25) serializes it. A later sync layer diffs and sends it. Tests assert against it.
  - A block must contain only data: no Node references, no `NodePath`, no signals into the scene tree, and no callbacks. Identity is by integer or StringName ID, never by object reference.
  - Blocks that hold other objects need an explicit copy or deep-copy rule. The reference notes `duplicate_deep()` (4.5+) as the explicit deep copy for nested Resource trees, and says old `duplicate()` behaviour is retained. Do not assume `duplicate()` is deep.
  - A round-trip test per block is mandatory: `from_dict(to_dict(x))` equals `x`.
  - Diffing summary state for sync: define a per-block `summary()` or `diff(prev)` contract at the kernel level now (a cheap hash or dirty-version counter per block), without building the sync. NOT SOURCEABLE: Godot built-in delta-sync of Resources or Dictionaries. MultiplayerSynchronizer replicates node properties, not kernel blocks (see section 4).
  - Packed-array caveat (4.7, sourced): writing one element of a packed array no longer calls the property's setter. A setter that marks a block dirty will NOT fire on `block.arr[i] = v`. Dirty tracking must be explicit in mutation methods, not in property setters.
  - gdUnit4 tests need no scene tree for any of these options. Plain objects and `Kernel.step()` are enough. gdUnit4 reports orphan nodes as exit 101, so a kernel that avoids Nodes also avoids orphan failures.
  
  ## 3. Change notification
  
  **Requirements.**
  - Presentation must be strictly read-only. Subscribers receive values or immutable snapshots and no mutable reference to a block, so they cannot write state even by accident.
  - The per-client Perception Filter (#20) must be able to transform what a given client sees. Players may see false or hallucinated values, so presentation must not read raw truth directly.
  - The Debug Overlay (#26) needs the true values in addition to the filtered ones.
  
  **Options.**
  - **Godot signals.** Simple and idiomatic. Risks: ordering between subscribers is implicit, emission mid-tick lets subscribers see half-applied state, and lambdas capture locals by value (sourced, current-best-practices), so a state flag set inside a lambda is lost. Share state through a reference type if lambdas are used.
  - **Explicit observer registry** (kernel-owned, called at a fixed point). Deterministic order, testable without a tree, and one place to enforce read-only. More code.
  - **Per-tick snapshot diff.** The kernel produces a per-tick change set (block id, version, changed keys) after the tick completes. Presentation and the filter consume it. It matches the future sync summary well. Cost scales with change count if dirty flags are used. A full diff of every block is wasteful.
  
  **Recommendation.**
  - Notifications are queued during the tick and flushed once, after all mutation, in a fixed phase.
  - The unit is a change record (block id, version, changed keys) delivered through a single kernel signal or registry callback. Godot signals are acceptable as the transport if the flush rule holds.
  - Two consumer channels: a true-value channel (Debug Overlay only) and a filtered channel (the Perception Filter reads true state and publishes what a client perceives). Presentation nodes subscribe to the filtered channel only.
  - Guard: presentation scripts never hold a reference to a state block. They receive a copied value or an immutable view, or query a read-only facade. The presentation-writes-only-CanvasItem/Material/Light2D rule from the brief is enforced by review plus a test that scans presentation scripts for kernel mutation calls. Whether this is a lint or convention is an ADR.
  
  ## 4. Future co-op
  
  **What networking.md says (all of it, briefly)**
  - 4.5, 4.6 and 4.7 have no relevant API breaks. ENet host and join go through `ENetMultiplayerPeer` and `multiplayer.multiplayer_peer`.
  - The server-authoritative RPC pattern: `@rpc("any_peer", "call_local", "reliable")` for client requests, an `is_server()` check with validation, then a broadcast via an `"authority"` RPC.
  - MultiplayerSpawner replicates nodes. MultiplayerSynchronizer syncs configured properties, with visibility filters for relevancy.
  - `SceneMultiplayer.auth_callback` and `server_relay` exist.
  - Common mistakes listed: client-to-server RPCs need `"any_peer"`; do not trust client data without server-side validation; use `"unreliable"` only for position-like updates; set `set_multiplayer_authority()` on spawned nodes.
  
  **What the kernel must already do (derived, not stated in the reference)**
  1. **Peer ID on every command.** Single-player is peer 1, which matches the systems-index kernel scope. In Godot the host's unique ID is 1 (general knowledge; networking.md does not state it). Command shape is `{peer_id, tick, seq, type, payload}`. Domain systems never read "the local player" as a global; they take `peer_id` from the command.
  2. **One authority check in one place** (the dispatcher), mirroring the sourced rule "validate on the server." Domain code never validates peers itself.
  3. **Deterministic ordering.** Commands are applied in a defined order (tick, then peer ID, then sequence number), never in arrival or dictionary-iteration order. State-block registry iteration is ordered by registration ID.
  4. **Commands are serializable data.** Payloads use only types that RPC or `var_to_bytes` can carry (primitives, packed arrays, StringName/ID). No Node or Object references. Note that Godot's RPC default is to disallow object serialization; the reference does not cover this (NOT SOURCEABLE).
  5. **Summary-state sync, not node-property sync.** MultiplayerSynchronizer replicates node properties. The kernel's blocks are not nodes. A future replication layer would either mirror summary blocks into synchronizer-visible properties on a thin proxy node or ship change records through RPC. The spawner and synchronizer fit the presentation and character nodes. They do not fit the authoritative state blocks directly. NOT SOURCEABLE: bandwidth, interest management or delta behaviour of MultiplayerSynchronizer on 4.7. The kernel must therefore expose `get_summary(block_id)`, `apply_summary(block_id, data)` and per-block version counters now, so the replication layer is additive. Whether this proxy approach is right is an ADR (co-op replication, #33).
  6. **Prediction and reconciliation** (a client applying its own commands speculatively): NOT SOURCEABLE and out of scope for MVP. The only guard now is that commands carry `tick` and `seq`, and that the sim is deterministic for given inputs. Note that floating-point and physics determinism across machines is not guaranteed. The reference claims Jolt is "more deterministic," but Jolt is 3D-only and Godot Physics 2D has no determinism claim. Therefore the GDD should record: do not rely on lockstep determinism of physics; host state is the truth.
  7. No kernel code should call `multiplayer.*`. A single adapter at the edge translates RPCs into commands and change records into sync messages.
  
  ## 5. Hard limits and gotchas from the pinned reference
  
  - **4.7 typed-return overrides (sourced, GDScript breaks):** an override of a method with a typed return type inherits that type and needs an explicit `return` (`return null` fix). This bites abstract-style base classes such as a `StateBlock` base with `func to_dict() -> Dictionary` or a `Command.apply() -> Result` that subclasses override. Every override must return on every path.
  - **4.5 `@abstract` (sourced):** classes and methods can be enforced abstract. An abstract method has no body. Usable for `StateBlock` and `Command` bases. The reference shows it only with `class_name ... extends CharacterBody3D`-style declarations; nothing tests it with RefCounted. Verify with a parse check.
  - **4.5 variadic args (sourced):** `...values: Array` comes last and is typed `Array` or untyped. `values: Variant...` and `...values: Array[int]` do not parse. A rest parameter works in lambdas, so `func(...args)` can connect to a signal of any arity. A lambda with the wrong arity errors at runtime ("expected 1 argument(s), but called with 0").
  - **Lambda capture (sourced):** locals are captured by value, and a lambda cannot reassign an outer local. Mutate a shared reference object.
  - **4.7 packed array element writes (sourced):** see section 2.
  - **4.5 `duplicate_deep()` (sourced):** see section 2.
  - **4.4 `FileAccess.store_*` return `bool` (sourced):** save code should check the return value. Relevant to Save/Load (#25).
  - **4.7 `Object.is_class()` takes `StringName` (sourced).** Minor: matters for block-type dispatch by class name.
  - **Typed arrays, autoloads, signal API changes, Resource saving:** the reference lists no breaking changes for these between 4.4 and 4.7. That means none are listed, not that none exist. NOT SOURCEABLE beyond the migration guides. Autoload caveat (sourced, observed): `--check-only` with `-s` fails on valid code that names an autoload ("Identifier not found"). The reliable parse check is the framework's `godot-parse-check.gd`. Practical consequence: if the kernel is an autoload, scripts that name it fail the quick check, and tests that need the kernel should instantiate it directly rather than through the autoload name.
  - **gdUnit4 on the pin (sourced):** 6.2.x runs on 4.7.2 though 4.7.2 is not yet in its README compatibility list (4.5 to 4.7.1 listed). Run `--import` before the first test run. Exit 101 also means orphan nodes leaked. Fresh `--import` crashed on exit in 3 of 17 runs on 4.7.x; rerun it.
  - **Process note:** "Last verified" for most reference files is 2026-02-12 for 4.4 to 4.6 content, so treat older rows as lower-confidence.
  
  ## 6. The three things most likely built wrong, with guard rails
  
  1. **State leaks into the scene tree (blocks that are Nodes, or blocks holding Node refs or signals to nodes).** For a first-time Godot developer, a Node is the default container, and state ends up on the player, the ship and the HUD.
     - Guard rail: blocks extend RefCounted or Resource, never Node, and contain no object references to nodes.
     - Enforcement: one gdUnit4 suite that constructs every registered block with no scene tree running and round-trips it through `to_dict`/`from_dict`. A block that cannot be built headless fails the suite.
     - Add a registry rule that rejects any block whose dictionary form contains a non-primitive.
  
  2. **Presentation mutating state, or the kernel being bypassed.** Typical shapes: a HUD button changes a block directly, a gameplay script sets a field "just this once", a signal handler writes back to a block.
     - Guard rail: all writes go through `Kernel.submit(command)`. Blocks expose read-only snapshots to presentation. Mutation methods live on the domain system and are called only by command handlers.
     - Enforcement: a test that scans presentation scripts for forbidden calls, plus a code-review checklist item. The brief's CanvasItem/Material/Light2D-only rule is the allow-list.
  
  3. **Ticks and notifications done on the wrong clock or in the wrong order** (mutation in `_process`, signals emitted mid-tick with half-applied state, order depending on dictionary iteration or node order, or the ship-body phase and the sim reading each other inconsistently).
     - Guard rail: a single `step()` entry with a fixed phase order (apply commands, step domain systems, physics sync, flush notifications), a tick index instead of time, and sorted command and block iteration.
     - Enforcement: a determinism test that feeds the same command sequence twice into two fresh kernels and asserts identical `to_dict` for every block and the same change-record sequence. This is also the cheapest test that the later co-op addition stays additive.
  
  **Peer ID plumbing is a fourth near-miss worth a guard**: a command constructor that does not require `peer_id` should not exist. A unit test asserts that every command type refuses to construct without it.
