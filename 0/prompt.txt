  **What the architecture is, in rendering terms.**
  
  - Root `Window` with `canvas_items` + `integer` + base 640×360: the root canvas (HUD `CanvasLayer`, `SubViewportContainer`) is laid out in 640×360 base units and drawn with a final transform of exactly N (N = floor(min(W/640, H/360))) `[UNV-4.3]`. The HUD is therefore integer-scaled by construction (8.11 flag 3's condition).
  - **Pass A** (`SubViewport.size = 640×360`, container `stretch = true`): the world raster is 640×360 texels; every sprite, light, shadow, glow and `CanvasModulate` resolves at base resolution; the container draws that texture ×N. Lit pixels = 230 400. Cone and shadow edges are on the base grid; glow radius is in base px.
  - **Pass B** (`SubViewport.size = W×H`, `size_2d_override = 640×360`, `size_2d_override_stretch = true`): the world raster is W×H texels; canvas coordinates are logically 640×360 (one canvas unit = N render px) `[UNV-4.3]`; sprites sample nearest at an integer scale **only if** item origins land on multiples of N render px — the snapping question in item 2; lights, shadows and glow resolve at W×H. Lit pixels at 1080p = 2 073 600 (the 9× lever of 8.11 flag 4). Rotated horror segments become angled N×N blocks (8.4's tolerated-for-horror consequence).
  - The two passes differ in **where the raster lives**, not in scene content; 8.12 step 2 judges them. Pass A is the accepted fallback.

  ## 2. Pixel integrity
  
  **Facts `[BIN]`.** `rendering/2d/snap/snap_2d_transforms_to_pixel = false`, `snap_2d_vertices_to_pixel = false`; both exist as `Viewport` members and as `RenderingServer.viewport_set_snap_2d_*` per viewport. `rendering/textures/canvas_textures/default_texture_filter = 1` (LINEAR); `Viewport.canvas_item_default_texture_filter = 1`; `CanvasItem.texture_filter = 0` (`PARENT_NODE`); `CanvasItem.TEXTURE_FILTER_NEAREST = 1`; `Viewport.gui_snap_controls_to_pixels = true`. `Sprite2D.centered = true`, `offset`. `physics/common/physics_interpolation = false`; `Node.physics_interpolation_mode` {INHERIT, ON, OFF}, `reset_physics_interpolation()`; `SceneTree.physics_interpolation`; `Engine.get_physics_interpolation_fraction()`; `RenderingServer.canvas_item_set_interpolated / canvas_item_transform_physics_interpolation / canvas_item_reset_physics_interpolation`, and the same three for `canvas_light_*` and `canvas_light_occluder_*`. **`get_global_transform_interpolated()` exists on `Node3D` only — not on `Node2D` or `CanvasItem`.**
  
  So the art bible's "2D physics interpolation NOT SOURCEABLE on 4.7" is upgraded: the 2D machinery **exists** in 4.7.2 `[BIN]` (items, lights, occluders). Its behaviour remains NOT SOURCEABLE.
  
  **Constraints and recommendations.**
  
  1. **One interpolator.** The kernel already mandates `tick_alpha` with prev/curr read views (CR-10, D.3) and clamps at 1 (no extrapolation — Pillar 1). Engine `physics_interpolation` and `Camera2D.position_smoothing` are each a *second* interpolator on a clock the kernel does not control. Recommend `physics/common/physics_interpolation = false`, every presentation node with `physics_interpolation_mode = OFF`, and sim-driven motion interpolated only from `tick_alpha`. Decisive `[BIN]` reason: no 2D `get_global_transform_interpolated()`, so a camera (or any script) cannot read where an engine-interpolated body is actually drawn — it would follow the un-interpolated pose and jitter against the sprite. **→ ADR (interpolation clock)**.
  2. **Snap is a floor, not a filter.** Interpolation then snapping can only change the *timing* of one-base-pixel steps, never their size: a body moving 1 base px/tick shows a 3×3 screen block step at 1080p whenever it moves. The GDD must promise "base-pixel steps at interpolated timing", not sub-pixel smoothness. Presentation computes `pos = floor(lerp(prev, curr, tick_alpha))` in base px itself (deterministic, unit-testable, headless), and the viewport snap flags are belt-and-braces. Spike: with both on, check for double-rounding (1-px flicker at .5 boundaries) `[UNV-4.3]`.
  3. **What snap snaps to under pass B is NOT SOURCEABLE** — base px (every N render px) or render px. If render px, pass B puts sprites off-grid relative to the viewport unless presentation floors to base px first — forbidden for human-built art (8.4). Rule 2 makes this moot for sim-driven motion; the spike still has to confirm for `Camera2D` and for tile layers.
  4. **Camera sub-pixel.** The camera's base-px position is floored by the same rule before being written; `Camera2D.limit_*` are `int` `[BIN]` so limits are already integer base px. Whether the engine's `snap_2d_transforms_to_pixel` also snaps the canvas transform the camera produces is NOT SOURCEABLE — flooring the camera manually removes the dependence.
  5. **Half-pixel origins.** `Sprite2D.centered = true` by default `[BIN]`: a texture with an odd dimension centred puts its origin on a .5 → a 1-px wobble under NEAREST (blur under LINEAR). 8.2's cells are even (80×80, 48×48, 96×96) and the foot-centre origin is set via `offset`, so this is satisfied by asset standard; the GDD should state the rule (even cells, or `centered = false` + integer `offset`) so VFX and one-off sprites do not break it.
  6. **Rotated sprites under nearest.** No antialiasing; edges staircase and texels drop/duplicate along the edge. Pass A: a rotated segment resolves on the base grid like everything else. Pass B: angled N×N blocks. Policy is settled in 8.4 (human-built never rotates at runtime; horrors/web quantised to 15°, 12 fps). Section C records it as a testable rule: `rotation == 0` on every node under the environment/pipe/prop/actor groups (lint), 15° quantisation on horror rigs (test). `snap_2d_vertices_to_pixel`'s effect on a rotated quad's corners is NOT SOURCEABLE — 8.12 step 2 judges the rotating segment.
  7. HUD: `gui_snap_controls_to_pixels = true` `[BIN]` on the root; the HUD's integer scale comes from the root stretch (item 1), and `Control.scale` stays `(1,1)`.
  
  **Spike must verify:** proposed **8.12 step 12 "motion integrity"** — a test body moving 1 base px/tick and another moving 0.4 base px/tick (sub-pixel speed), captured at 30, 60, 144 fps: no frame shows a backward step, a doubled step, or a fractional offset; `physics_interpolation` ON vs OFF, measuring camera-vs-sprite jitter in render px; both snap flags on vs off; pass A vs B snap target.

  ## 4. Camera
  
  **Facts `[BIN]` — exhaustive `Camera2D` member list:** `anchor_mode = 1` (DRAG_CENTER), `custom_viewport`, `drag_bottom/left/right/top_margin = 0.2`, `drag_horizontal/vertical_enabled = false`, `drag_horizontal/vertical_offset = 0.0`, `editor_draw_drag_margin/limits/screen`, `enabled = true`, `ignore_rotation = true`, `limit_bottom/left/right/top: int = ±10 000 000`, `limit_enabled = true`, `limit_smoothed = false`, `offset`, `position_smoothing_enabled = false`, `position_smoothing_speed = 5.0`, `process_callback = 1` (IDLE), `rotation_smoothing_enabled/speed`, `zoom: Vector2 = (1,1)`. Methods: `align()`, `force_update_scroll()`, `get_screen_center_position()`, `get_target_position()`, `reset_smoothing()`. **There is no pixel-snap member — confirmed by the exhaustive list**, so snapping is the viewport's flags plus presentation flooring (item 2).
  
  **Constraints and recommendations.**
  
  1. **Zoom is N, not `Camera2D.zoom`.** 8.1's zoom-out step ("at 1080p the single step out is 2×, sprites at 67 %") is a change of the world's integer scale factor N (3→2) with more base pixels in view (960×540), not a camera zoom: `Camera2D.zoom = (2/3, 2/3)` would be fractional and `(0.5, 0.5)` would drop every other texel under nearest. Rule: **`Camera2D.zoom` stays `(1,1)` always**; zoom-out is implemented as the world `SubViewport` showing `(W/N', H/N')` base px for the smaller integer N' (pass A: `size`; pass B: `size_2d_override`) **while the HUD stays at N** (8.1: "the frame grows, the world does not"). That is two integer scales in one window — **the same wiring question as pass B** (item 1 constraint 4): under one root `integer` stretch the container would draw a 960×540 texture into a 640×360 base rect, a fractional container scale that is only integer in render px if the engine composes the chain before sampling (NOT SOURCEABLE). Zoom-out therefore shares pass B's candidate wirings (i)/(ii) and is folded into proposed step 11. The brief's "zoom as integer Vector2" should be reframed: integer `zoom` values ≥ 1 zoom *in* — the direction of this convention flipped between Godot 3 and 4 and is `[UNV-4.3]`, checked in step 11 — and are not what 8.1 asks for. Game-designer flag already in 8.12 ("integer zoom steps only"). **→ ADR**.
  2. **Camera is a top-level presentation node, never a child of the body.** `process_callback` default IDLE `[BIN]` means the camera updates in `_process`; a camera parented to a `CharacterBody2D` inherits the body's transform on the engine's clock, not the kernel's (and its rotation unless `ignore_rotation`, default true `[BIN]`), and no 2D API exposes an interpolated global transform (`get_global_transform_interpolated()` is `Node3D`-only `[BIN]`). The camera script reads the Body read view (prev/curr) and `tick_alpha`, composes **ship(α) × local(α)** exactly as the actor's presentation node does, floors to base px, writes `global_position`. If the two compose differently the camera lags the sprite by up to a tick. `Node.process_priority` `[BIN]` orders the camera after the actor presentation within `_process` (behaviour `[UNV-4.3]`, step 12).
  3. **`position_smoothing_enabled` stays false** — second interpolator (item 2). If designers want lag/ease, it is applied to the *target* in base px by the presentation script and floored afterward, so the camera still lands on whole base px every frame. `limit_smoothed` likewise false.
  4. **Limits** are `int` base px `[BIN]`; with the world in ship-local coordinates the limits are the loaded section's bounding rect and are set by a `PROJECTOR` when sections weld/detach (kernel CR-10 class), never by the camera itself.
  5. **`drag_*` margins** (default 0.2, disabled `[BIN]`): usable, but the drag window is in viewport fractions, so the resulting camera position is fractional and must be floored (rule 2 above); with `anchor_mode = DRAG_CENTER` and a 640×360 view the margins are 128×72 base px. The frame is tight (13.3 × 7.5 tiles, 8.2); recommend starting with drag off and a hard follow, adding margins only if the spike shows readable framing.
  6. **Transform hierarchy and the moving ship.** If the ship's world-space transform rotates, every human-built interior sprite rotates off-grid under nearest sampling — forbidden by 8.4. Two consistent resolutions, neither Section C's to pick: (a) **render in the ship-local frame** — the world `SubViewport`'s canvas *is* the ship frame, the ship's motion appears only on the exterior/background layer (`Parallax2D` / `ParallaxBackground` exist `[BIN]`), the interior never rotates; (b) `ignore_rotation = false` so the camera rotates with the ship and the interior stays axis-aligned in screen space while the exterior rotates. (a) is cheaper and avoids the question of what snapping does to a rotated canvas transform (NOT SOURCEABLE). Dependency question for the Ship Body GDD (kernel C.3 #6, Open Question 3). **→ ADR**.
  
  **Spike must verify (proposed 8.12 step 12):** camera following a body on a translating ship section at 144 fps — zero render-px disagreement between camera and sprite each frame; `get_screen_center_position()` is integer base px; limits clamp without fractional residue; `drag` margins + floor produce no 1-px oscillation at rest.

  ## 6. Frame pacing
  
  **Facts `[BIN]`.** `physics/common/physics_ticks_per_second = 60`, `max_physics_steps_per_frame = 8`, `physics_jitter_fix = 0.5`, `physics/common/physics_interpolation = false`; `application/run/max_fps = 0`, `delta_smoothing = true`, `low_processor_mode = false`; `display/window/vsync/vsync_mode = 1` (ENABLED) with `DisplayServer.VSYNC_{DISABLED=0, ENABLED=1, ADAPTIVE=2, MAILBOX=3}`, `window_set_vsync_mode`, `screen_get_refresh_rate`; `rendering/rendering_device/vsync/frame_queue_size = 2`, `swapchain_image_count = 3`; `Engine.get_physics_interpolation_fraction()`, `is_in_physics_frame()`, `get_physics_frames()`, `get_process_frames()`, `get_frames_per_second()`; `SceneTree.physics_frame` / `process_frame` signals; `Node.process_priority`, `process_physics_priority`.
  
  `_process`/`_physics_process` ordering within a frame is **silent in REF** (kernel D.4 says so and makes the "same-frame" best case spike-conditional).
  
  **Constraints and recommendations.**
  
  1. **The sim is fps-independent by construction and the GDD says so as a test**: identical `state_hash` after a scripted 10-s input replay at `max_fps` 30, 60, 144 and 0 (kernel G3 determinism + CR-11). Presentation reads last-committed state at render rate and never causes a tick.
  2. **Who drives the tick is an ADR the pacing promises depend on.** Kernel D.4 assumes the tick is driven by the physics callback (60 Hz; `max_physics_steps_per_frame = 8` `[BIN]` — if it caps catch-up at 8 ticks/frame `[UNV-4.3]`, the engine stops catching up below 7.5 fps; step 13 checks); kernel D.5 defines a kernel-side accumulator with its own `MAX_TICKS_PER_FRAME`. Two accumulators drift; one must be the clock. If the physics callback drives, `physics_jitter_fix` (default **0.5**, non-zero `[BIN]`) alters per-step timing in a way NOT SOURCEABLE here — recommend **0** pending the spike, since a fixed-tick kernel that forbids wall-clock reads (H9) should not receive engine-smoothed steps. `delta_smoothing = true` `[BIN]` affects `_process` delta only `[UNV-4.3]`; harmless to presentation, irrelevant to the sim. **→ ADR (tick driver)**.
  3. **Promise at 30 fps render:** two ticks per frame, sim unchanged; `tick_alpha` clamps at 1 so nothing extrapolates; input-to-pixel worst case 50 ms (kernel D.4); motion shows every second tick's pose — 2-base-px steps for a 1 px/tick body, which is honest, not smoothed.
  4. **Promise at 144 fps render:** ticks occur on ~42 % of frames; without interpolation 58 % of frames would repeat a pose (visible judder); with `tick_alpha` interpolation + base-px flooring, the camera and sprites step one base px at the interpolated instant, never twice in a frame and never backward. No sub-base-pixel motion exists at any fps (item 2 rule 2). Input latency is unchanged by fps above 60 except `L_render` shrinks to ≤ 6.9 ms.
  5. **V-sync defaults:** ship `VSYNC_ENABLED` (engine default `[BIN]`); expose `MAILBOX` as the "uncapped, no tearing" option and `DISABLED` + `max_fps` for benchmarking; never `ADAPTIVE` by default (behaviour on Windows D3D12 vs Vulkan NOT SOURCEABLE). `max_fps = 0` default `[BIN]`; a user-facing cap of 30/60/120/144/240/0 is a Settings-slice item. On the Deck, 40 Hz or 90 Hz panels are not multiples of 60: the interpolation path is what keeps motion even there — spike at 40 and 90 fps caps.
  6. **Pause and reduced motion** never alter the tick (CR-11); `SceneTree.paused` `[BIN]` must not be the kernel's pause (H10 — the kernel is scene-tree independent), so the pipeline root maps game pause to kernel `PAUSED` and the engine's `paused` only to presentation nodes if at all. **→ ADR** (part of tick driver).
  
  **Spike must verify (proposed 8.12 step 13 "pacing"):** `state_hash` equality across fps caps; frames-with-repeated-pose count at 144 fps with and without interpolation; `physics_jitter_fix` 0 vs 0.5 effect on tick timing (log `get_physics_frames()` vs wall clock); same-frame `_physics_process` → `_process` ordering (kernel D.4 best case); 40/90 fps caps; the `max_physics_steps_per_frame` cap semantics.

  **The three things a solo first-time Godot developer most likely builds wrong here, with a guard rail each:**
  
  1. **Shipping the engine defaults.** `project.godot` has no `[display]` block: the game runs at 1152×648, stretch disabled, fractional, LINEAR, unsnapped, SDR — and looks "almost right" in the editor at 1× so nobody notices until 1440p. **Guard:** the explicit block (approval path 8.11 flag 7) plus a **debug-build startup assertion** in the pipeline root that reads back `get_window().content_scale_mode == CANVAS_ITEMS`, `content_scale_stretch == INTEGER`, `content_scale_size == (640,360)`, the world `SubViewport`'s filter/snap/hdr members, the container filter (with the correct enum per target), and prints the driver name — failing loudly on any mismatch; plus a gdUnit4 test that parses `project.godot` for the same keys so the check runs headless in CI.
  2. **Two clocks moving one thing.** Turning on `physics_interpolation`, or `position_smoothing_enabled`, or parenting the `Camera2D` under the `CharacterBody2D`, each adds an interpolator on a clock the kernel does not own — the symptom is a sprite that swims 1–3 render px against the camera at 144 fps and looks fine at 60. **Guard:** `physics/common/physics_interpolation = false` and `position_smoothing_enabled = false` asserted at startup; a scene-tree lint "no `Camera2D` descends from a `PhysicsBody2D`"; and the motion-integrity test (8.12 step 12) run at 144 fps in CI with a scripted body.
  3. **Fractional transforms leaking into the world canvas.** A float position from a tween, a `Camera2D.zoom = 0.67` for "zoom out", a `Control.scale` on a HUD panel, `centered = true` on an odd-sized VFX sprite, or a horror rig rotated by an unquantised angle — each produces a half-pixel or off-grid draw under NEAREST that reads as a one-frame flicker. **Guard:** a debug-only tree walk (every frame in debug builds, behind a console toggle) over the world `SubViewport` that flags any `CanvasItem` whose `global_position` has a fractional part after presentation has written it, any `rotation != 0` under human-built groups, any `Camera2D.zoom != (1,1)`, and any `Control.scale != (1,1)` on the HUD; and the lint from item 2 rule 6.
  
  A fourth that is already settled by art but worth a lint: Y-sort on the floor layer, or a `TileSet.tile_size` left at 16×16 `[BIN]`.
