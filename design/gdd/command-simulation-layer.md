## Summary

The Command & Simulation Layer is the thin kernel every other system runs inside: a fixed 60 Hz tick, a single door through which every change to the game's state passes as an authority-checked, peer-stamped **command**, a registry of **state blocks** that domain systems own and the kernel never does, and a once-per-tick **change notification** that presentation reads but can never write back through. The player never sees it; what they get from it is a ship that cannot lie — gauges and sprites may be hallucinated, but there is exactly one authoritative truth beneath them, and every command is judged against it. The kernel does not make that truth visible — how, when and at what cost the player learns why a command failed is priced by Interaction, Sanity and the HUD under Pillar 4's verification rule. It exists so that *The World Never Lies* and *Sanity Rewrites Reality* are structural rather than aspirational, and so that co-op can be added later without a rewrite: single-player is simply the host with one local peer.

> **Quick reference** — Layer: `Foundation` · Priority: `MVP` · Key deps: `None` (upstream); 16 downstream dependents, all MVP/VS systems register with it

## Overview

The Command & Simulation Layer is the thin kernel every other system of The Synaptic Sea runs inside. It advances the simulation at a fixed tick, accepts every change to the game's state as a **command** carrying the identity of the peer that issued it, checks that peer's authority, validates the command against current state, applies it or rejects it with a reason, and then tells presentation what changed. It owns no domain state of its own: the Life-Support Graph, the ship layout, suit vitals, Attention, sanity and the rest each register their own **state block** with the kernel's registry and define their own command handlers. The kernel's job is to be the one door through which truth changes.

The player never sees this system; they interact with it only through the systems built on it — every weld, every valve turned, every step taken is a command the kernel admitted. It is automatic from the player's point of view and invisible when it works.

It exists for two reasons that are both pillars. First, **The World Never Lies** needs one authoritative truth: if any system could mutate state directly, two readers could disagree about whether a pipe is leaking, and the honest-world promise would be unenforceable. Second, **Sanity Rewrites Reality** needs a wall: the Perception Filter and every other presentation script may *read* simulation state and write only what is drawn, never what is true. The kernel is that wall made structural rather than aspirational, and its registry is also the hook the Save/Load contract and the true-value Debug Overlay hang from. The game would lose, without it, the ability to add co-op later without a rewrite (TD-FEASIBILITY: authority discipline from day one — in single-player the local peer simply *is* the host) and the guarantee that a hallucination can never corrupt the ship.

**Design-level only.** Whether the kernel is an autoload, how commands are encoded, and how change notification is delivered are implementation choices → **becomes an ADR** (authority model). *(Framing: technical infrastructure, no ADR yet to cite, no direct player fantasy — selected as the recommended options for a `Core`/`Foundation` system under `autonomous` automation.)*

## Player Fantasy

*Indirect — the player never meets this system; they meet a promise it keeps.*

**There is only one ship.** A gauge in the scrubber bay can read green while frost climbs the elbow beside it, and the player has to decide which to believe. The answer is always the same, and it is always available: the gauge and the frost both read the same state, and only one of them passed through the player's mind on the way to the screen. Nothing the player sees, hears or imagines can reach back and change what the ship is doing.

The anchor moment is in the cryo bay or on the first sortie. The player has "fixed" a scrubber and the needle has settled. Then their breath fogs, and they realise the room is still getting colder. The horror is personal: *I am the thing that is broken.* The comfort is structural: *the ship is not.* Each time a player checks and the world turns out to be right, they learn to trust the world more and their own eyes less. That trust is the only thing this system gives the player, and one physical consequence that disagrees with what the ship is actually doing would spend it.

In co-op, the same rule gives every act a name. A sane crewmate cannot fake the web's violence, and the beam in the corridor belongs to whoever's beam it is.

**Pillars served.** *The World Never Lies*: "Pipes leak, frost forms, air hisses; the physical world is ground truth. Only instruments and perception can be wrong." *Sanity Rewrites Reality*: "Broken reads as fixed, fixed as broken; the lie extends from the gauge to the sprite. The physical consequence stays honest." The concept's own resolution of their tension — "the physical ship is ground truth; instruments and perception are what can be wrong. The tension is the game" — is what this kernel makes structurally true.

**Design tests.**
- If we are debating whether a presentation-side effect (a hallucination, a light flicker, a UI animation) may adjust simulation state for convenience, or must be routed through a command: route it, or don't do it.
- The fantasy has failed if any player-visible physical consequence ever disagrees with the authoritative state. That is a Pillar 1 violation, not a cosmetic bug — and the reason the Debug Overlay exists.

*What this section does not claim*: the kernel does not make the truth visible. Failure & Trail, Lighting's true reveal radius and the human channel do that. The kernel is why there is only one truth for them to show. (Alternatives considered: a co-op-first "identity behind every act" framing — true but untestable before VS-B and over-credits the kernel; a "steady pulse" fairness framing — honest about the tick but mostly the Graph's and Attention's fantasy.)

## Detailed Design

### Core Rules

*Specialists consulted: systems-designer (primary), gameplay-programmer (feel/feasibility), engine-programmer (Godot 4.7.2 integration). Their one disagreement — tick rate — is resolved in CR-1. Items tagged **→ ADR** are engine-integration choices deliberately left out of this behaviour spec.*

**Vocabulary.** *Tick*: one fixed-step iteration of the authoritative simulation; tick number `T` is a monotonically increasing integer and the only clock the simulation knows. *State block*: a named, versioned, single-owner container of domain state registered with the kernel. *Command*: a serializable request to change state, carrying issuer identity. *Owner*: the domain system that is the only writer of a block. *Read view*: the read-only accessor an owner publishes. *Step hook*: owner-registered code that runs in the propagation phase. *Mode*: `HOST` (authoritative; the only mode in MVP) or `MIRROR` (VS-B guest: receives state, runs no authoritative tick) — the public API is identical in both. *PlayerId*: a stable seat identity (1 in single-player; PlayerId 0 is reserved as "no seat" — additive, provisional *(Amended 2026-10-27 — consistency pass, routed from ship-body-and-interior-physics)*); *peer_id*: the transport identity of a connection (host = 1). Persistent per-player state is keyed by PlayerId, never by peer_id, because peer IDs are reassigned per connection (this corrects the systems index's "keyed by peer ID" for Sanity and Suit).

**CR-1. Fixed tick at `TICK_RATE` = 60 Hz, with per-hook step divisors.** The simulation advances in steps of exactly `1/TICK_RATE` seconds of *simulated* time, independent of render frame time; durations everywhere are in ticks (the Attention tell window of 10–30 s is 600–1800 ticks). The kernel never reads wall-clock time or `delta`. Input- and physics-adjacent hooks run every tick; slow systems run at a divisor (Graph 6 → 10 Hz, Attention 6, Suit vitals 6, Sanity drift 12 → 5 Hz).
*Rationale and alternatives.* The gameplay-programmer argued for a 20 Hz kernel (slow systems don't need more; worst-case 50 ms latency is invisible behind immediate local acknowledgement) but set a hard floor of 15 Hz and would push back at 10. The engine-programmer argued for tick = physics rate so the moving ship body and the characters inside it share one timeline. 60 Hz + divisors satisfies both: one clock, submit-to-applied within one tick (16.7 ms of simulated time) on an empty queue, and the cost profile of a 10 Hz graph. *(Amended 2026-10-27 — design review)* A variable timestep was rejected (breaks replay, tests and save equivalence); a 30 Hz kernel sits at an awkward ratio to Godot's 60 Hz physics step. The tick *source* is settled in CR-1a (a `TickDriver` with an injected delta, not the physics callback); `step()` stays a plain method that tests and a future server call directly. Changing `TICK_RATE` later invalidates every tuned value expressed in ticks. *(Amended 2026-10-27 — design review)*

**CR-1a. Tick driver, clock source and catch-up** *(Amended 2026-10-27 — design review; closes former Open Question 2, the technical-director confirms it in the spike)*. `Kernel.step()` has no clock. A `TickDriver` (a `RefCounted`, no scene tree) owns the accumulator, receives time as an injected integer count of microseconds (`delta_us`), and is driven by exactly one node with `process_mode = PROCESS_MODE_ALWAYS` from its `_process(delta)`; that node converts the engine's `delta` to `delta_us` once, and that conversion plus the diagnostics timer are the only wall-clock reads in the project (H9). **Godot's physics step is not the clock**: at MVP the avatar has no physics body (CR-13), so nothing needs the physics callback, and the driver needs no coupling to `physics/common/max_physics_steps_per_frame` (the former coupled constraint 4 is deleted). A later Vertical Slice physics projection runs in `_physics_process` as a `PROJECTOR` reading committed state and never steps the kernel. The accumulator is an integer in units of *microseconds × TICK_RATE*, so one tick is exactly `TICK_UNITS` = 1,000,000 units for every integer `TICK_RATE` (no float drift, no boundary flips); each frame `acc += delta_us × TICK_RATE`. Per frame the driver (1) runs the boundary service (CR-15) before any tick; (2) while the kernel is `RUNNING`, runs `step()` `ticks_run = min(floor(acc / TICK_UNITS), MAX_TICKS_PER_FRAME)` times, **re-reading the kernel state after every `step()`** and stopping (and clearing `acc`) the moment it is no longer `RUNNING` — a P6 pause, a restore, a fault; (3) applies lag forgiveness (D.5); (4) flushes the result buffer (CR-5); (5) while `PAUSED`, runs the paused boundary service (CR-16). **The accumulator is cleared on every transition into `RUNNING`** (from `LOADING`, `PAUSED` or `SAVING`), so a load, an autosave or a pause never produces catch-up ticks afterwards. The driver node has a process priority that runs it before the presentation nodes, so presentation reads the tick the driver just produced. Tests call `Kernel.step()` directly, or inject `delta_us` into the driver; nothing in the kernel sleeps or reads a clock.

**CR-2. Tick phase order.** Each tick executes these phases to completion, in order, with no interleaving:

| # | Phase | What happens | Who may write blocks |
|---|-------|--------------|----------------------|
| P0 | Begin | Tick counter increments; the pending set is *frozen* as this tick's candidate set (commands arriving now wait for T+1) | nobody |
| P1 | Intake | Candidate set in ordering-key order (CR-13) — a sort only when a non-monotone (remote) insert happened since the last tick, otherwise the head of an already-ordered queue — the first `MAX_CMDS_PER_TICK` form this tick's **batch**; the overflow returns to the unfrozen pending set in order and stays supersedable (Section E) | nobody |
| P2 | Dispatch | Per command in order: authority check → validate → apply or reject (CR-5) | the handler, inside `apply` only |
| P3 | Step | Step hooks in resolved order (CR-3); a hook runs when `T mod divisor == offset` | the hook's own block, plus owner-published mutators of other blocks (CR-9) |
| P4 | Commit | Dirty sets finalised; "tick committed" marker advances; interpolation baseline captured | nobody |
| P5 | Notify | Batched change notifications delivered (CR-10), then the result buffer is flushed (CR-5) | nobody — writes disabled |
| P6 | Boundary services | Pending control-plane requests in arrival order (CR-15), pending snapshot (Saving), command-log append | the kernel only |

P2 commands see earlier P2 effects in the same tick; P3 sees all of P2; subscribers and presentation only ever see post-P4 state, never a half-applied tick. **Paused service cycle** *(Amended 2026-10-27 — design review; a retained seam that only test fixtures exercise at MVP, because no MVP command type sets `allowed_when_paused`)*: on every rendered frame while `PAUSED` the driver runs the paused boundary service — P1, P2, P4, P5, P6 with no P0 and no P3, `T` unchanged — dispatching only commands of `allowed_when_paused` types (CR-16). It is a deliberate carve-out from the running-tick guarantees: its commits apply at the current `T` (`apply_tick == queued_tick` is legal there, unlike a running tick), several commits can share one `T`, and G1/G2/G3 hold for it only as CR-13 states.

**CR-3. Step hooks and ordering.** Hooks register `(hook_id, owner, divisor, offset, after: [hook_id | {hook_id, tolerates_stale}])`. The kernel resolves a total order by topological sort of `after`; ties break by registration order, then `hook_id`. A cycle or unknown `hook_id` fails boot (CR-6). Sim-to-sim data flow within a tick is "reader declares `after` writer" (Suit vitals `after: graph.propagate.atmo` — the Graph registers three chained hooks, see its LS-1 *(Amended 2026-10-26 — consistency check, routed from the Life-Support Graph GDD)*). The order is data: testable, and printable by the Debug Overlay. An `after` edge between two hooks that never run in the same tick (Section E) must carry `tolerates_stale: true` if the reader accepts data up to a divisor old; boot warns only for **undeclared** mismatches, so the real boot (`horror.step` divisor 5 after `attention.step` divisor 6) stays silent once declared and the warning keeps its meaning. *(Amended 2026-10-27 — design review)* Hooks may not submit `PLAYER`-origin commands; they may submit `SYSTEM`-origin ones (CR-4) through `submit_system(type, payload, dedupe_key = none)` and may ask `has_pending(type, dedupe_key)` (CR-9 owner rule).

**CR-4. Command anatomy, origin and intents.** A command is plain serializable data:

| Field | Meaning |
|-------|---------|
| `type` | Registered command type ID, owned by a domain system |
| `issuer_peer` | Stamped by the kernel's ingress — never taken from the payload |
| `origin` | `PLAYER` or `SYSTEM`, stamped by ingress |
| `actor` | The entity the command acts as (opaque ID), or none |
| `seq` | Monotonically increasing integer per `(issuer_peer, origin)` — the host's `PLAYER` and `SYSTEM` streams are separate spaces *(Amended 2026-10-27 — design review)* |
| `payload` | Plain data only, per the recursive whitelist below; no object references, node paths or callables; `var_to_bytes(payload, false).size()` ≤ `MAX_PAYLOAD` |
| `queued_tick` | Stamped on enqueue |
| `submission_id` | Kernel metadata, never payload-borne: a kernel-unique counter stamped at ISSUED, before admission, so even a rejected submit has one; it is the `result_id` of the command's result (CR-5) *(Amended 2026-10-27 — design review)* |

*Discrete commands vs continuous intents.* If the sim must log, validate, save or replay it, it is a command (examples; each type's owner GDD is authoritative: Controller `set_move_intent`, `set_aim`, `toggle_beam`; Interaction `begin_cut` (module salvage, V8), `begin_patch`, `cancel_channel`, `pickup`, `drop`, `set_switch`, `field_check`; Modular Ship Assembly `begin_weld` (declared by Interaction, registered by Assembly), `begin_seam_cut`, `install_module` and the `SYSTEM`-only completions `weld` / `seam_cut` (registry: `assembly_commands`; there is no `remove_module` — it is reserved and unregistered, and V8 salvage is the only removal); Suit `equip_tool` (its only type); Web Map & Transit `pod_hop`, `berth`, `unberth` and the `SYSTEM`-only `pod_arrive`, `pod_settle`, `berth_step`, `web_reconcile` (registry: `web_commands`). `interact` is an input action, not a command type, and `use_item` has no owner and is not a command *(Amended 2026-10-27 — consistency pass, routed from interaction-system, suit-and-equipment, modular-ship-assembly and web-map-and-transit)*). What the stick is doing *right now* is an intent: intents are commands too, but a type may declare `coalesce = LATEST_PER_ACTOR_PER_TICK` — coalescing happens at admission over the unfrozen queue, keyed `(type, actor, issuer_peer)`, the older command becoming `Superseded` — and the input adapter sends one only when the quantised value changes — a few per second, never one per tick. Edge-triggered inputs (press, release, confirm) must declare `coalesce = NONE` or taps are lost. Movement integration runs inside the sim: Body's `body.integrate` hook (divisor 1, P3) reads the current intent and integrates ship-local kinematics (CR-13), so a move intent takes effect one tick after it is submitted, like every command; there is no physics-side integration at MVP, and position ownership is settled (Body owns it; the Controller owns intent and facing) *(Amended 2026-10-27 — design review)*. Under `STRICT_DEBUG` every command is round-tripped through serialization before dispatch, even locally; one that cannot survive is a violation (CR-19). **Submit is fire-and-forget and never calls back**: `submit()` returns nothing and invokes no callback, handler or subscriber, so it is safe to call from any handler, hook or result handler; its only outcome is one result record appended to the kernel's result buffer (CR-5), delivered at the next flush and identified by `result_id` — a remote issuer could never get a synchronous answer, so the local one doesn't either *(Amended 2026-10-27 — design review)*.

**Payload whitelist** *(Amended 2026-10-27 — design review)*. 'Plain' is a recursive `Variant.Type` whitelist checked at admission: `NIL`, `BOOL`, `INT`, `FLOAT` (finite only — `NaN` and `±inf` are `MALFORMED`), `STRING`, `STRING_NAME`, `VECTOR2`, `VECTOR2I`, the `Packed{Byte,Int32,Int64,Float32,Float64,String,Vector2}Array` types, and `ARRAY`/`DICTIONARY` of the same, to a depth cap `PAYLOAD_MAX_DEPTH` = 8 (which also rejects a self-containing container). Dictionary keys must be `INT`, `STRING` or `STRING_NAME` and **all keys of one dictionary must share one type** (mixed keys have no canonical order, D.12). Anything else — an `Object`, `NodePath`, `Callable`, `Signal`, `RID`, a non-whitelisted `Variant.Type`, a non-finite float, a depth-9 nesting, mixed dictionary keys — is `MALFORMED`; the size bound is measured as `var_to_bytes(payload, false).size()` after the walk passes. Immediate *acknowledgement* (a tool sound, a hand animation, a linear progress bar starting) is presentation's job and happens in the same frame; the sim confirms on the next tick. The latency bounds are stated once, in Game Feel and D.4.

**CR-5. Command lifecycle and the exactly-one-result guarantee.** Every command reaches exactly one terminal state and emits exactly one result record (identified by `result_id`; delivered to its issuer unless it is `SYSTEM`-origin, see Result identity and delivery below). Stages: *Issued* → *Admission* (kernel state accepts commands; type registered; **origin allowed for the type — known at admission, so rejected there**; queue not full; `seq` not a duplicate — gaps are accepted and counted, not rejected; issuer rate limit; payload plain) → *Queued* → *Authority check* in P2 (origin re-checked as a defence in depth; if the type declares `actor_binding = OWNED_BY_ISSUER`, the binding table says the issuer controls `actor`; age ≤ the type's `max_age_ticks`) → *Validate* (owner's side-effect-free `validate(cmd, read_views)` returns OK or a domain reason) → *Apply* (`apply(cmd, write_scope)`; infallible by contract once validate passed, CR-9) → terminal:

| Terminal | Meaning |
|----------|---------|
| `Applied` | Effects are in state as of tick T (a command dispatched earlier in a tick that then faults is still `Applied`, with `detail.uncommitted = 1`) |
| `Rejected(reason)` | No effect |
| `Dropped(reason)` | Never evaluated: a reload, a shutdown or a fault flushed it — `RELOAD`, `SHUTDOWN`, `FAULTED` (the last added so G5 holds on the defect path). Includes the not-yet-dispatched commands of a faulting tick's batch *(Amended 2026-10-27 — design review)* |
| `Faulted(code)` | Evaluated, and its `validate` or `apply` (or a mutator it called) reported a fault through the fault channel (CR-19): effects may be partial and are unreachable to presentation. Exactly one command per fault — the cause. Distinct from `Rejected` (not 'no effect') and `Dropped` (not 'never evaluated') *(Amended 2026-10-27 — design review)* |
| `Superseded` | Coalesced away by a newer command of a coalescing type |

Kernel reject reasons are a closed set: `NOT_ACCEPTING`, `PAUSED`, `UNKNOWN_TYPE`, `QUEUE_FULL`, `RATE_LIMITED`, `DUPLICATE_SEQ`, `ORIGIN_NOT_ALLOWED`, `ACTOR_NOT_OWNED`, `STALE`, `MALFORMED`, `VALIDATION_FAILED(domain_code)` — domain codes are namespaced and owned by the registering system (Interaction's set, e.g. `OUT_OF_RANGE`, `INVALID_TARGET`, `PRECONDITION`, `BUSY`, is its GDD's). The result record carries `result_id`, `issuer_peer`, `origin`, `seq`, `ok`, `reason`, `subject` (the target the rejection refers to), an optional `detail` dictionary of numbers, and `tick` — **never display strings** *(Amended 2026-10-27 — design review: `result_id` and `origin` added)*. Presentation maps reasons to sound, shake or tooltip. **Reason codes are computed from true state and the kernel never filters them.** That is the whole of the kernel's claim. Whether, when and how cheaply a reason reaches the player is *not* the kernel's: Interaction, Sanity and the HUD own it and must obey Pillar 4's cost rule (a check costs time, risk or trust) — for example surfacing a `PRECONDITION` only after channel time has been spent, or only through diegetic feedback rather than an instant tooltip. *Design test (CD-GDD-ALIGN):* if a rejection lets the player falsify a hallucination at zero time, risk or trust cost, the presentation of that rejection is wrong — not the kernel. A command *aborted mid-channel* (power drops during a cut) is reported by the channel owner through state change, not through the command result. The kernel never retries.

**Result identity and delivery** *(Amended 2026-10-27 — design review)*. A result is identified by `result_id` (the command's `submission_id`). The issuer correlates by `(issuer_peer, origin, seq)`, which is unique among results **except** `DUPLICATE_SEQ` rejections, which by definition repeat an earlier command's `(issuer_peer, origin, seq)` and are told apart by `result_id` and `reason`. Every terminal result — admission rejections, `Superseded`, P2 results, `Dropped(...)`, `Faulted` — is appended to the kernel's **result buffer** in the order it occurs; `submit()` itself never delivers. The buffer is flushed (a) at P5 of every tick, after the change batch, and (b) by the driver once per rendered frame after that frame's ticks, **in every kernel state** (`BOOTING`, `LOADING`, `PAUSED`, `SAVING`, `FAULTED`, `SHUTTING_DOWN`, and an idle frame with no tick), so `NOT_ACCEPTING`, `PAUSED`, `Dropped(RELOAD|SHUTDOWN|FAULTED)` and every other result always have a delivery point. A flush swaps the buffer out before delivering: whatever a result handler submits (the STALE resubmit of Section E, for example) is admitted normally, and any result it produces lands in the fresh buffer and is delivered at the next flush, never recursively — a handler that resubmits on every rejection costs one result per flush and cannot loop. Results go to the issuing `INPUT_SURFACE`'s result handler and to the diagnostics log. **`SYSTEM`-origin results are never delivered to a subscriber or to the submitting owner** (owners never subscribe, CR-10); they go to the command log and the diagnostics counters only, and an owner that needs the outcome reads state. **Fault semantics (a designer decision, not an implementer detail)**: when the kernel faults, each command already dispatched in the faulting tick whose `apply` completed receives `Applied` with `detail.uncommitted = 1` (its effects are in the live blocks although P4 never ran); the faulting command receives `Faulted(code)`; every not-yet-dispatched batch command and every pending command receives `Dropped(FAULTED)`; all are buffered at the fault transition and delivered at the next frame flush.

**CR-6. Registration at boot, then frozen.** Block, command-type, hook and diagnostics-channel registration are legal only in `BOOTING` *(Amended 2026-10-27 — consistency pass, routed from debug-overlay-true-values (E-DO-38))*; after `BOOTING → LOADING` the registries are immutable until shutdown. Registration is an explicit declaration by the composition root, not discovery via the scene tree. Duplicate IDs, unknown types, missing owners and hook cycles fail boot loudly in every build. A command type registered without `allowed_origins`, `actor_binding`, `coalesce` or `max_age_ticks` (**no silent defaults**: an omitted `actor_binding` must never mean 'no ownership check'), a block registered without `class`, `gameplay`, `repl_hint` or `persist`, a type whose `writes_blocks` names an unregistered block, and an `allowed_when_paused` type whose `writes_blocks` names any `gameplay = true` block likewise fail boot (`BOOTING → FAULTED`) naming the registration. *(Amended 2026-10-27 — design review)*

**CR-7. Authority model (behaviour).** The host is the sole authority: only a `HOST` kernel ticks and applies; a `MIRROR` never applies. Each command type's owner declares `allowed_origins ⊆ {PLAYER, SYSTEM}` and `actor_binding ∈ {NONE, OWNED_BY_ISSUER}` — both mandatory (CR-6) — and `allowed_origins` is checked at admission, with a P2 re-check as defence in depth. *(Amended 2026-10-27 — design review)* `SYSTEM` commands never arrive from a network; remote ingress always stamps `PLAYER`. The kernel holds a **binding table** — `peer_id → PlayerId` and `PlayerId → {controlled entity IDs}` — as identity data, not domain state; it is mutated only through a host-only API called by the session owner (a boot step in MVP; Co-op Session in VS-B) and is not saved, since sessions rebuild it; Body persists `seat`, and the binding table may be rebuilt from Body's `seat` field *(Amended 2026-10-27 — consistency pass, routed from ship-body-and-interior-physics)*. *(Alternative: Player Controller owns the binding as a block — rejected because the kernel could then not authority-check without calling a domain system. → ADR.)* **Single-player is not a special case**: local input is `PLAYER`-origin peer 1 (registry: `HOST_PEER_ID` = 1) acting on an entity peer 1 is bound to; the authority stage runs on every command from day one, so TD-FEASIBILITY's "authority discipline lapsing" risk is structural, not disciplinary. The kernel checks *who*; owners validate *whether the world allows it*; the kernel encodes no game rules. For friendly harm the kernel checks only issuer→actor ownership; the "attacker below the sanity threshold" gate is Interaction's `validate` calling Sanity's query on the actor's authoritative sanity level (a `SIM` block), never on anyone's perception.

**CR-8. State-block registry contract.** An owner registers: `block_id` (unique, namespaced, e.g. `graph.state`); `owner`; `schema_version` (bumped on any serialized-shape change); `class` ∈ {`SIM`, `PERCEPTION_OUT`} (CR-12); `persist` (false = derived, rebuilt after load) and, when true, `persist_scope` ∈ {`WORLD`, `PROFILE`} — `WORLD` blocks live in the world snapshot and roll back on `request_restore`; `PROFILE` blocks (decoded rules, lore, scars: Pillar 5's "never knowledge") live outside it and are never rolled back by a world restore; `scope` ∈ {`SHARED`, `PER_PLAYER` keyed by PlayerId}; `gameplay` (bool, mandatory: true when a gameplay verb can change the block; false only for settings, menu and save-request state — the CR-16 paused-write test) and `interpolated` (bool, default false: when true the kernel calls the owner's `commit_baseline()` at P4 so the previous/current pair rolls exactly once per tick, and after a restore or an owner-declared teleport/reset the owner calls `snap_baseline(key)` so presentation never interpolates across a discontinuity) *(Amended 2026-10-27 — design review)*; `repl_hint` ∈ {`HOST_ONLY`, `SHARED_SUMMARY`, `OWNER_PRIVATE`} — mandatory now though unused until VS-B, so no block ever ships without the decision; `snapshot()` (plain data, canonical state only, deterministic ordering, entity references by stable ID, no derived caches; **returns a deep copy** — `duplicate_deep()` for Dictionary/Array, `duplicate()` for Packed arrays, which GDScript passes by reference — never a reference into live state); `restore(data, stored_version)` (whole-block replace; **copies in** and never retains a reference to `data`, so two restores from one payload cannot alias; the owner migrates from `stored_version`; an unsupported version is a reported failure through the fault channel, never a silent default) *(Amended 2026-10-27 — design review)*; `default_state()` (when a save lacks the block); `post_restore()` (after *all* blocks restore: resolve cross-block IDs, rebuild caches, check invariants); `read_view()` (a getter-only facade or a copy — never a live container, CR-12); optionally `init_world(world_seed)` (a new-game step, CR-18). Restore order follows declared `restore_after`; a cycle in it, or a reference to an unregistered block, fails boot. *(Amended 2026-10-27 — design review)* Entity IDs are allocated by the owning block from a counter stored inside it; the kernel allocates none. **No global RNG in simulation**: each system draws from a named stream whose counter lives in its block; the kernel supplies a pure derivation helper from `(world_seed, stream_name, counter)`. The kernel's own clock (`kernel.clock`: tick counter + world seed) is its one registered block, class `SIM`, `persist = true` (scope `WORLD`; carried in the snapshot header as `T` and `world_seed`), **never marked dirty and never notifying** (`T` advances every tick; presentation reads it from the batch's `tick` and the read view), and excluded from the D.12 block fold because the hash prefix already covers `T ‖ world_seed`, so `T` is counted once *(Amended 2026-10-27 — design review)* — so a `PRESENTATION` subscriber (Failure & Trail) reads `world_seed` from its read view *(Amended 2026-10-27 — consistency pass, routed from failure-and-trail-system)* — and contains no domain facts. Blocks are typed data objects whose interchange form is plain data per H7, round-tripped through `var_to_bytes(..., false)` / `bytes_to_var` (Save/Load SL-2); a JSON dump is diagnostic only, and any 64-bit value above 2^53 (`world_seed`, `T`, `state_hash`, per-block hashes, RNG counters) crosses it as a `hex64` string (owned by Save/Load; registry: `hex64`), never as a JSON number *(Amended 2026-10-27 — consistency pass, routed from save-load-and-versioned-format (K-3))* (→ ADR for Resource vs RefCounted); every block has a round-trip test. **4.7 gotcha (sourced)**: writing one element of a packed array no longer fires the property setter, so dirty-tracking must be explicit in mutation methods, never in setters.

**CR-9. Write discipline and atomicity.** A block is written only by its owner's mutators, and only inside a `WriteScope` the kernel issues during P2 apply or P3 step; outside those phases a mutator is refused in every build (no write, no dirty key), increments `WRITE_OUTSIDE_SCOPE` and reports a violation (CR-19). *(Amended 2026-10-27 — design review)* **Cross-block commands** (weld, cut, module install, pod hop) call *public mutators* other owners explicitly publish; the kernel guarantees the whole `apply` is atomic against every other command, hook and snapshot, followed by one notification batch. **Failure model: validate-then-apply, no rollback.** `validate` proves everything through read-only queries (for weld, the Graph's pure join-validation query); `apply` is infallible by contract; a failure inside `apply` — reported through the fault channel, never by throwing or asserting (CR-19) — is a defect that moves the kernel to `FAULTED` (C.2). *(Amended 2026-10-27 — design review)* *(Copy-on-write rollback rejected for MVP cost; event sourcing rejected as primary store — the kernel keeps a bounded command log for diagnostics and replay tests only.)* Step hooks affect other systems by (a) a published unconditional mutator (a horror writing a footprint into the Graph's footprint channel) or (b) a `SYSTEM`-origin command processed at T+1 when the target may reject. The kernel enforces *phase*; "only declared callers call declared mutators" is enforced by lint and the control manifest. → ADR

**Owner rule for `SYSTEM`-submitting hooks** *(Amended 2026-10-27 — design review)*. The pending queue is kernel data, not a block, so it is not in a snapshot, and a `SYSTEM` rejection is invisible to hooks (results go to the log only). A hook that submits `SYSTEM` commands (Assembly's `weld` / `seam_cut` completions, Transit's `pod_*`, Horror) must therefore be **restart-safe and rejection-tolerant**: its decision to submit is a function of persisted state, so after a restore (pending queue empty, `Dropped(RELOAD)`) it simply decides again; the completions are idempotent; timeouts are expressed in state (`submit_T + PENDING_TTL_TICKS + 1`), never as 'wait for the result'. A divisor-1 hook must guard re-submission with `has_pending(type, dedupe_key)` (or a `dedupe_key` on `submit_system`), because while the queue is backlogged it would otherwise queue a duplicate every tick. G4 (CR-13) holds only for owners that obey this rule.

**CR-10. Change notification contract.** Notifications are emitted once per tick in P5, after commit, batched per block as `(block_id, tick, change_keys)`; if more than `MAX_DIRTY_KEYS` changed, `change_keys` collapses to `ALL`. **Payloads carry no state**; subscribers fetch through read views, so notifications are identical whether state arrived by command (`HOST`) or by replication (`MIRROR`) and presentation never changes between modes. Subscriber classes are declared at subscribe time:

| Class | May do | Examples |
|-------|--------|----------|
| `PRESENTATION` | Read `SIM` and `PERCEPTION_OUT` views; write only CanvasItem / Material / Light2D / particle / audio nodes | Failure & Trail, Instruments, HUD, Lighting, Perception Filter, Audio |
| `INPUT_SURFACE` | As `PRESENTATION`, plus **submit** commands as the local seat | Player input adapter, Chart Table, menus |
| `PROJECTOR` | Same reads; write engine-side *derived* objects owned by its block owner (physics shapes, bodies, scene content); never writes blocks | Body's Vertical Slice physics shapes (at MVP the Layout's integer footprint rectangles are SIMULATION data read by Body's `LocomotionStep` and the Emitter's segment test; the avatar has no physics body *(Amended 2026-10-27 — consistency pass, routed from ship-section-and-layout-data-model)*); derelict content build |
| `REPLICATION` | Read views marked for replication; send | Co-op adapter (VS-B) |
| `DIAGNOSTIC` | Read everything, including kernel internals | Debug Overlay |
| *(none for SIM)* | An object that **owns a block or a hook** never subscribes; sim-to-sim is ordered step reads or commands. The rule is per subscriber *object*, not per system: Player Controller's input adapter and Interaction's prompt object are separate objects that subscribe as `INPUT_SURFACE` (they own no block and no hook) *(Amended 2026-10-27 — design review)* | — |

Subscriber handlers run with writes disabled. Render `PRESENTATION` gets no submit API; `INPUT_SURFACE` is the one class that may submit, which is how "presentation never writes simulation" coexists with menus that issue commands. *(The `INPUT_SURFACE` and `PROJECTOR` readings of the TD rule are provisional pending a technical-director ruling — Open Questions.)* **Sim never calls presentation**: the flow is always state → notification → presentation. Horror light disturbance and Attention flicker are state that Lighting reads, not calls into Lighting. There are two consumer channels: true values (Debug Overlay only) and filtered values (the Perception Filter reads true state and publishes what a client perceives; presentation nodes read the filtered channel). The kernel exposes `tick_alpha` for render interpolation; owners of moving state expose previous and current committed values in their read views. → ADR for transport (signals vs registry). **Catch-up delivery** *(Amended 2026-10-27 — design review; ratified 2026-10-27 — user ruling (design-review decisions), R-12, Open Question 21 resolved)* *(Amended 2026-10-27 — user rulings)*: in a frame that runs more than one tick, `PRESENTATION`, `PROJECTOR` and `DIAGNOSTIC` batches are delivered once, after the frame's last tick, with `tick` = that tick and `change_keys` = the union of the frame's ticks (collapsing to `ALL` past `MAX_DIRTY_KEYS`), because presentation only ever reads the last committed state and N intermediate batches are wasted work; `INPUT_SURFACE`, `REPLICATION` and control-plane callers still receive every tick's batch, and the result buffer is flushed every tick. Ticks stay atomic (G6); only the delivery of a presentation batch is merged.

**CR-11. Time model for presentation.** Presentation runs at render rate and reads last-committed state. It never causes a tick; pausing presentation effects (reduced motion) never pauses the sim.

**CR-12. Perception isolation, enforced by block class.** `SIM` blocks are readable by simulation code and presentation. `PERCEPTION_OUT` blocks (Sanity's per-player "what lies to show" output) are *write-only to simulation*: no sim code — including the owner's own hooks — obtains a read view; presentation and the replication adapter do. Sanity's drift and the friendly-harm gate read the sanity *level* (`SIM`), never the perception block. A sim-side read of a `PERCEPTION_OUT` view is refused in every build: it returns an empty view, increments `PERCEPTION_READ_BLOCKED` and reports a violation (CR-19). *(Amended 2026-10-27 — design review)* Perception state is `persist = false` by default (rebuilt from the sanity level and the persisted `sanity.ledger`) *(Amended 2026-10-27 — consistency pass, routed from sanity-and-hallucination-rules (C19))* and `OWNER_PRIVATE` in VS-B.

**Read views are getter-only facades or copies, and the guarantee is 'structural plus tripwire'** *(Amended 2026-10-27 — design review)*. GDScript has no const references: a `Dictionary`, `Array` or Packed array returned from a view is a live container any reader could write to. A read view therefore returns either a facade exposing getters only (indexed access into the owner's storage, for large blocks such as the Graph) or a copy (`duplicate_deep()` / `duplicate()`, for small blocks) — never the owner's live container. What the kernel enforces *structurally* is the issuance surface: `WriteScope` exists only in P2/P3, `PRESENTATION` and `PROJECTOR` receive no submit handle, and owners register no subscription. What it can only *detect* is a reader that mutates a container it should not hold: under `STRICT_DEBUG` the kernel hashes the `SIM` blocks (uncached, so a write that bypassed the dirty bit is seen) around P5 and around each `validate`, and a changed hash is a `SIM_WRITE_TRIPWIRE` violation naming the block. H3/H4 are thus enforced by structure, lint and tripwire together, not by structure alone.

**CR-13. Determinism and ordering guarantees** (`HOST` mode, same build and platform). **G1 Order**: commands apply in ascending `(queued_tick, host_order)`; in single-player that is submission order. *Carve-out (paused service cycle, CR-2)*: commits there are ordered by the same key but at the frozen `T`. *(Amended 2026-10-27 — design review)* **G2 Single timeline**: every command applies at exactly one tick (a paused-cycle commit applies at the current, frozen `T`; running-tick commands satisfy `apply_tick ≥ queued_tick + 1`). *(Amended 2026-10-27 — design review)* **G3 Replay**: from an initial snapshot, the same `PLAYER` command stream, the same *recorded physics observations* and the same **control-plane request log** (each request with the boundary at which it was honoured, including any paused cycle's `host_order` keys) yield identical block state at tick N (canonical snapshot hash). *(Amended 2026-10-27 — design review)* **G4 Save equivalence**: snapshot at T, restore, continue ≡ uninterrupted play for `persist` blocks (hash-compared) — the key regression test for CR-8. *Precondition*: every `SYSTEM`-submitting hook obeys the CR-9 owner rule (the pending queue is not saved, so a `SYSTEM` command queued at tick T's P3 is absent after a restore at T; a restart-safe hook resubmits from state). *(Amended 2026-10-27 — design review)* **G5** exactly-one-result (CR-5). **G6 Atomic ticks** (CR-2). Physics-derived facts (positions after collision, contacts, raycasts) are *inputs* from the engine: Godot Physics 2D makes no determinism claim, so G3 either records and replays them or excludes physics-coupled blocks. This is a stated limit, not a defect; host-authoritative co-op needs host truth, not cross-machine lockstep. In the MVP no block is physics-coupled: Body's `body.integrate` hook integrates ship-local integer kinematics and samples nothing (the avatar has no physics body), so G3 needs no recorded observations and Open Question 5 is moot for the MVP *(Amended 2026-10-27 — consistency pass, routed from ship-body-and-interior-physics (BDY-3))*. → ADR

**CR-14. Hard rules** — each becomes a lint, a test, or a control-manifest line. **H1** No domain state in the kernel (kernel-owned data is exactly: `kernel.clock`, the command queue, the registries, the binding tables, the command log, kernel state, diagnostics). **H2** No kernel-defined domain commands; its control plane (CR-15) is a host-local API, not commands. **H3** One owner per block; writes only via owner mutators inside a `WriteScope`. **H4** Presentation never writes simulation; render presentation has no submit API. **H5** No simulation system reads perception state. **H6** Peer identity on every command, kernel-stamped, never payload-borne; a command constructor without `issuer_peer` must not exist. **H7** Everything crossing the kernel boundary is plain data. **H8** No networking code in MVP: the only ingress is local input, the only egress local presentation. **H9** Simulation never reads wall-clock or global RNG. **H10** Kernel logic is scene-tree independent — runs headless, testable without a scene; a `Kernel.step()` call advances the sim synchronously in tests. Autoload vs node → ADR; if an autoload exists it is a thin holder of an instance that code receives as a parameter, so tests never share global state.

**CR-15. Control plane** (host-local, not commands): `request_pause`, `request_resume`, `request_snapshot`, `request_restore`, `request_shutdown`. Callers: Save/Load, the pause/Chart Table UI (host-local call), boot code. **Timing** *(Amended 2026-10-27 — design review)*: a request is recorded when made — from any phase, from a hook, from a P5 handler, or from outside a tick (a UI call between frames) — and served at the **next boundary**, where a boundary is the P6 of a tick or the driver's per-frame boundary service (run before any tick of the frame and, while `PAUSED`, every frame), whichever comes first; the call itself never changes state. `request_shutdown` is accepted from **every state except `SHUTTING_DOWN`** (including `BOOTING`, `LOADING` and `SAVING`; in those it is served at the boundary that follows the atomic step). Requests reaching the same boundary are applied in arrival order, never coalesced: a `request_pause` then a `request_resume` on one boundary leaves the kernel `RUNNING` with no paused service cycle run; a caller that needs a definite state re-issues the state it wants (Chart Table CT-4) *(Amended 2026-10-27 — consistency pass, routed from chart-table-web-map-and-menus (ASK-CT-9))*. **`request_restore(payload, expected_state_hash = none)`** (K-4): when an expected hash is given, the kernel recomputes `state_hash(PERSIST, T)` (D.12) after the last `post_restore()`, inside `LOADING` and before the first `RUNNING` tick, and reports `{T, computed_hash, match}` to the requester; Save/Load derives its EXACT / REBASED / mismatch verdict from it (SL-12). A mismatch is **not** a `FAULTED` transition — release plays on; policy is the requester's. Save/Load does not use restore-into-`PAUSED` for this window *(Amended 2026-10-27 — consistency pass, routed from save-load-and-versioned-format (K-4))*. **Control-plane read access:** a control-plane caller is not one of the CR-10 subscriber classes; Save/Load (the one such caller at MVP) may read `kernel.clock`, the Controller's per-seat `loco_state`, the Graph's `read_view.failures()` and an optional Attention `SIM` read view, and receives end-of-tick notifications, all read in the tick boundary in which it issues a request; it never reads `PERCEPTION_OUT`, never submits commands and never holds a `WriteScope` *(Amended 2026-10-27 — consistency pass, routed from save-load-and-versioned-format (SL-13))*. In VS-B a guest's pause or save *request* is a command defined by Session or Save/Load, validated on the host, which then calls the control API.

**CR-16. Pause semantics.** `PAUSED` stops the tick but not rendering. While paused, submit accepts only types flagged `allowed_when_paused` by their owner, and **only non-diegetic actions may carry the flag** (save, settings, resume, menu navigation) — no gameplay verb that changes `SIM` state is allowed while paused, so a solo player cannot equip, repair or re-route with time stopped mid-tell (Dread Before Chaos), and solo pause behaves like co-op's overlay-only pause; a paused-allowed command may write only blocks registered `gameplay = false` **and** named in the type's `writes_blocks` (boot-checked, CR-6; the `WriteScope` issued in the paused cycle carries exactly that set, and a write outside it is refused and counted as `WRITE_OUTSIDE_SCOPE`), never a `SIM` gameplay block *(Amended 2026-10-27 — design review)*; everything else is rejected `PAUSED` immediately, never queued, so there is no burst on resume. Admitted paused-allowed commands are dispatched by a **paused service cycle** that runs P1, P2, P4, P5 and P6 with no P3 and with `T` unchanged, **once per rendered frame while `PAUSED`** (the paused boundary, which also serves control-plane requests), so a save or a menu action takes effect without advancing simulated time. At MVP no command type sets the flag; the cycle is a retained seam that only test fixtures exercise (CR-2). *(Amended 2026-10-27 — design review)* Commands already queued when the pause is honoured are neither dispatched by the service cycle nor rejected: they wait, in order, for the first `RUNNING` tick after resume. **Pause is single-player only**: in co-op a menu cannot stop a shared sim — VS-B treats pause as a UI overlay with the kernel `RUNNING`. The Chart Table GDD must not assume "pick a target" happens while paused. Relationship to the scene tree's pause → ADR.

**CR-17. Bounds and overload behaviour.** At most `MAX_CMDS_PER_TICK` processed per tick, the rest waiting FIFO. `QUEUE_CAPACITY` total and `PER_ISSUER_CAPACITY` per issuer; beyond that `QUEUE_FULL` at admission — never silent drop, never unbounded growth. Catch-up runs at most `MAX_TICKS_PER_FRAME` ticks per frame, then lets simulated time lag rather than spiral (lag above `LAG_FORGIVE_TICKS` is dropped at the end of the frame, D.5); a lag counter is exposed to diagnostics. P3 exceeding `STEP_BUDGET_MS` logs the slowest hooks but the tick completes. A command older than its type's `max_age_ticks` is rejected `STALE`, so a hitch cannot unleash a second of stale intents. At the defaults `STALE` is unreachable from local ingress (the queue can hold a command at most 8 ticks and `T` does not advance while paused or saving); it is a VS-B seam for remote-stamped ticks, guarded locally by a "never stale" invariant test (Section E; ratified 2026-10-27 — user ruling, R-3). *(Amended 2026-10-27 — user rulings)*

**CR-18. Snapshot semantics.** A snapshot is taken only at a tick boundary (P6), covers all `persist` blocks at the same T, and records `(T, per-block schema_version)`. Capture is synchronous and in memory with the tick halted (`SAVING`), and **atomic within a single boundary service — `SAVING` never spans a frame**; file I/O is Save/Load's and off the critical path → ADR. *(Amended 2026-10-27 — design review)* Restore replaces all `WORLD`-scoped persisted blocks atomically and leaves `PROFILE`-scoped blocks untouched (Pillar 5: losing the ship or a body never loses knowledge); partial restore within a scope is unsupported; failure aborts to `FAULTED` with pre-restore state intact where possible. With join-in-progress deferred, the same snapshot/restore contract is VS-B's guest transfer at session start, so it must be complete and cheap. **New game (K-2):** a new game passes through `LOADING`: every block takes `default_state()`, Save/Load's `new_game(world_seed)` sets `world_seed` into `kernel.clock`, then each owner that registered an `init_world(world_seed)` step runs it in `restore_after` order under one `WriteScope`, before `post_restore()`; at MVP the world build is Web Map & Transit's `init_world` (WM-7), which calls the Layout, Graph and Body mutators in its fixed order *(Amended 2026-10-27 — consistency pass, routed from save-load-and-versioned-format (SL-18) and web-map-and-transit)*.

**CR-19. Fault channel, violations and build profiles** *(Amended 2026-10-27 — design review; replaces the earlier 'throws / asserts' model)*. GDScript has no `try`/`catch`: a runtime script error is printed by the engine, aborts the function it occurred in and hands control back to the caller with a default value the caller cannot distinguish from a result; and `assert()` is compiled out of release exports. The kernel therefore **never relies on an exception or an assertion for control flow**, and every behaviour in this document is identical in debug and release unless a clause calls it a `STRICT_DEBUG` extra.
- **(a) Fault channel.** Every owner-supplied callable — `validate`, `apply`, step hooks, `snapshot()`, `restore()`, `post_restore()`, `init_world()`, the mutators they call, and result/subscriber handlers — receives a context object (`ApplyContext`/`WriteScope`, `HookContext`, `SnapshotContext`, `NotifyContext`) and reports failure by calling `ctx.fault(code, detail)` and/or returning a status (`OK` or a fault code). Published mutators take the scope, return a status, and callers propagate it. The kernel checks `ctx.faulted` and the status after **every** such call, before using its result. A fault in `apply`, a mutator, a hook, `snapshot()`, `restore()` or `post_restore()` moves the kernel to `FAULTED`; a fault reported by `validate` does not reject, it faults (a defect); a fault in a P5 handler is recorded and counted but cannot fault the kernel (the tick is committed).
- **(b) Completion sentinel.** The kernel arms `ctx.completed = false` before each call and the callable ends with `return ctx.complete()`. A call that returns without the sentinel (the script aborted on an engine error, or forgot) is `fault(INCOMPLETE)` for `apply`, hooks, `validate` and snapshot/restore, and a recorded `INCOMPLETE` diagnostic, without a fault, for a P5 handler. The sentinel catches a *function that aborted*; it cannot catch an error in a nested helper that the outer function then ignores — which is why mutators also return statuses and callers must propagate them.
- **(c) What cannot be done.** Engine script errors cannot be intercepted. P5 subscriber isolation is therefore **best-effort plus lint**: the kernel calls handlers one at a time from its own loop, so an aborted handler does not stop the loop; the sentinel names the offending subscriber in diagnostics; a lint forbids handlers from calling anything that can write.
- **(d) Violations.** A *violation* (write outside a `WriteScope`, a sim read of `PERCEPTION_OUT`, a hook reaching the `PLAYER` ingress, a payload that passed the size check but fails the round-trip, a `SIM` hash change at the tripwire) is, in every build: the offending action refused, a named diagnostics counter incremented, `push_error` called. Under `STRICT_DEBUG` the kernel additionally calls the injected `violation_handler(code, detail)`; the dev default halts via `assert(false)`, the test default records. No state-machine outcome (`FAULTED`, reject reasons, results) differs between profiles.
- **(e) KernelProfile.** `KernelProfile` ∈ {`STRICT_DEBUG`, `LENIENT_RELEASE`} is injected at construction (H10) and never read from `OS.is_debug_build()` inside the kernel, so one test process can construct a kernel per profile and exercise both branches. `STRICT_DEBUG` enables only the extras: the per-command serialization round-trip (CR-4), the violation handler, the `SIM` tripwire (CR-12) and the counter test seams.

**Velocity rule (gameplay-programmer, adopted as an acceptance criterion).** Adding a new command verb touches at most two files: one handler and one registration line. If the kernel ever makes a feature cost more than that, the layer will be bypassed — which is the exact lapse TD-FEASIBILITY named. Hence: commands are plain data records (no class per verb), state blocks are coarse (one per domain system, not per entity), and replay/undo/rollback/middleware are deferred.

### States and Transitions

**Kernel states**

| State | Meaning | Tick advancing | Accepts submit |
|-------|---------|----------------|----------------|
| `BOOTING` | Registries being populated (CR-6); nothing loaded | No | No (`NOT_ACCEPTING`) |
| `LOADING` | Restoring a snapshot or building new-game state; also entered mid-session for reload, including the MVP death stub (Save/Load). Atomic within one boundary service — it never spans a frame *(Amended 2026-10-27 — design review)* | No | No (`NOT_ACCEPTING`) |
| `RUNNING` | Normal ticking | Yes | Yes |
| `PAUSED` | Single-player pause (CR-16) | No | Only `allowed_when_paused` types |
| `SAVING` | Snapshot capture at a tick boundary; atomic within a single boundary service (never spans a frame), returns to the prior state; control-plane requests made while it is active are queued and applied in arrival order afterwards *(Amended 2026-10-27 — design review)* | No | Queues normally; no tick runs until capture completes |
| `FAULTED` | A fault reported through the fault channel (CR-19) by `apply`, `validate`, a hook, `snapshot()`, `restore()` or `post_restore()`; a restore failure; or a boot failure after registration. Never requested | No | No |
| `SHUTTING_DOWN` | Teardown | No | No |

`FAULTED` exists because CR-9's "apply cannot fail" contract needs somewhere for a reported fault to go other than undefined behaviour. In `FAULTED` the kernel never writes or autosaves over an existing save; a dev build halts with diagnostics, release returns to the menu.

| From | Trigger | To | Notes |
|------|---------|----|-------|

No transition leaves `SAVING` except to its return state or `FAULTED`; a restore requested while `SAVING` is active is queued and served after the capture (the state is atomic within one boundary service); there is no `BOOTING → RUNNING`.

**Per-command states**

| State | Entered when | Next |
|-------|--------------|------|
| `ISSUED` | submit called (`submission_id` stamped) | `ADMITTED` or `REJECTED` |
| `ADMITTED` | passes admission | `QUEUED` |
| `QUEUED` | enqueued | `AUTHORIZING`; or `DROPPED` on flush; or `SUPERSEDED` by a coalescing successor |
| `AUTHORIZING` | reached in P2 | `VALIDATING` or `REJECTED` |
| `VALIDATING` | authority passed | `APPLYING` or `REJECTED` |
| `APPLYING` | validate OK | `APPLIED`, or `FAULTED_CMD` when `apply` reports a fault (the kernel faults too, CR-19) |
| `APPLIED` · `REJECTED(reason)` · `DROPPED(reason)` · `SUPERSEDED` · `FAULTED_CMD(code)` | terminal | exactly one result record appended to the result buffer (CR-5) |

## Formulas

*Scope note.* This is an infrastructure kernel, so every formula below is timing, capacity, ordering or identity math; nothing here is a balance curve. Every numeric default is the proposal from Section C's numeric quantities and is **provisional until the kernel spike** unless marked otherwise. Source column vocabulary: `constant` = compiled into the kernel, changing it is a code change; `data file` = kernel config or registration data, read at boot; `calculated` = derived at runtime. All "ticks" are the integer tick counter `T` of CR-1; all "seconds" are simulated seconds unless prefixed *wall*.

**D.1 Tick duration and duration conversion**

The `tick_duration` formula is defined as:

`tick_duration = 1 / TICK_RATE`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| TICK_RATE | int | 15–120 (default **60**) | constant (set once at project start, CR-1) | Authoritative ticks per simulated second |
| tick_duration | float | 0.00833–0.0667 s | calculated | Simulated seconds advanced by one tick |

**Output Range:** 16.667 ms at the default; 66.7 ms at the gameplay-programmer's hard floor of 15 Hz; 8.33 ms at 120 Hz. Never zero because `TICK_RATE ≥ 15` is a boot assertion. The kernel never multiplies by wall-clock `delta` (H9); `tick_duration` is the only place seconds and ticks meet.
**Example:** `TICK_RATE = 60` → `tick_duration = 1/60 = 0.016667 s`.

The `ticks_for_seconds` formula is defined as:

`ticks_for_seconds(s) = round(s × TICK_RATE)` *(Ratified 2026-10-27 — user ruling (design-review decisions), R-1; rationale: `round` half-up for durations; owners that need a guaranteed-minimum wait use `ceil` and say so)* *(Amended 2026-10-27 — user rulings)*

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| s | float | 0–unbounded | data file (the owning system's tuning) | A designer-facing duration in simulated seconds |
| TICK_RATE | int | 60 | constant | As above |
| ticks_for_seconds | int | 0–unbounded | calculated | The same duration expressed in ticks — the only unit the sim stores |

**Output Range:** 0 for any `s < 1/(2·TICK_RATE)` = 8.3 ms — a duration shorter than half a tick rounds to zero ticks and happens "immediately" on the next tick; owners must not rely on sub-tick durations. Unbounded above; a 64-bit int never overflows in practice (see D.14). Every tuned value stored in ticks is invalidated if `TICK_RATE` changes; the conversion is done once at data-load, never per tick.
**Example:** Attention tell window 10–30 s → `round(10 × 60) = 600` to `round(30 × 60) = 1800` ticks. A hook at divisor 6 sees that window as 100–300 of its own runs.

**D.2 Hook scheduling**

The `hook_runs_this_tick` formula is defined as:

`hook_runs_this_tick(h, T) = (T mod divisor_h) == offset_h`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| T | int | 1–2^63−1 | calculated (kernel.clock) | Current tick number |
| divisor_h | int | 1–`TICK_RATE` (defaults: Graph **6**, Attention **6**, Suit vitals **6**, Sanity drift **12**, Horror **5**, input/physics-adjacent **1**) *(Amended 2026-10-27 — consistency pass, routed from horror-entities)* | data file (hook registration, frozen at boot) | Run every `divisor_h` ticks |
| offset_h | int | 0–divisor_h−1 (default 0) | data file (hook registration) | Phase within the divisor cycle; staggers load |
| hook_runs_this_tick | bool | {false, true} | calculated | Whether hook `h` executes in P3 of tick `T` |

**Output Range:** Boolean. `divisor_h = 0` is a boot failure (division by zero; `BOOTING → FAULTED`), as is `offset_h ≥ divisor_h` or any negative value. `divisor_h = 1` is true every tick.
**Example:** Graph `(6, 0)` runs at T = 6, 12, 18 …; Sanity drift `(12, 0)` at T = 12, 24 …; at T = 12 both run and `after` ordering decides who goes first.

The `effective_hook_rate` formula is defined as:

`effective_hook_rate(h) = TICK_RATE / divisor_h`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| TICK_RATE, divisor_h | int | as above | constant / data file | — |
| effective_hook_rate | float | 1–`TICK_RATE` Hz (1–60 at the default) | calculated | Runs per simulated second |

**Output Range:** 60 Hz at divisor 1 down to 1 Hz at divisor 60 (`TICK_RATE`/`TICK_RATE` at the top of the range). Integer only when `divisor_h` divides `TICK_RATE`; 60 is divisible by 1, 2, 3, 4, 5, 6, 10, 12, 15, 20, 30, 60 — choosing a divisor outside that set is legal but produces a non-integer rate that reads badly in tuning tables.
**Example:** Graph `60/6 = 10 Hz`; Sanity drift `60/12 = 5 Hz` — exactly the CR-1 claims.

The `hooks_running_at` formula (per-tick load) is defined as:

`hooks_running_at(T) = |{ h : hook_runs_this_tick(h, T) }|` and the worst-case tick is `T* = lcm(all divisors) × k` where every zero-offset hook coincides.

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| hooks_running_at | int | (#divisor-1 hooks)–(#all hooks) | calculated | Hooks executing this tick |

**Output Range:** With all offsets 0 and divisors {1, 6, 6, 6, 12} (the kernel's illustrative default set; the registered MVP set also contains `horror.step` at divisor 5, offset 0 (registry: `horror.state`), so with it the all-hooks-coincide tick is lcm(1, 5, 6, 12) = 60, not 12, and Horror's 5 does not divide Graph's 6) *(Amended 2026-10-27 — consistency pass, routed from horror-entities)*, every 12th tick runs all five hooks and ticks 6 mod 12 run four; the P3 cost profile is spiky. Staggering offsets would flatten it, but LS-8's rule that a reader shares its writer's offset pins the registered MVP readers to the Graph's: Attention (`attention.step`, divisor 6, offset 0), Suit (divisor 6, offset 0) and `sanity.drift` (divisor 12, offset 0) all read the Graph same-tick, so the MVP profile stays spiky by design; staggering is reserved for a hook with no same-tick `after` partner (see the `after` caveat in Section E) *(Amended 2026-10-27 — consistency pass, routed from attention-system (C3))*. This is what `STEP_BUDGET_MS` (D.6) is measured against.
**Example:** Defaults, offsets all 0: T = 12 → 5 hooks; T = 6 → 4; T = 7 → 1.

**D.3 Render interpolation**

The `tick_alpha` formula is defined as:

`tick_alpha = clamp(t_since_last_commit / tick_duration, 0, 1)`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| t_since_last_commit | float | 0–unbounded wall-seconds | calculated (by the tick *driver*, not the sim) | Wall time since the last P4 commit; equivalently `acc / TICK_UNITS × tick_duration` from the driver's accumulator after the frame's steps (D.5) *(Amended 2026-10-27 — design review)* |
| tick_duration | float | 0.0167 s | calculated | D.1 |
| tick_alpha | float | 0.0–1.0 | calculated | Fraction of the way from the previous committed state to the current one |

**Output Range:** 0 at the instant of commit, 1 when a full tick has elapsed; clamped at 1 so that during a hitch or catch-up lag presentation holds the latest committed pose rather than extrapolating past it (extrapolation would show the ship doing something the sim has not yet done — a Pillar 1 hazard). The sim never reads this value (H9); only the driver computes it and only `PRESENTATION`/`PROJECTOR` consume it.
**Example:** 7 ms after commit at 60 Hz → `7/16.67 = 0.42`; a position read view exposes `prev + (curr − prev) × 0.42`.

**D.4 Input-to-effect latency**

The `apply_tick` formula is defined as:

`apply_tick(c) = queued_tick_c + 1 + floor(q_pos_c / MAX_CMDS_PER_TICK)`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| queued_tick_c | int | ≤ T | calculated (stamped at enqueue) | Tick during (or after) which the command was admitted |
| q_pos_c | int | 0–QUEUE_CAPACITY−1 | calculated | Position of `c` among pending commands in ordering-key order at the moment of the next P0 freeze |
| MAX_CMDS_PER_TICK | int | 128 | data file | CR-17 per-tick processing cap |
| apply_tick | int | queued_tick+1 – queued_tick+8 | calculated | The one tick at which `c` is dispatched (G2) |

**Output Range:** Minimum `queued_tick + 1` (an empty or lightly loaded queue — the normal case; this is the *simulated-time* bound of CR-1, one tick); maximum `queued_tick + ceil(QUEUE_CAPACITY / MAX_CMDS_PER_TICK) = queued_tick + 8` when the queue is full. A running-tick command never applies at `queued_tick` itself because P0 freezes the pending set before P1; the single exception is the paused service cycle (CR-2), whose commits apply at the frozen `T` (`apply_tick == queued_tick`). *(Amended 2026-10-27 — design review)*
**Example:** Command admitted while T = 1000 with 300 commands ahead of it → `1000 + 1 + floor(300/128) = 1003`.

The `input_to_effect_latency` formula (wall-clock, to the pixel) is defined as: *(Amended 2026-10-27 — design review: the earlier form double-counted the wait for the next tick and left out interpolation)*

`L_first = L_wait + (apply_tick − queued_tick − 1) × tick_duration_wall + L_present`, and `L_full = L_first + tick_duration_wall`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| L_wait | float | 0–`frame_duration` | calculated | Wall time from submit to the frame whose driver step runs tick `queued_tick + 1` — ≈ 0 when the event is handled before that frame's driver `_process`, up to one frame when it arrives after it (or from a P5 handler) |
| (apply_tick − queued_tick − 1) × tick_duration_wall | float | 0–116.7 ms | calculated | Backlog term: 0 for an empty queue (`apply_tick − queued_tick == 1`); 0 wall time for ticks run inside a catch-up frame |
| frame_duration | float | 16.7 ms at 60 fps; 33.3 at 30 fps | calculated (engine) | Render frame period |
| L_present | float | 0–`frame_duration` | calculated | From the P5 commit to the end of the frame that draws it; presentation runs after the driver in the same frame (CR-1a), so this is the rest of that frame, not an additional one |
| tick_duration_wall | float | 16.7 ms | calculated | Interpolation term: presentation draws `prev + (curr − prev) × tick_alpha`, so the first drawn frame shows a fraction of the change and the full committed value is drawn one tick later |
| L_first / L_full | float | see below | calculated | Submit → first changed frame / submit → full committed value drawn (excludes display scan-out) |

**Output Range (60 Hz tick, 60 fps render, driver ahead of presentation within the frame):** **Empty queue: `L_first` < 33.3 ms** (< 16.7 ms of waiting for the tick plus < 16.7 ms to the end of the drawing frame), **`L_full` < 50 ms**. **Backlogged queue:** add `(apply_tick − queued_tick − 1) × 16.7 ms`, up to +116.7 ms at a full queue (`apply_tick − queued_tick == 8`). At 30 fps render the empty-queue `L_first` is < 66.7 ms. Immediate *acknowledgement* (CR-4) is presentation's and is 0 ticks by construction. These are the only latency bounds in this GDD: CR-1's 'within one tick' is the simulated-time component (`apply_tick − queued_tick == 1`), the 33.3 ms figure in Game Feel is `L_first`, and the interpolation term makes `L_full` a tick longer. The engine reference is silent on `_process` ordering between nodes, so the 'same frame' path is verified by the spike.
**Example:** Press at 2 ms into frame k, before the driver's `_process` at 3 ms: the tick runs at ≈ 3 ms, P5 at ≈ 4 ms, the frame is drawn when it ends at 16.7 ms → `L_first` ≈ 14.7 ms (`L_wait` ≈ 1, `L_present` ≈ 13.7), `L_full` ≈ 31 ms. Press at 8 ms (after frame k's driver step) or from a P5 handler at 6 ms: the tick runs in frame k+1 at ≈ 19.7 ms, drawn when that frame ends at 33.3 ms → `L_first` ≈ 25 ms, `L_full` ≈ 42 ms.

**D.5 Catch-up, simulated-time lag and forgiveness** *(Amended 2026-10-27 — design review: integer accumulator owned by the `TickDriver` (CR-1a); forgiveness is part of the formula; the physics callback is not the clock)*

The `ticks_run_this_frame` formula is defined as:

`acc ← acc + delta_us × TICK_RATE`; `ticks_due = floor(acc / TICK_UNITS)`; `ticks_run = min(ticks_due, MAX_TICKS_PER_FRAME)` (fewer if the kernel leaves `RUNNING` inside the loop); `acc ← acc − ticks_run × TICK_UNITS`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| delta_us | int | 0–unbounded µs | injected into the `TickDriver` (the driver node converts the engine's `delta` once) | Wall time of the frame |
| TICK_UNITS | int | 1,000,000 | constant | Accumulator units per tick: the unit is microseconds × `TICK_RATE`, so a tick is exact for every integer `TICK_RATE` |
| acc | int | 0–unbounded | calculated (`TickDriver`) | Un-simulated time; **cleared on every transition into `RUNNING`** |
| ticks_due | int | 0–unbounded | calculated | Ticks that would keep sim time equal to wall time |
| MAX_TICKS_PER_FRAME | int | 1–8 (default **4**) | data file | CR-17 catch-up cap |
| ticks_run | int | 0–4 | calculated | Ticks actually stepped this frame |

**Output Range:** 0 (a frame shorter than a tick) to `MAX_TICKS_PER_FRAME`. Pure integer arithmetic: no float comparison, so no result depends on a fixture landing on a float boundary. The kernel's own `step()` has no accumulator; this lives in the driver, which needs no coupling to Godot's physics step cap.
**Example:** `delta_us = 100,000` at 60 Hz: `acc += 6,000,000` → `ticks_due = 6`, `ticks_run = 4`, `acc = 2,000,000` (2 ticks of lag).

The `lag_ticks` and forgiveness formula is defined as: *(Resolved 2026-10-27 — user ruling (design-review decisions), Open Question 19: `LAG_FORGIVE_TICKS = 0`, option B)* *(Amended 2026-10-27 — user rulings)*

`lag_ticks = floor(acc / TICK_UNITS)` after the frame's ticks; if `lag_ticks > LAG_FORGIVE_TICKS` then `dropped = lag_ticks`, `acc ← acc mod TICK_UNITS` (the sub-tick remainder is kept so `tick_alpha` stays continuous), `lag_ticks ← 0`, the forgive counter and `dropped_ticks_total` increment — **at the end of the frame in which the threshold is exceeded**; `simulated_time_lag_s = lag_ticks × tick_duration`. At the ruled default `LAG_FORGIVE_TICKS = 0` this fires on every frame that ends with at least one whole tick of lag, so **no whole tick of lag ever survives into a later frame and the kernel never fast-forwards**. A non-zero value stays a parametric seam (tests exercise it as a fixture); it is not shipped.

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| lag_ticks | int | 0 after every frame at the default; 0–`LAG_FORGIVE_TICKS` after every frame in general | calculated | Exposed to diagnostics (CR-17); never exceeds the threshold after a frame (pre-forgiveness it can read up to `ticks_due − MAX_TICKS_PER_FRAME`) |
| LAG_FORGIVE_TICKS | int | 0–120 (default **0**, ruled 2026-10-27 — user ruling, Open Question 19) | data file | Lag above this is dropped, not repaid; 0 = every whole tick of lag is dropped |
| simulated_time_lag_s | float | 0 at the default; 0–`LAG_FORGIVE_TICKS` × `tick_duration` in general | calculated | How far the ship's clock is behind the player's |
| dropped_ticks_total | int | 0–unbounded | calculated | Diagnostics only |

**Output Range:** At the default, `lag_ticks == 0` after every frame, so the player never sees fast-forward: a frame that runs more than one tick does so only to cover wall time that elapsed within that one frame (at most `MAX_TICKS_PER_FRAME`), never to repay lag from an earlier frame. Sustained frame times above `MAX_TICKS_PER_FRAME × tick_duration` (66.7 ms) run the sim at `MAX_TICKS_PER_FRAME` ticks per frame — slow motion, no spiral. Since no domain system reads wall time, dropped time is observable only in diagnostics. The earlier text allowed up to 30 ticks of sub-threshold lag to be repaid at up to 4× for up to 10 frames; that allowance is withdrawn. For a fixture with `LAG_FORGIVE_TICKS = N > 0` the most repayment is `N` ticks over `ceil(N / (MAX_TICKS_PER_FRAME − 1))` frames.
**Example (default, hitch):** a 1.000 s hitch: `acc += 60,000,000` → `ticks_run = 4`, `lag_ticks = 56 > 0` → forgiven the same frame: `dropped = 56`, `lag_ticks = 0`, `acc = 0`; the next 16,667 µs frame (`acc = 1,000,020`) runs exactly 1 tick and leaves `acc = 20`.
**Example (default, mid-size hitch, off any tick boundary):** a 152 ms hitch (`delta_us = 152,000`): `acc = 9,120,000` → `ticks_due = 9`, `ticks_run = 4`, `acc = 5,120,000`, `lag_ticks = 5 > 0` → dropped: `dropped = 5`, `acc = 5,120,000 mod 1,000,000 = 120,000`, `lag_ticks = 0`. The next 16,667 µs frame: `acc = 1,120,020` → `ticks_run = 1`, `acc = 120,020`. No frame after the hitch runs more than 1 tick.
**Example (fixture only, `LAG_FORGIVE_TICKS = 30`):** the same 152 ms hitch leaves `lag_ticks = 5 ≤ 30`, kept; following 16,667 µs frames add 1,000,020 units: `acc = 6,120,020` → `ticks_run = 4`, `lag_ticks = 2`; then `acc = 3,120,040` → `ticks_run = 3`, `lag_ticks = 0` — cleared in 2 further frames.

**D.6 Step budget**

The `step_over_budget` formula is defined as:

`step_over_budget(T) = (Σ_h∈running t_hook(h, T)) > STEP_BUDGET_MS`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| t_hook | float | 0–unbounded ms | calculated (diagnostics timer, not visible to the sim) | Wall time one hook took |
| STEP_BUDGET_MS | float | 1–8 (default **4**) | data file | CR-17 logging threshold for P3 — **a threshold, not a cap**; the tick always completes |
| step_over_budget | bool | — | calculated | Logs the slowest hooks when true |

**Output Range:** Boolean. `STEP_BUDGET_MS` is a *per-tick P3 alarm*; the frame-level contract is the next formula. At defaults `4 × 4 ms = 16 ms` of P3 alone would fill a 60 fps frame, so the real target is a typical tick well under 2 ms and 4 ms is the alarm.
**Example:** T = 12 runs five hooks at 1.2 + 0.9 + 0.4 + 0.3 + 0.1 = 2.9 ms → under the 4 ms alarm. A hypothetical regression that takes one hook to 4.5 ms on its own is over budget and logged as the slowest hook (an illustration of the alarm, not a design figure: each system's P3 target is its own GDD's, and the kernel's P3 acceptance target is ≤ 2.0 ms at P99).

The `frame_sim_over_budget` formula is defined as: *(Amended 2026-10-27 — design review)*

`frame_sim_ms = Σ over the frame's ticks of (t_P1 + t_P2 + t_P3 + t_P4 + t_P5) + t_flush + t_boundary`; `frame_sim_over_budget = frame_sim_ms > FRAME_SIM_BUDGET_MS(ticks_run)`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| frame_sim_ms | float | 0–unbounded ms | calculated (diagnostics timer, invisible to the sim) | All simulation work in one rendered frame, including result flush and boundary service |
| FRAME_SIM_BUDGET_MS | float | **4.0** for a frame that runs one tick, **6.0** for a frame that runs `MAX_TICKS_PER_FRAME` ticks (the worst tick, `lcm(1, 5, 6, 12) = 60`, is the one that runs every hook) | data file | Logged threshold, never a cap; **measured on a release export on the minimum-spec reference machine `[reference machine: TBD — Open Question 22]`**, never on a debug build |
| t_P2, t_P5 | float | ms | calculated | Per-phase timings, published in diagnostics so a P2 or P5 overrun is attributable (P2 and P5 previously had no metric) |

**Output Range:** Boolean. The Performance ACs gate on the **maximum** `frame_sim_ms` over whole `lcm` cycles (60 ticks = 1 s), not on a mean or a single tick. Catch-up frames run the cheaper non-`lcm` ticks, which is why 6 ms for four ticks is plausible; P5 is merged per frame in a catch-up frame (CR-10).
**Example:** A 60 fps frame at the `lcm` tick: P1–P2 0.3 ms, P3 2.9 ms, P4–P5 0.4 ms, flush 0.1 ms → 3.7 ms ≤ 4.0, not over budget.

**D.7 Ordering, staleness and the STALE finding**

The `ordering_key` formula is defined as:

`ordering_key(c) = (queued_tick_c, host_order_c)`, compared lexicographically; `host_order` is a kernel-stamped counter incremented on every *admission*, never reused *(Ratified 2026-10-27 — user ruling (design-review decisions), R-2; rationale: Section C names `host_order` but does not say who stamps it)* *(Amended 2026-10-27 — user rulings)*

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| queued_tick_c | int | ≤ T | calculated | Tick stamped at enqueue |
| host_order_c | int | 1–2^63−1 | calculated | Admission sequence number, unique per kernel instance per session |
| ordering_key | tuple(int, int) | — | calculated | G1 total order |

**Output Range:** A strict total order: `host_order` is unique, so no two commands compare equal and no tie-break is ever needed. In single-player it reduces to submission order (G1). The pair rather than `host_order` alone is kept so a VS-B ingress can legitimately stamp an earlier `queued_tick` and still sort deterministically. P1 takes the first `MAX_CMDS_PER_TICK` by this key; overflow keeps its key and position.
**Example:** `(1000, 5817) < (1000, 5818) < (1001, 5816)` — the third was admitted earlier but carries a later `queued_tick` (only possible via a VS-B ingress; impossible locally).

The `is_stale` formula is defined as:

`is_stale(c, T) = (T − queued_tick_c) > max_age_ticks(type_c)`, evaluated at P2 authority check

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| T | int | — | calculated | Dispatch tick |
| queued_tick_c | int | ≤ T | calculated | Enqueue tick |
| max_age_ticks | int | `queue_drain_ticks`–600, i.e. 8–600 at defaults (defaults: intents **30** = 0.5 s, actions **120** = 2 s) *(Amended 2026-10-27 — design review: range made to agree with Tuning Knobs)* | data file (per command type, owner-declared) | Oldest acceptable age |
| is_stale | bool | — | calculated | Rejects `STALE` when true |

**Output Range:** Age at dispatch is `apply_tick − queued_tick ∈ [1, 8]` locally (D.4), because `T` does not advance in `PAUSED` or `SAVING` and a full queue drains in 8 ticks. **Finding: with the defaults `is_stale` is unreachable in HOST mode with local ingress — 8 < 30 < 120.** This is not a bug if the intent is "local commands never go stale; STALE guards a remote ingress", but Section C implies it also guards hitches, which it cannot (hitches stop frames and ticks together; wall time is invisible). *(Ratified 2026-10-27 — user ruling (design-review decisions), R-3: option (a).)* Options considered: **(a, adopted)** keep the predicate; declare the invariant `max_age_ticks(any type) ≥ ceil(QUEUE_CAPACITY / MAX_CMDS_PER_TICK)` as a boot assertion and acceptance test ("a local command is never STALE"); have the VS-B ingress adapter stamp `queued_tick = clamp(issuer_observed_tick, T − max_age − 1, T)` so remote lateness is measurable — which is what the 30/120 values are really for. **(b)** lower defaults so STALE is reachable locally — rejected because a local command that waited 9 ticks in a full queue is still the player's genuine latest input. **(c)** delete STALE from MVP's reason set and reintroduce in VS-B — honest but loses the seam; not adopted. *(Amended 2026-10-27 — user rulings)*
**Example:** Intent queued at T = 1000, queue full → dispatched T = 1008, age 8 ≤ 30 → not stale. VS-B guest intent carrying observed tick 1000, arriving at T = 1040 → age 40 > 30 → `STALE`.

**D.8 Queue admission and rate limit**

The `admitted` formula is defined as:

`admitted(c) = accepts(kernel_state, type_c) ∧ registered(type_c) ∧ origin_allowed(type_c, origin_c) ∧ |queue| < QUEUE_CAPACITY ∧ |queue_issuer(c)| < PER_ISSUER_CAPACITY ∧ seq_c > last_seq(issuer_c, origin_c) ∧ ¬rate_limited(issuer_c) ∧ plain(payload_c) ∧ size(payload_c) ≤ MAX_PAYLOAD`; the first failing term in that order is the reject reason (`NOT_ACCEPTING`/`PAUSED`, `UNKNOWN_TYPE`, `ORIGIN_NOT_ALLOWED`, `QUEUE_FULL`, `QUEUE_FULL`, `DUPLICATE_SEQ`, `RATE_LIMITED`, `MALFORMED`, `MALFORMED`) *(Amended 2026-10-27 — design review: `origin_allowed` added at admission; `plain` before `size` because size is measured after the walk)*

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| QUEUE_CAPACITY | int | 256–4096 (default **1024**) | data file | Total pending commands, all issuers |
| PER_ISSUER_CAPACITY | int | 64–QUEUE_CAPACITY (default **256**) | data file | Pending commands per `(issuer_peer, origin)` |
| last_seq | int | 0–2^63−1 | calculated (per issuer, reset when the issuer's binding is created) | Highest admitted `seq` |
| MAX_PAYLOAD | int | 1–64 KiB (default **4 KiB**) | data file | Serialized payload bound, measured as `var_to_bytes(payload, false).size()` |
| PAYLOAD_MAX_DEPTH | int | 8 | constant | Container nesting cap of the CR-4 whitelist walk |
| admitted | bool | — | calculated | Enters `QUEUED` when true |

**Output Range:** Boolean; the order of terms is normative so the same bad command always gets the same reason (G5 determinism of results). Coalescing (Section E) runs *before* the capacity terms, so a superseding intent never fails `QUEUE_FULL` because of the intent it replaces. Queue memory bound: `QUEUE_CAPACITY × (MAX_PAYLOAD + ~200 B overhead) ≈ 4.2 MiB` worst case. The queue is a head-index array (no `pop_front`), ordered by construction for local admissions, and supersession finds its target through a Dictionary keyed `(type, actor, issuer_peer)` over the unfrozen pending set — both O(1) *(Amended 2026-10-27 — design review)*.
**Example (test-only `QUEUE_CAPACITY = 300`, `PER_ISSUER_CAPACITY = 256`):** the `SYSTEM` issuer at 256 pending, the local player at 43 → 299 pending: the player's next command → admitted (the 300th slot); the Horror hook's next `SYSTEM` command → `QUEUE_FULL` (global, and it is under no per-issuer cap of its own) *(Amended 2026-10-27 — design review: the earlier example's counts did not add up)*.

The `rate_limited` formula is defined as:

`rate_limited(i) = remote(i) ∧ (submits_in_window(i) ≥ REMOTE_RATE_LIMIT × RATE_WINDOW_TICKS / TICK_RATE)`, window measured in ticks `[T − RATE_WINDOW_TICKS, T]`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| remote(i) | bool | always false in MVP (H8) | calculated | Issuer arrived via a network ingress |
| REMOTE_RATE_LIMIT | int | 30–600 per s (default **120/s**) | data file | Admissions per second per remote issuer |
| RATE_WINDOW_TICKS | int | 6–120 (default **60**) | data file | Sliding window length; tick-based because the kernel has no wall clock (H9) |
| rate_limited | bool | — | calculated | Rejects `RATE_LIMITED` when true |

**Output Range:** Boolean; in MVP the predicate is a seam that is always false. At defaults the budget is 120 admissions per 60-tick window — bursts up to 120 pass, sustained input above 2/tick is cut. Because the window is tick-based, during `PAUSED`/`SAVING` the window does not slide and a remote cannot be rate-limited more harshly than 120 per paused period — acceptable since VS-B has no pause.
**Example:** A guest sending 2 intents + 1 tap per frame at 60 fps = 180/s → the 121st in any 1 s window is `RATE_LIMITED`.

The `queue_drain_ticks` formula is defined as:

`queue_drain_ticks = ceil(QUEUE_CAPACITY / MAX_CMDS_PER_TICK)`

**Variables:** as above. `queue_drain_ticks` int, 1–unbounded.
**Output Range:** 8 ticks (133 ms) at defaults — the worst wait for the last-admitted command, and the bound D.7's invariant compares against.
**Example:** `ceil(1024/128) = 8`.

**D.9 Dirty-key collapse**

The `change_keys` formula is defined as:

`change_keys(b, T) = dirty(b, T) if |dirty(b, T)| ≤ MAX_DIRTY_KEYS else ALL`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| dirty(b, T) | set of key | 0–|keys(b)| | calculated (explicit marks in mutators — CR-8's packed-array gotcha) | Keys of block `b` written during P2/P3 of tick `T` |
| MAX_DIRTY_KEYS | int | 32–4096 (default **256**; never below 128 while the Graph is registered, Graph D.10) | data file | Collapse threshold |
| change_keys | set of key ∪ {ALL} | — | calculated | Delivered in P5 as `(block_id, T, change_keys)` |

**Output Range:** A set of at most 256 keys, or the sentinel `ALL`. Collapse is worth it when `|dirty| × c_key > c_full` — the per-key subscriber refresh cost times count exceeds a full-block refresh — so the threshold should sit near `c_full / c_key`; the Graph (largest key volume) sets it, per Interactions row 1. **Example:** A weld dirties 14 Graph keys → delivered as 14 keys; a hull breach cascading through 300 nodes → `ALL`; Failure & Trail does one full re-read.

**D.10 RNG stream derivation**

The `rng_derive` formula is defined as: *(Amended 2026-10-27 — design review: GDScript `int` is signed 64-bit and `>>` is an arithmetic shift, so every shift is a masked logical shift and every constant is written signed)*

`rng_derive(world_seed, stream_name, counter) = mix64( world_seed ⊕ mix64(fnv64(stream_name)) ⊕ (counter × GOLDEN) )`; `unit = lsr(rng_derive, 11) / 2^53`; `rng_int(lo, hi) = lo + floor(unit × (hi − lo + 1))`

with `lsr(x, n) = (x >> n) & ((1 << (64 − n)) − 1)` for 1 ≤ n ≤ 63 (logical shift); `mix64(z)` = the SplitMix64 finaliser: `z = (z ⊕ lsr(z, 30)) × C1; z = (z ⊕ lsr(z, 27)) × C2; return z ⊕ lsr(z, 31)`; `fnv64` = FNV-1a over the UTF-8 bytes of the name, `h = FNV_OFFSET; for each byte: h = (h ⊕ byte) × FNV_PRIME`, **computed once per stream at registration and cached, never per draw**. Constants as GDScript `int` literals (hex shown for reference only — a hex literal above `0x7FFF…` is not a valid `int` literal): `GOLDEN` = 0x9E3779B97F4A7C15 = `-7046029254386353131`; `C1` = 0xBF58476D1CE4E5B9 = `-4658895280553007687`; `C2` = 0x94D049BB133111EB = `-7723592293110705685`; `FNV_OFFSET` = 0xCBF29CE484222325 = `-3750763034362895579`; `FNV_PRIME` = 0x100000001B3 = `1099511628211`. **Integer wrap on multiplication is intended** and relied on; the golden vectors below (several have the top bit set) fail at once on an implementation that does not wrap or that uses an arithmetic shift.

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| world_seed | int (64-bit pattern) | any `int` | data file (kernel.clock block; set at new game, persisted) | Per-world seed; stored as the signed `int` with the same bit pattern as the u64 |
| stream_name | string | registered, e.g. `horror.tell` | data file (owner declares) | Names an independent stream |
| counter | int | 0–2^63−1 | calculated (lives in the owner's block, incremented per draw, persisted with it) | Draw index |
| mix64 | fn | bijective 64-bit → 64-bit, full avalanche | constant (SplitMix64 finaliser; **set-once**, ratified 2026-10-27 — user ruling, R-17 — the kernel ADR may change it only before the first save format ships) | Mixing function |
| rng_derive | int (64-bit pattern) | any `int` | calculated | Deterministic raw value (print as `hex64`) |
| unit | float | [0, 1) | calculated | 53-bit uniform |
| rng_int | int | [lo, hi] | calculated | Uniform integer in an inclusive range; **requires `lo ≤ hi` and `hi − lo + 1 ≤ 2^32`** |

**Output Range:** `unit` is in `[0, 1)` exactly (the top 53 bits divided by 2^53 can never reach 1). `rng_int` is inclusive at both ends; its bias is at most `span / 2^53 ≤ 2^-21` (there is no modulo, so no modulo bias, and the span cap is what keeps it negligible). A call with `lo > hi` or a span above 2^32 is a caller defect: it returns `lo`, increments `RNG_RANGE_VIOLATION` and reports a violation (CR-19). Pure: the same `(seed, name, counter)` always gives the same value regardless of call order or which other streams drew — which is what lets G3 replay and G4 save-equivalence hold with no RNG state outside blocks. A stream's counter restores with its block, so a save mid-tell reproduces the same tell.
**Golden vectors** (computed with an independent 64-bit reference implementation; these are the acceptance values): `fnv64("horror.tell")` = `0xE500B5B58A7689E2`; `mix64(1)` = `0x5692161D100B05E5`; `mix64(0x8000000000000000)` = `0x25C26EA579CEA98A`; with `world_seed = 0x5EED000000002026`: `rng_derive(seed, "horror.tell", 17)` = `0xB2AA94991B52A02E` → `unit ≈ 0.6979153513` → `rng_int(600, 1800) = 600 + floor(0.6979153513 × 1201) = 600 + 838 = 1438` ticks ≈ 24.0 s; `rng_derive(seed, "horror.tell", 0)` = `0x4988DBEFD7F20FF5`; `rng_derive(seed, "graph.failure", 0)` = `0x0CEEC43F97221B55`; with `world_seed = 0xFFFFFFFFFFFFFFFF`: `rng_derive(seed, "horror.tell", 1)` = `0x883EA97FED4A4613`. The `horror.tell` / `rng_int(600, 1800)` usage matches Horror's HE-9 stream use (*Amended 2026-10-27 — consistency pass, routed from horror-entities*).

*Maintenance note:* a 63-bit owner-defined key (for example the Graph's `(step_no, subject_id)`) is a valid `counter` for `rng_derive` *(Amended 2026-10-27 — consistency pass, routed from save-load-and-versioned-format (SL-23))*. **Restore-epoch re-keying** *(Amended 2026-10-27 — user rulings)* (ruling X8): threat draws (Attention, Horror) are re-keyed per restore epoch by their owners, who fold the epoch (owned by Save/Load) into `stream_name` or `counter`; `rng_derive` is unchanged and needs no kernel change. Graph physical-failure draws and persisted counters do not fold the epoch, so they replay exactly; a draw is not steerable by quitting or dying (the epoch is not player-controllable).

**D.11 Snapshot size and capture budget**

The `snapshot_bytes` formula is defined as:

`snapshot_bytes = header_bytes + Σ_{b ∈ persist} (block_header_bytes + canonical_bytes(b))`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| header_bytes | int | ~64 | calculated | `T`, `world_seed`, `TICK_RATE` (ratified 2026-10-27, R-9), block count |

| persist | set | ≤ MAX_BLOCKS (**128** registry cap; **32** expected) | data file | Blocks with `persist = true` |

**Example:** Graph 2,000 nodes × 6 fields × 8 B ≈ 96 KiB; 31 other blocks at ~2 KiB ≈ 62 KiB; headers ≈ 1.6 KiB → ≈ 160 KiB.

The `capture_time_ms` formula is defined as: *(Amended 2026-10-27 — design review: the cost is dominated by the GDScript canonical encoder, not the hash function)*

`capture_time_ms = Σ_{b ∈ persist} ( t_snapshot(b) + t_encode(b) ) + t_hash`; budget `capture_time_ms ≤ SNAPSHOT_BUDGET_MS`; per-block guideline `t_snapshot(b) + t_encode(b) ≤ SNAPSHOT_BUDGET_MS / |persist|`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| t_snapshot(b) | float | ms | calculated (diagnostics timer) | Owner's `snapshot()` wall time, including its deep copy |
| t_encode(b) | float | ms | calculated (diagnostics timer) | The GDScript canonical encoder over the block's Dictionary/Array/scalar fields — budgeted separately because it, not hashing, is the dominant cost; Packed arrays bypass it |
| t_hash | float | ms | calculated | `HashingContext` over the dirty blocks' canonical bytes plus the fold (D.12). **Runs in release builds too** (K-4 verification window and the Save/Load integrity path), not only in debug/test |
| SNAPSHOT_BUDGET_MS | float | 8–33 (default **16.7** = one 60 fps frame) | data file | CR-18 "cheap" target; the visible hitch at autosave |
| capture_time_ms | float | — | calculated | Length of the `SAVING` state in wall time |

**Output Range:** The budget is a diagnostics threshold like `STEP_BUDGET_MS`, not a cap — a snapshot is never truncated. Per-block guideline ≈ `16.7 / 32 ≈ 0.5 ms`. GDScript builds Dictionaries at roughly 0.5–1 M entries/s (unverified, spike), so a 0.5 ms block has a budget of ~250–500 scalar fields; any block larger than that must snapshot as `Packed*Array` copies (memcpy-speed), which is the Graph's design constraint. VS-B reuses this as the guest's initial transfer, so the same budget applies there. *(All numbers provisional until spike.)*
**Example:** 31 small blocks at 0.1 ms (snapshot + encode) + Graph at 3 ms (packed arrays) + hash 1.0 ms (only dirty blocks rehashed) ≈ 7.1 ms → under budget; the same Graph as nested Dictionaries at ~25 ms → over, logged.

**D.12 State hash (G3/G4)**

The `state_hash` formula is defined as: *(Amended 2026-10-27 — design review: two-level hash with per-block cached hashes and length prefixes; scopes made exact)*

`block_hash(b) = H64( canonical_bytes(b) )` — **cached per block and invalidated by the block's dirty bit** (any write in P2/P3 clears it; `restore` clears it)

`state_hash(scope, T) = H64( T ‖ world_seed ‖ ⨁_{b ∈ scope, sorted by block_id} ( len(block_id) ‖ block_id ‖ schema_version ‖ len(canonical_bytes(b)) ‖ block_hash(b) ) )`, where `canonical_bytes` serialises dictionaries with keys sorted bytewise (keys of one type, CR-4), arrays in order, ints as 64-bit little-endian, floats as their IEEE-754 bit pattern with `−0.0 → +0.0` and all NaNs → one canonical NaN, strings as UTF-8 length-prefixed, booleans as one byte, and `Packed*Array` fields as their raw bytes behind an element-type tag and a length (owners keep NaN and `−0.0` out of packed float state — mutators normalise, and a test asserts it)

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| scope | enum | {`PERSIST` (G4), `ALL_SIM` (G3)} | calculated (test chooses) | `PERSIST` = blocks with `persist = true` **and** `persist_scope = WORLD` — never `PROFILE`; `ALL_SIM` = every `SIM` block (`WORLD`, `PROFILE` and non-persisted derived). Both **exclude `kernel.clock`** (its `T` and `world_seed` are the hash prefix, so they are counted once) and **never include `PERCEPTION_OUT`** |
| H64 | fn | 64-bit digest | constant (ratified 2026-10-27 — user ruling, R-17: the first 8 bytes, little-endian, of SHA-256 computed with Godot's `HashingContext`; native speed, no GDScript byte loop; → ADR) | Hash function |
| canonical_bytes | bytes | — | calculated | Byte form identical for equal state regardless of insertion order (Godot `Dictionary` is insertion-ordered, so sorting is mandatory) |
| state_hash | int (64-bit pattern) | any | calculated | Shown by the Debug Overlay (print as `hex64`); compared by G3/G4 tests |

**Output Range:** Uniform over 64 bits; collision probability 2^−64 per comparison, negligible for tests. Equal hashes with unequal state would be a false pass, so G4's test also diffs on mismatch rather than only comparing hashes. Physics-coupled blocks are excluded from `ALL_SIM` in G3 unless physics observations were recorded (CR-13's stated limit). **Cost:** the hash also runs in release (K-4 at every load; the Overlay's cadence in dev), and its cost is dominated by the GDScript `canonical_bytes` encoder, not by `H64`; the per-block cache means a tick that dirtied two blocks re-encodes two blocks, Packed arrays reach `HashingContext` as raw bytes, and the encoder is budgeted separately (`t_encode`, D.11).
**Example:** Snapshot at T = 5000, restore, run to 5600 → `state_hash(PERSIST, 5600)`; uninterrupted run to 5600 → the same value on both sides (shown as `hex64`); any difference names the first differing `block_id` and key. (No value is quoted here: the digest depends on the unfrozen `H64` choice.)

**D.13 Command log coverage**

The `log_coverage_ticks` formula is defined as:

`log_coverage_ticks = COMMAND_LOG_CAPACITY / cmds_per_tick_actual`; worst case `COMMAND_LOG_CAPACITY / MAX_CMDS_PER_TICK`

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| COMMAND_LOG_CAPACITY | int | 256–8192 (default **1024**) | data file | Ring buffer of commands with results (CR-9, diagnostics and replay tests only) |
| cmds_per_tick_actual | float | 0–128 | calculated | Observed admissions per tick |
| log_coverage_ticks | float | ≥ 8 | calculated | How far back the Debug Overlay's "last-N commands" reaches |

**Output Range:** At least 8 ticks (133 ms) at saturation; at a realistic 0.1 commands/tick (~6/s: a few intents and a tap) ≈ 10,240 ticks ≈ 2.8 minutes. Log entries store the command plus its result and `tick`, ≤ `MAX_PAYLOAD + ~100 B` each → ≤ ~4.3 MiB.
**Example:** `1024 / 0.1 = 10,240` ticks ≈ 171 s.

**D.14 Tick counter bound**

The `ticks_to_overflow` formula is defined as:

`ticks_to_overflow = (2^(bits−1) − 1) / TICK_RATE` seconds

**Variables:**
| Variable | Type | Range | Source | Description |
|----------|------|-------|--------|-------------|
| bits | int | 64 (Godot `int`) | constant | Width of `T`, `seq`, `host_order`, counters |
| ticks_to_overflow | float | — | calculated | Simulated seconds before wrap |

**Output Range:** 64-bit → 1.5 × 10^17 s ≈ 4.9 billion years: overflow is impossible and the kernel does no wrap handling; a boot assertion that `T`, `seq` and `host_order` are 64-bit is the whole mitigation. (For contrast, 32-bit signed would wrap after 414 days of continuous play — the reason the width is asserted rather than assumed.)
**Example:** `(2^63 − 1) / 60 ≈ 1.54 × 10^17 s`.

## Edge Cases

Every outcome below is the exact kernel behaviour **as the design currently stands**; the items that fill a gap in Section C (formerly marked *(adopted — decision log 2026-10-25)* or *(proposed)*) were **ratified as written on 2026-10-27 — user ruling (design-review decisions), R-1..R-20, Open Question 18**, and carry no marker any more. *(Amended 2026-10-27 — user rulings)* "Result event" means the single CR-5 result record, identified by `result_id`, correlated by `(issuer_peer, origin, seq)`, appended to the result buffer when the command reaches its terminal state and delivered at the next flush (P5 or the driver's frame boundary) — never during `submit`. *(Amended 2026-10-27 — design review)*

**Submission timing and kernel state**

- **If `submit` is called during P2 or P5 of tick T (or any phase P0–P6)**: the intake queue has been frozen since P0, so the command is admitted into the *unfrozen* pending set with `queued_tick = T` and is eligible no earlier than tick T+1 (`apply_tick ≥ T+1`, D.4). No result event yet; it is `QUEUED`. From a P5 `INPUT_SURFACE` handler this is the normal and intended path (a menu confirming a selection). From P2/P3 only `SYSTEM`-origin submits exist (CR-3/CR-9); see "a hook submits a PLAYER command" below.
- **If `submit` is called while `SAVING`** (reachable only from inside a block's `snapshot()` or another boundary callback, because `SAVING` is atomic within one boundary service): admitted and queued normally with `queued_tick = T` (the tick just captured). The pending queue is kernel data, not a block, so the snapshot never contains it; the command is dispatched at T+1 once the kernel returns to `RUNNING`. If the save is later restored, that command's effects exist in the live world but not in the save — correct, because it applied *after* T.
- **If `submit` is called while `LOADING`, `BOOTING`, `FAULTED` or `SHUTTING_DOWN`**: rejected `NOT_ACCEPTING` at admission; `submit` returns nothing and calls nothing back — the result is appended to the result buffer during the call and delivered at the next flush, which runs at every frame boundary in every kernel state (CR-5), so the rejection always has a delivery point and never waits for a tick. Nothing is queued. *(Amended 2026-10-27 — design review)*
- **If `submit` is called while `PAUSED` with a type not flagged `allowed_when_paused`**: rejected `PAUSED` immediately, never queued (CR-16), so resume produces no burst.
- **If `submit` is called while `PAUSED` with an `allowed_when_paused` type**: *(Ratified 2026-10-27 — user ruling (design-review decisions), R-4; rationale: Section C admits these commands but no tick runs in `PAUSED`, so CR-16 has no dispatch path)*. Rule: while `PAUSED` the driver runs a **paused service cycle** once per render frame consisting of P1, P2, P4, P5, P6 — **no P0 (T does not increment) and no P3 (no hooks)**. Commands dispatch at the current `T` with their ordinary `(queued_tick, host_order)` key; several commits can therefore occur at the same `T`, each logged with its `host_order` so G3 replay reproduces them in order (the control-plane log is part of the replay input, CR-13). The paused boundary runs on every rendered frame while `PAUSED`; no MVP type sets `allowed_when_paused`, so the cycle is exercised only by test fixtures, and a type may carry the flag only if its `writes_blocks` names `gameplay = false` blocks (CR-6, CR-16). *(Amended 2026-10-27 — design review)* The alternative (make every paused action a control-plane call or pure presentation and drop `allowed_when_paused`, the paused cycle and `writes_blocks` from CR-16) was **not adopted**: the paused service cycle is kept as a retained seam exercised only by fixtures (R-4). *(Amended 2026-10-27 — user rulings)*
- **If `request_resume` arrives after a long pause**: the driver's accumulator is cleared on the `PAUSED → RUNNING` transition, so `ticks_due = 0` on the first running frame; a pause never produces catch-up ticks. The same clear happens on **every** transition into `RUNNING` (`LOADING → RUNNING`, `SAVING → RUNNING`; CR-1a), so a load or an autosave is never followed by a burst. *(Amended 2026-10-27 — design review)*
- **If a control-plane request (`request_pause`, `request_snapshot`, `request_restore`, `request_shutdown`, binding change) is made at any time** — between ticks from UI code, inside a P3 hook, or inside a P5 handler: the call only records it; it is served at the **next boundary**, which is the P6 of the current or next tick or the driver's per-frame boundary service, whichever comes first (CR-15). A request made inside a P3 hook or a P5 handler of tick `T` is therefore served at `T`'s P6; one made between frames is served at the start of the next driver frame, before any tick of that frame runs; one made between two steps of a catch-up frame is served at the P6 of the tick that just ran (the driver re-reads the state, CR-1a). Requests at one boundary are applied in arrival order; the second may become an invalid `(state, trigger)` pair and is then ignored and reported to diagnostics. `request_shutdown` is accepted from every state except `SHUTTING_DOWN`. *(Amended 2026-10-27 — design review)*

**Ordering, coalescing and sequence numbers**

- **If two commands target the same actor in one tick**: both dispatch in `ordering_key` order (D.7); the second sees the first's applied effects in its `validate` and `apply` (CR-2). No kernel coalescing unless the type declares it.
- **If a second command of a `coalesce = LATEST_PER_ACTOR_PER_TICK` type arrives for the same `(type, actor, issuer_peer)` while the first is still in the *unfrozen* pending set**: *(Ratified 2026-10-27 — user ruling (design-review decisions), R-5; rationale: Section C does not say where coalescing happens)* *(Amended 2026-10-27 — user rulings)* the earlier one is removed, becomes `SUPERSEDED` and its result is appended to the result buffer immediately (delivered at the next flush); the new one is admitted with its own fresh `host_order` and `queued_tick`. Coalescing runs before the capacity terms of `admitted` (D.8), so it never fails `QUEUE_FULL` because of the command it replaces. The key includes `issuer_peer` because admission precedes the authority check — without it a remote issuer could supersede another seat's intent. A P1 batch therefore never contains two commands of the same coalesce key.
- **If the earlier intent is already in the current tick's P1 batch when the newer one arrives**: *frozen* means exactly 'in this tick's P1 batch' and nothing wider. A batch member is not superseded — it applies at T, the newer applies at T+1; the batch is immutable after P1. A command that was in the P0 candidate set but fell into the P1 **overflow** (beyond `MAX_CMDS_PER_TICK`) has returned to the unfrozen pending set and **is** supersedable, so a newer same-key intent arriving before the next P0 supersedes it and the next batch never holds two commands of one coalesce key. *(Amended 2026-10-27 — design review)*
- **If a `coalesce = NONE` tap (e.g. `begin_weld`) is queued between two intents of the same key** (`[intent A, tap, intent B]`): A is superseded; the queue becomes `[tap, intent B]` in `host_order`. B keeps its own (newer) `host_order` and never inherits A's position — the kernel never reorders. The tap therefore validates against the movement state *before* B, which is the issuer's actual chronology.
- **If a `NONE` type is submitted twice in one inter-tick window**: both are queued and both apply; losing one would lose a tap (CR-4). Idempotence of a double tap is the owner's `validate` (`BUSY`).
- **If `seq` is less than or equal to the issuer's `last_seq` for its `(issuer_peer, origin)`**: rejected `DUPLICATE_SEQ`; nothing else changes (replays and reorders are both caught by this one rule). The rejection's result shares the original command's `(issuer_peer, origin, seq)` and is told apart by its own `result_id` and its reason (CR-5). *(Amended 2026-10-27 — design review)*
- **If `seq` skips values (gap)**: *(Ratified 2026-10-27 — user ruling (design-review decisions), R-6; rationale: CR-5 has `DUPLICATE_SEQ` but no gap reason)* *(Amended 2026-10-27 — user rulings)* admitted; `last_seq` jumps forward; the gap size is added to a per-issuer diagnostics counter. Gaps are expected under VS-B loss and the kernel never retries, so rejecting them would strand every later command.
- **If an issuer's binding is (re)created (new session, VS-B reconnect)**: that issuer's `last_seq` resets to 0 and its rate window clears; `host_order` never resets within a session.
- **If a `SYSTEM`-origin command is submitted by a hook or handler**: `issuer_peer = 1` (host), `origin = SYSTEM`, and `seq` is drawn from a kernel-held `SYSTEM` sequence (owners never manage it); its result goes to the command log and the diagnostics counters only — **never to the submitting owner or any subscriber** (CR-5, CR-10) *(Amended 2026-10-27 — design review; the earlier 'delivered to the owner at the next P5' text contradicted 'owners never subscribe'; ratified 2026-10-27 — user ruling, R-7)* *(Amended 2026-10-27 — user rulings)*. Seq spaces are per `(issuer_peer, origin)` so a SYSTEM command can never collide with the host player's own `seq`. A hook never receives a `SYSTEM` result, so an owner that needs the outcome reads it from state — e.g. Assembly's `NOT_TAKEN` at `submit_T + PENDING_TTL_TICKS + 1` — and obeys the CR-9 owner rule (restart-safe, rejection-tolerant, `has_pending` before resubmitting). `SYSTEM` commands count toward `PER_ISSUER_CAPACITY` in their own `(1, SYSTEM)` bucket (the `SYSTEM` issuer of D.8), separate from the host player's. The command log records them like any command, but a replay test injects only `PLAYER` commands and lets the hooks regenerate their `SYSTEM` submissions *(Amended 2026-10-27 — consistency pass, routed from modular-ship-assembly (K1))*.

**Dispatch and apply**

- **If a command's `actor` was destroyed earlier in the same tick (by an earlier command or, for a hook-submitted command, by last tick's P3)**: the kernel's authority check consults only the binding table, which is identity data and is not touched by domain destruction, so authority *passes* if the issuer is still bound to that entity ID; the owner's `validate` then fails on a missing entity and the result is `VALIDATION_FAILED(domain_code)` (Interaction's `INVALID_TARGET` or equivalent). The kernel never checks entity existence (H1). If the session owner has also unbound the actor (honoured at P6, so earliest next tick), the result is `ACTOR_NOT_OWNED` instead.
- **If a type declares `actor_binding = OWNED_BY_ISSUER` and the command's `actor` is none**: `ACTOR_NOT_OWNED`.
- **If a type declares `allowed_origins = {SYSTEM}` and a `PLAYER` command arrives for it**: `ORIGIN_NOT_ALLOWED` **at admission** — the origin is stamped at ingress and the type is registered, so it is known when `submit` runs (D.8). The P2 re-check stays as defence in depth and is reachable only through a test ingress that bypasses admission. *(Amended 2026-10-27 — design review)*
- **If `validate` passes but a published mutator called inside `apply` would violate another block's invariant** (e.g. a weld whose join query said OK but the Graph's mutator refuses): the mutator reports the violation through the fault channel (`scope.fault(code, detail)` and a non-`OK` status, CR-19) — it does not throw or assert. The kernel checks the status after the mutator returns and after `apply` returns, and: stops evaluating this `apply` (its remaining statements are the owner's to skip by propagating the status); does not reach P4 (nothing is committed, notified, logged as applied or saveable); leaves writes already made by this `apply` in the live blocks (no rollback), unreachable to presentation because P5 never runs; transitions `RUNNING → FAULTED`; buffers `Faulted(code)` for the failing command, `Applied` with `detail.uncommitted = 1` for every command already dispatched in this tick, and `Dropped(FAULTED)` for every undispatched batch command and every pending command (CR-5); records `(T, type, issuer, host_order, block_id, code)` in diagnostics. An `apply` that returns without the completion sentinel (aborted by an engine script error) is the same fault with code `INCOMPLETE`. The dev build halts with the diagnostic; release returns to the menu; no autosave is written (FAULTED rule). Identical in both `KernelProfile`s. *(Amended 2026-10-27 — design review)*
- **If `validate` reports a fault, returns without the sentinel, or has a side effect**: a reported fault or a missing sentinel is a defect and moves the kernel to `FAULTED` exactly as an apply fault (the command receives `Faulted(code)`); it is not a rejection. Side effects in `validate` are not detectable at run time by the kernel in release; under `STRICT_DEBUG` the `SIM` hash tripwire (CR-12) detects them, and in all builds they are a lint/test obligation on the owner. *(Amended 2026-10-27 — design review)*
- **If a handler calls a mutator outside a `WriteScope`** (from a notification handler, from presentation, from `validate`): the write is refused in every build, no dirty key is marked, the `WRITE_OUTSIDE_SCOPE` counter increments and a violation is reported (CR-19); under `STRICT_DEBUG` the injected `violation_handler` also runs. The kernel state does not change — this is not an apply fault because no `apply` is running. *(Amended 2026-10-27 — design review)*

**Hooks**

- **If hook `after` lists contain a cycle or reference an unknown `hook_id`**: `BOOTING → FAULTED` with the cycle path (or the unknown ID and its referrer) in diagnostics, in every build (CR-6). No partial order is ever used.
- **If two hooks have no `after` relation**: ordered by registration index, then `hook_id` (CR-3); the resolved order is printed by the Debug Overlay and is identical on every boot with the same composition root.
- **If hook A declares `after: B` but their `(divisor, offset)` mean they never run in the same tick** (fixture: a hook at `(6, 4)` after Graph `(6, 0)` — not Suit's registration, which is divisor 6, offset 0 and co-runs with the Graph *(Amended 2026-10-27 — consistency pass, routed from suit-and-equipment)*; and the real registered pair `horror.step` `(5, 0)` after `attention.step` `(6, 0)`): the order is still well-defined on the ticks where both run, and A reads B's state as committed by B's most recent run. *(Ratified 2026-10-27 — user ruling (design-review decisions), R-8)* *(Amended 2026-10-27 — user rulings)*: boot emits a **warning** (not a failure) listing the pair **only when the `after` edge does not declare `tolerates_stale: true`** (CR-3), because staggering and unequal divisors are legitimate when a reader tolerates up-to-`divisor`-tick-old data and the owner says so; a declared edge boots silently, so the warning is not trained away. If the owner needs same-tick data, offsets must match and the divisors must be equal or one divide the other. *(Amended 2026-10-27 — design review)*
- **If a hook submits a `PLAYER`-origin command**: there is no API path — hooks receive only `submit_system()`, which stamps `SYSTEM` (H6). If a hook nevertheless reaches the local input ingress while the kernel's phase is P2 or P3, the command is rejected `ORIGIN_NOT_ALLOWED` at admission in every build and the `HOOK_PLAYER_SUBMIT` counter increments (a violation, CR-19; `STRICT_DEBUG` also runs the violation handler). It is never silently re-stamped `SYSTEM`. *(Amended 2026-10-27 — design review)*
- **If two or more hooks share a `(divisor, offset)`**: this is normal (Graph, Attention and Suit all at `(6, 0)` by default); they run in the same tick in resolved order. The only cost is a load spike every `divisor` ticks (D.2 `hooks_running_at`).
- **If a hook registers `divisor = 0`, `offset < 0`, or `offset ≥ divisor`**: `BOOTING → FAULTED` naming the hook.
- **If P3 exceeds `STEP_BUDGET_MS`**: the tick completes in full; the per-hook timings for that tick are logged with the slowest first (CR-17). Nothing is skipped or deferred.
- **If a hook reports a fault, returns without the completion sentinel, or trips a step invariant it checks itself**: `RUNNING → FAULTED` exactly as an apply fault (CR-19): P4 and P5 do not run, commands dispatched in P2 of this tick are `Applied` with `detail.uncommitted = 1`, and the pending queue gets `Dropped(FAULTED)` (there is no faulting *command*, so no `Faulted` result). An engine script error inside a hook can only be caught by the sentinel, never intercepted. *(Amended 2026-10-27 — design review)*

**Time and overload**

- **If the catch-up cap `MAX_TICKS_PER_FRAME` is reached on one frame**: `ticks_run = 4`, `lag_ticks` reads `ticks_due − 4` at the end of the loop and, at the default `LAG_FORGIVE_TICKS = 0`, is dropped in the same frame (D.5); the counter is exposed to diagnostics. The sim is correct and merely behind. *(Amended 2026-10-27 — user rulings)*
- **If the cap is reached on consecutive frames** (sustained frame time > 66.7 ms at defaults): the sim runs `MAX_TICKS_PER_FRAME` ticks per frame — slow motion, no spiral, because work per frame is capped. Lag is forgiven at the end of every frame (`LAG_FORGIVE_TICKS = 0`, D.5): all lag is dropped, never fast-forwarded, so the player never sees a repayment run, and since no domain system reads wall time the dropped time is observable only in diagnostics. *(Resolved 2026-10-27 — user ruling (design-review decisions), Open Question 19: `LAG_FORGIVE_TICKS = 0`.)* *(Amended 2026-10-27 — design review)* *(Amended 2026-10-27 — user rulings)*
- **If the kernel leaves `RUNNING` inside a catch-up frame** (a P6 pause, a restore, a fault): the driver re-reads the state after every `step()`, stops stepping, and clears the accumulator; the remaining due ticks are not run later (CR-1a). *(Amended 2026-10-27 — design review)*
- **If the tick source is asked about Godot's physics step**: it is not consulted. The driver runs from `_process` on a `PROCESS_MODE_ALWAYS` node and needs no match with `physics/common/max_physics_steps_per_frame`; a Vertical Slice physics projection reads committed state and never steps the kernel (CR-1a). *(Amended 2026-10-27 — design review; replaces the former physics-callback boot assertion)*
- **If the queue holds more than `MAX_CMDS_PER_TICK` commands at P0**: P1 takes the first 128 by `ordering_key`; the rest remain queued with their keys and are first in line at T+1 (CR-17). The 129th command's `apply_tick` is `queued_tick + 2`.
- **If a command reaches P2 with age `T − queued_tick > max_age_ticks`**: rejected `STALE`. At the defaults this cannot happen for a local issuer (ratified, R-3) (D.7 finding); it is the VS-B remote-lateness guard.
- **If a coalesced (`LATEST_PER_ACTOR_PER_TICK`) intent is rejected `STALE`**: the actor's intent block retains the *previously applied* intent — a "stop" that went stale leaves the character moving. Consumer rule carried to the Player Controller GDD: an issuer receiving `STALE` for a coalescing type must resubmit its current value from its result handler (the input adapter's quantised-change filter must be bypassed for one send); the result arrives at the next flush and the resubmit is admitted normally — `submit` never calls back, so the handler cannot recurse. The kernel never retries.
- **If a queued command's `max_age` would expire while the kernel is `PAUSED` or `SAVING`**: it cannot — `T` does not advance in either state, so age is frozen with it.

**Queue capacity**

- **If one issuer's pending count reaches `PER_ISSUER_CAPACITY` (256)**: that issuer's next submit is rejected `QUEUE_FULL`; all other issuers are unaffected. Supersession still works for that issuer (it frees a slot before the capacity check).
- **If the global pending count reaches `QUEUE_CAPACITY` (1024)**: every issuer's next submit, including the local player's and `SYSTEM` submits from hooks, is rejected `QUEUE_FULL`; the hook receives no result (`SYSTEM` results go to the log only) and must tolerate rejection and read the outcome from state (CR-9 owner rule; path (b) targets may reject anyway). In MVP this is unreachable (`2 issuers × 256 = 512 < 1024`); in VS-B it is reachable (Section G). *(Option, not spec)*: a `SYSTEM_RESERVE` of slots only `SYSTEM` may use so remote floods cannot starve the host's own systems.
- **If a submitted payload fails the CR-4 whitelist or exceeds `MAX_PAYLOAD` (4 KiB)** — an object reference, node path, callable, any non-whitelisted `Variant.Type`, a non-finite float, nesting deeper than `PAYLOAD_MAX_DEPTH` (8, which also catches a self-containing container), mixed dictionary key types, or `var_to_bytes(payload, false).size() > 4096`: rejected `MALFORMED` at admission, in every build. A payload of exactly 4096 serialized bytes is admitted; 4097 is rejected. Under `STRICT_DEBUG` the round-trip test (CR-4) additionally reports a violation for any whitelisted payload that fails to survive serialization. *(Amended 2026-10-27 — design review)*

**Notification**

- **If a block's dirty set exceeds `MAX_DIRTY_KEYS` (256) in one tick**: `change_keys` collapses to `ALL` for that block only; other blocks deliver their key sets normally. The kernel does not retain the individual keys. Every subscriber must treat `ALL` as "re-read everything you use from this block".
- **If a block is written but every write restores the original value**: it is still dirty (the kernel marks writes, not diffs); the subscriber may re-read and find nothing changed.
- **If a `PRESENTATION` subscriber attempts a block write from its handler**: writes are disabled in P5 — the mutator refuses the write in every build, increments `WRITE_OUTSIDE_SCOPE` and reports a violation (`STRICT_DEBUG` also runs the violation handler). The notification batch completes for all other subscribers. *(Amended 2026-10-27 — design review)*
- **If a `PRESENTATION` subscriber attempts to submit**: it has no submit handle — the handle is issued only to `INPUT_SURFACE` subscribers at subscribe time and is bound to the local seat (H4). If a `PRESENTATION` script obtains an `INPUT_SURFACE` handle by reference-passing, the kernel cannot distinguish the call and the control manifest/lint is the enforcement; the kernel-level guarantee is that no handle is ever *issued* to `PRESENTATION`.
- **If a subscriber handler aborts on an engine script error**: the engine cannot be intercepted (CR-19). The kernel calls handlers one at a time from its own loop, so the abort ends only that handler — the error is printed, the loop continues and the remaining subscribers still receive the batch; the completion sentinel (the handler did not return `ctx.complete()`) lets diagnostics record the subscriber ID as `INCOMPLETE`. The tick is already committed, so the sim is unaffected. This is **best-effort isolation plus lint**, not a guarantee: a handler is a presentation defect, never a kernel fault. *(Amended 2026-10-27 — design review)*
- **If sim code (any call during P2 or P3, or any registered owner) requests a `PERCEPTION_OUT` read view**: in every build the read returns an empty view (no data, not null — callers should not crash), increments `PERCEPTION_READ_BLOCKED` and reports a violation naming the caller (`STRICT_DEBUG` also runs the violation handler). The owner's own hooks are included (CR-12). A view obtained legitimately outside tick phases and cached for use inside one is a lint obligation.

**Snapshot and restore**

- **If `request_snapshot` is issued while `PAUSED`**: `PAUSED → SAVING` at the (idle) boundary; capture runs at the current `T` with no tick; return state is `PAUSED`.
- **If `request_snapshot` is issued during a cross-block `apply` or any mid-tick phase**: it is recorded and honoured at this tick's P6, after P4 commit; a snapshot can never observe a half-applied command or a mid-P3 state (CR-18, G6).
- **If a block's `snapshot()` reports a fault, returns without the completion sentinel, or returns non-plain data (whitelist walk)**: capture error → `SAVING → FAULTED`; the partial snapshot is discarded and nothing is handed to Save/Load; the existing save file is untouched. The pending queue gets `Dropped(FAULTED)`. *(Amended 2026-10-27 — design review)*
- **If a restore payload lacks a registered `persist` block**: `default_state()` is used for that block, a diagnostics note is written, and restore proceeds (CR-8; Save/Load decides whether a missing block is acceptable before calling).
- **If a restore payload contains a `block_id` the registry does not know**: the kernel's **pre-check** (run over the whole payload before any `restore()` is called) fails with `RESTORE_UNKNOWN_BLOCK`; state is fully intact (nothing was touched) and the kernel goes `LOADING → FAULTED` per the transitions table. Save/Load is expected to strip or refuse unknown blocks first, so reaching this is a Save/Load defect.
- **If a block's stored `schema_version` is newer than the code's**: the owner reports unsupported (never a silent default) — caught in pre-check if owners declare `supported_versions`, otherwise at that block's `restore()`; either way `LOADING → FAULTED`. State is intact only if caught in pre-check.
- **If a block's stored `schema_version` is older and the owner has no migration for it**: same path and outcome as "newer".
- **If the snapshot header's `TICK_RATE` differs from the running constant**: *(Ratified 2026-10-27 — user ruling (design-review decisions), R-9; rationale: record `TICK_RATE` in the header)* *(Amended 2026-10-27 — user rulings)* pre-check fails `TICK_RATE_MISMATCH` → `FAULTED`; migrating every tick-expressed value in every block is impractical, so a save is bound to the tick rate that wrote it.
- **If any block's `post_restore()` fails (cross-block ID unresolved, invariant violated)**: `LOADING → FAULTED` with the block and invariant named. Because restore is whole-block replace and all blocks have been replaced by the time `post_restore` runs, **pre-restore state is not intact here** — "where possible" in CR-18 means pre-check failures only. *(Option)*: capture an in-memory snapshot of the live state before a mid-session restore so diagnostics can diff; automatic revert to it is out of scope (would need a second restore pass that could itself fail).
- **If `request_restore` is made while `SAVING` is active** (only possible from inside the atomic capture): it is queued and served, in arrival order with any other queued request, at the boundary that follows the capture; the queue is flushed with `Dropped(RELOAD)` at that point. *(Amended 2026-10-27 — design review)*
- **If a restore completes while the pending queue is non-empty**: every pending command has already received `Dropped(RELOAD)` at the `→ LOADING` transition; the first tick after `RUNNING` sees an empty queue.

**Authority, classes and identity**

- **If an `INPUT_SURFACE` submits with an `actor` its seat's PlayerId does not control**: for `OWNED_BY_ISSUER` types → `ACTOR_NOT_OWNED` at P2; for `actor_binding = NONE` types the kernel does not check `actor` at all and the owner's `validate` decides. The surface can never choose its `issuer_peer` (stamped by the handle — H6), so "submitting as another seat" is unrepresentable.
- **If the binding table is changed during a tick**: the change is a control-plane request honoured at P6, so every authority check within one tick sees one consistent table; a command admitted before the change and dispatched after it is checked against the *new* table (authority is checked at P2, not at admission).
- **If a `PlayerId` is unbound from an entity while that entity has pending `OWNED_BY_ISSUER` commands**: those commands reach P2 and are rejected `ACTOR_NOT_OWNED`; they are not dropped early.
- **If a peer is bound to a PlayerId that already has persistent `PER_PLAYER` blocks**: nothing in the kernel changes — persistent state is keyed by PlayerId, never peer_id (Vocabulary); the binding only maps the new peer to the existing seat.

**Lifecycle, mode and tests**

- **If the kernel is `SAVING` when an invariant check (inside a block's `snapshot()`) fails**: see capture error above — `FAULTED`, snapshot discarded, existing save untouched.
- **If `FAULTED` is entered while a notification batch is mid-delivery**: impossible — faults originate in P2/P3 (apply, validate, hook) or `SAVING`/`LOADING`; P5 handlers cannot fault the kernel (a handler's reported fault or missing sentinel is recorded, CR-19).
- **If `request_shutdown` arrives with queued commands**: every pending command receives `Dropped(SHUTDOWN)` — appended to the result buffer during the `→ SHUTTING_DOWN` transition and delivered by the final flush that teardown runs — then teardown; no further ticks, no snapshot (the FAULTED/shutdown rule: the kernel never autosaves on the way out).
- **If the tick counter would overflow**: it cannot — `T`, `seq` and `host_order` are 64-bit (D.14); the boot assertion on width is the only handling.
- **If anything attempts to construct or switch the kernel into `MIRROR` mode in MVP**: `BOOTING → FAULTED` with `MODE_UNSUPPORTED`; the `MIRROR` enum value exists so the API is mode-agnostic, but no MIRROR ingress, replication subscriber or constructor is compiled in MVP (H8). An acceptance test asserts that a MIRROR submit is impossible by asserting the construction fails.
- **If two kernel instances exist in one process (a test constructing two)**: each has its own registries, queue, clock, binding table and log; a block object registered with a second kernel while bound to a first fails that kernel's boot (`BLOCK_ALREADY_BOUND`) because owners are instance-scoped; an autoload, if one exists, is a thin holder of *one* instance and kernel code never reads it (H10), so the second instance is unaffected by whatever the autoload holds. gdUnit4's orphan-node check (exit 101) is avoided because neither instance is a Node.
- **If `TICK_RATE` is changed in code between two play sessions without a save in between**: nothing breaks at the kernel level, but every tick-expressed tuned value in every data file is now wrong by the ratio of the rates; this is why `TICK_RATE` is a set-once constant and why Section G lists every knob it invalidates.

## Visual/Audio Requirements

None of its own — the kernel renders nothing and plays nothing (H4, CR-11). What it *requires* of visual and audio systems is structural: every presentation element subscribes as `PRESENTATION` (or `INPUT_SURFACE`), reads last-committed state through read views, and interpolates with `tick_alpha` where motion must be smooth. Two consequences for the art bible's rules are worth stating here so they are not rediscovered per system: (1) the art bible's truth-channel / corruptible tag contract (Perception Filter) maps onto the kernel's two consumer channels — truth-channel elements read `SIM` views directly, corruptible elements read the Filter's `PERCEPTION_OUT`-derived channel; (2) the "nothing fails silently" rule of Pillar 1 is served by the kernel only in that every state change produces a notification — *what* is drawn for it is the owning system's Visual/Audio section. No asset-spec flag: there are no assets.

## Game Feel

Optional for a `Core` system; one target is recorded because it is the kernel's doing. **Input-to-effect latency, empty queue, 60 Hz tick / 60 fps render: the first changed frame is drawn within 33.3 ms of the input event and the full committed value within 50 ms (D.4 `L_first`, `L_full`); the sim confirms within one tick (16.7 ms of simulated time); acknowledgement is immediate.** A backlog adds one tick per 128 queued commands. *(Amended 2026-10-27 — design review)* The gameplay-programmer's feel bar: a press should produce a local response in the same frame (tool sound, hand animation start, linear progress bar beginning), with the sim confirming on the next tick; the only visible effect of the command path is a bar that begins a tick later. Movement waits one tick like every command — Body's integration hook reads the current intent in P3 (CR-4) — so the avatar's first response is inside the same bound; only the acknowledgement (a footstep sound, a stance change) is same-frame. *(Amended 2026-10-27 — design review)* Two anti-targets: no synchronous local fast path for results (it would not survive a remote issuer), and no client-side prediction in MVP (the `seq`/`queued_tick` fields and determinism guarantees are the hooks for it later). Reduced-motion settings never alter the tick (CR-11), so feel and accessibility settings cannot change simulation outcomes.

## UI Requirements

No player-facing UI. The kernel exposes one **developer-only** surface, consumed by the Debug Overlay (True Values) as a `DIAGNOSTIC` subscriber: current tick and kernel state; queue depth and per-issuer depth; the last-N command log with results and reject reasons; resolved hook order with per-hook timings and the `STEP_BUDGET_MS` overrun flag; rejection counters by reason; catch-up lag counter; `state_hash` as last refreshed at the diagnostics cadence (`DIAG_HASH_CADENCE_TICKS`), through a read-only `diagnostics` accessor carrying `hash_T` and `hash_algo`; and the kernel's diagnostics timer, read-only (H9 — nothing simulated reads it), for the Overlay's own cost row *(Amended 2026-10-27 — consistency pass, routed from debug-overlay-true-values (OQ-DO-5))*. It must be absent from release builds and is never an accessibility feature (art bible R-7, concept risks). Player-facing *consequences* of kernel behaviour — rejection feedback, honest pending-vs-confirmed states on channels — are UI requirements of Interaction, HUD & Suit Layer and In-World Instruments, which must map reason codes to feedback without display strings ever entering the kernel (CR-5). *(No UX flag: nothing here is a player screen.)*

### Gaps / untestable as written

- **Formula count.** Section D names 24 formulas, not 21 (D.1 two, D.2 three, D.3 one, D.4 two, D.5 two, D.6 two, D.7 two, D.8 three, D.9 one, D.10 one, D.11 two, D.12 one, D.13 one, D.14 one). Every one of the 24 has a criterion above; the brief's "21" should be corrected in whichever document carries it.
- **`L_first` / `L_full` best case (D.4).** The 'same-frame' path depends on node `_process` ordering the engine reference is silent on; the driver's process priority is set to run first and the spike verifies it. The manual latency criterion measures it in-engine.
- **`H64` chosen but golden `state_hash` values not yet written (D.12).** `mix64` (SplitMix64 finaliser) and `fnv64` (FNV-1a) are pinned by the D.10 golden vectors; `H64` (SHA-256 low 64 bits via `HashingContext`) was ratified 2026-10-27 — user ruling, R-17, to be recorded in the ADR. Golden `state_hash` values still have to be computed with an independent reference implementation and then frozen as set-once. *(Amended 2026-10-27 — user rulings)*
- **`PRESENTATION` script obtaining an `INPUT_SURFACE` handle by reference passing.** The kernel cannot detect it; the only enforcement is the control manifest and lint (criterion written as a lint on `submit(` outside `INPUT_SURFACE` files). The control-manifest format does not yet exist.
- **"Only declared callers call declared mutators" (CR-9).** Same: control-manifest/lint obligation with no manifest format to lint against.
- **Commands queued before `request_pause` is honoured.** Decided in CR-16 (they wait, in order, for resume) and tested by the criterion at the end of Tick & phases.
- **Physics step cap (D.5).** Removed: the tick is driven from `_process` (CR-1a), so no criterion depends on how Godot treats excess physics steps.
- **`LAG_FORGIVE_TICKS`.** Ruled 0 on 2026-10-27 (user ruling, Open Question 19) and restated in D.5; the non-zero branch is a fixture-only parametric seam. Criteria under Bounds & overload. *(Amended 2026-10-27 — user rulings)*
- **Open Question 5 (G3 scope).** Moot at MVP (no block is physics-coupled, CR-13); the physics-coupled exclusion criterion stays as a fixture until a Vertical Slice projection feeds a block, at which point a record-and-replay criterion is needed.
- **Open Question 1 (subscriber-class reading of H4).** The `INPUT_SURFACE`/`PROJECTOR` criteria encode the GDD's provisional reading; a different TD ruling changes them.
- **Release-build reactions ("returns to the menu", "dev build halts").** The menu return is Save/Load/UI behaviour, not kernel-observable; only "no snapshot handed, state `FAULTED`" is tested.
- **Post-`restore` failure leaves state replaced.** CR-18's "pre-restore state intact where possible" is testable only for pre-check failures (criterion written); the `post_restore` failure path is by design not revertible and has no intact-state criterion.
- **D.11 size expectation (100–300 KiB).** No real blocks exist; the `snapshot_bytes` criterion checks the sum identity, not the magnitude.
- **Wall-clock figures.** All Performance-budget numbers are machine-dependent and spike-provisional, as stated in that block.
- **Engine script errors (CR-19).** Not interceptable. The sentinel catches a function that aborted, not a nested helper whose error the caller ignores; P5 subscriber isolation is best-effort plus lint. No criterion claims otherwise.
- **Determinism is "same build and platform" only (CR-13).** No cross-machine or cross-version hash equality is claimed or tested.
- **`MIRROR` behaviour.** Only "construction fails in MVP" is testable; the identical-API claim is VS-B scope.
- **Global `QUEUE_FULL` for an under-cap issuer is unreachable in MVP by design.** Coupled constraint 2 guarantees it; the criterion above disables the constraint to cover the code branch, not a live state. In VS-B (5 issuers × 256 > 1024) it becomes reachable and the criterion should be re-expressed against real configuration.
- **Headless determinism test (a) runs on stand-in blocks.** The Life-Support Graph and Attention GDDs now exist; the real-block variants are the **[Integration]** criteria above. The stand-in fixture stays for kernel-only unit tests.
