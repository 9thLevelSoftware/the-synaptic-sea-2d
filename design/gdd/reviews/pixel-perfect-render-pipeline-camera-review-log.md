Findings:
  - [BLOCKING] Core Rules PR-6 C4 / C11 / Formulas D.7; player-controller-input.md PC-5 (L384, L393): [godot-specialist][gameplay-programmer] The look-ahead and mouse aim form a closed loop that nothing models. I confirmed it in the files. C4 (L159) reads the local raw aim. PC-5 defines mouse aim as cursor_world - floor(chest_point) (player-controller L384), and cursor_world comes from the pipeline's C11 mouse-to-world (L393), which depends on the camera pose. The pose includes L, and L is driven by the aim. So with a still mouse, the lean rotates the aim and the beam. When the cursor is within about L_MAX of picture centre, which is where a mouse player's cursor usually rests, the aim locks toward the existing lean. The cursor is hidden in gameplay ('the beam is the pointer'), so the player sees the beam drift with nothing to explain it. That breaks Pillar 1 (The World Never Lies) at the game's main verb, the chest-lamp beam. All D.7 tests feed the aim in as an independent input, so none of them can catch this.
  - [BLOCKING] Formulas D.6 / D.7 / D.9; Game Feel (Stillness); Player Fantasy design test 2: [main][systems-designer][gameplay-programmer] floor() of an asymptotic approach makes a still scene's frame land one pixel late, or never. The main review found this for f. The systems-designer and gameplay-programmer showed that L has the same tail, because c = f + L and L_target is an exact integer 72 for axis-aligned aims, and L = 0 under reduced motion, which is an accessibility path. The systems-designer also showed that with float32 Vector2 state f can stall one ulp short of the target, so the error lasts indefinitely, not about 7 s. The result is a 1 px frame shift with no cause in the world, the counterfeit tremor that Pillar 2 and design test 2 forbid.
  - [BLOCKING] Core Rules PR-6 C3 ('identical at 60 and 144 fps') / Formulas D.6 / D.10 / AC L935-L939: [systems-designer][gameplay-programmer] The core contract that the solver is 'identical at 60 and 144 fps for the same wall time' (C3, L157) does not hold for a moving target under the D.6 update. A per-frame exponential factor is exact only when the target is held constant through the frame. For a ramp, the steady-state lag depends on dt, so floor(pose_q) differs between frame rates during a run. The AC requiring identical pose_q (L936) fails a correct implementation, and so do the lag ACs (32.4 / 21.6 +/-0.5). The two specialists' numbers differ (30.9 vs 33.9 px at 60 fps) only because they measure before and after the target update. They agree the result depends on frame rate. Both also find that the inner-box margin erodes at low fps.
  - [BLOCKING] Core Rules PR-5 sort origin / Formulas D.12 (L533) / Edge Cases (same sort origin) / AC L983: [main][godot-specialist][gameplay-programmer][systems-designer] The equal-row tie-break is wrong, and Godot cannot implement it as written. I confirmed the D.12 text at L533: ties among free items fall to 'x ascending, then creation_id'. That leaves an actor standing flush south of a console or door, the game's most common interaction posture, overdrawn depending on x. The godot-specialist adds that Godot's Y-sort has no comparator hook. The godot-specialist and gameplay-programmer both note that an x rule changes the draw order mid-motion, when an actor's x crosses a prop's x. The gameplay-programmer also notes that creation_id changes after a reload. The systems-designer adds that door and doorway crossings put an actor inside a passable footprint, so the actor hides behind the face for the whole transit and the actor_in_footprint lint fires on every legal crossing.
  - [RECOMMENDED] Core Rules PR-7 / PR-12 / Open Question 1: [main][godot-specialist][performance-analyst][gameplay-programmer] The SubViewport wiring is unresolved. The main review rated this BLOCKING. I downgrade it to a gate on implementation stories rather than a GDD defect. The GDD already routes it to an ADR and spike step 11. The solver, the sort contract and D.12 do not depend on the wiring. The godot-specialist argues that wiring (i) (root stretch disabled, script-set integer container scale and integer CanvasLayer.scale) is the expected answer, because under (ii) the root stretch scales the container a second time and the scales end up as floats.
  - [RECOMMENDED] Acceptance Criteria (follow, look-ahead, z-band, jolt) / D.6 / D.7 / D.11 examples: [main][systems-designer] Several ACs fail a correct implementation because their arithmetic is wrong. I confirmed 17.3 at L428 and L935; the correct value is 17.05. The look-ahead L.y >= +68 at 1.4 s should be about +64.2. The BAND_H = 1 clamp cannot occur at L_h = 800. The 38.0 px check passes only from frame 33. The jolt sequence should be +2, -2, +1, -1, 0, 0. D.11 also reuses s for three different meanings.
  - [RECOMMENDED] Formulas D.5 / D.6 / D.7 / D.10 (field scaling s): [godot-specialist][gameplay-programmer][systems-designer] Scaling tau by s > 1 makes the frame keep drifting for 1.6 s at 1x on 1080p and 3.2 s on 2160p, which contradicts Stillness. The s = 1 default only applies at 640x360, and tau_eff on 1600x900 is outside its safe range. A zoom step changes the parameters without rescaling the state, so P_lag or the inner-box clamp fires when zooming in while running.
  - [RECOMMENDED] Formulas D.3 / D.5 (logical field sizes): [main][gameplay-programmer][systems-designer] Logical field sizes are odd or non-integer in common cases. The odd expand sizes put the camera on a half pixel. The keep-mode ladder field is fractional on the Deck at k_z = 3 (426.67 x 240), at 1440p, and at 2160p with k_z = 7.
  - [RECOMMENDED] Core Rules PR-5 z-band fallback / D.13 / Edge Cases: [main][godot-specialist][gameplay-programmer][performance-analyst][systems-designer] The z-band fallback overlaps the cap and dust bands, and its N_bands count misses the face and cap overhang. It also cannot be implemented as written. A TileMapLayer's z_index is per layer or per tile type, not per cell. Camera-relative bands slide against the world, so 'a wall is alone in its band' is false, and the fallback probably adds draw calls and CPU work rather than removing them.
  - [RECOMMENDED] Core Rules C2 camera host / C8 limits / States and Transitions / AC L959: [godot-specialist][gameplay-programmer] Camera2D applies its scroll in its own internal processing, so the frame can show last frame's pose against this frame's sprites [UNV]. process_priority does not fix that. Limits are clamped twice (by the engine and by the solver), so world_to_hud is offset while CLAMPED. The state table conflates follow/clamp, zoom level and hold/cut, so transitions are missing.
  - [RECOMMENDED] Core Rules C5 / C10 / CUT state / MVP death: [gameplay-programmer][main] A CUT snaps L to the current aim, so re-wake framing is not reproducible. A body transfer zeroes the lag and visibly shifts the avatar. The MVP death stub's zoom behaviour (restore from autosave, which is the user's decision) appears only in parentheses.
  - [RECOMMENDED] Formulas D.6 / D.7 / D.10 (degenerate inputs): [gameplay-programmer][systems-designer] tau = 0 combined with dt = 0 gives NaN, which then persists in the state. Nothing clamps dt after a hitch. Look-ahead applies the full lean at any aim magnitude, swinging 72 px when the cursor crosses the avatar. The slew is clamped per axis, so a diagonal swing runs about 41% faster than the stated limit.
  - [RECOMMENDED] Acceptance Criteria (Performance budget, Y-sort draw calls) / PR-7 pass A vs B / D.16: [performance-analyst][main] The draw-call caps (D_world <= 350, sum <= 1000) cannot be met at the 4x and 9x zoom-out fields given the GDD's own D_ysort range. At 1x, pass A costs as much as or more than pass B in lit pixels and memory. Nothing measures 1440p or 2160p at 1x. There is no reference hardware, no Deck figures, no total-frame-time AC, and the Forward+ renderer choice is not recorded. Nothing in the performance block can fail.
  - [RECOMMENDED] Core Rules PR-13 / Formulas D.15 / OQ6: [main][performance-analyst][systems-designer] The flash governor has no measurement mechanism. A GPU readback either stalls the frame or arrives late. F = floor(n/2) lets a 3.5 Hz flicker pass. Y is undefined, and Y_scale is 0 for a light that is off. The deployable flicker has no value.
  - [RECOMMENDED] Tuning Knobs vs Section G build invariant: [main][systems-designer] INNER_BOX_FRAC 0.25 and tau 0.20 are listed as safe but fail the strict invariant. The JUMP_CUT row cites an 8-tick burst, but MAX_TICKS_PER_FRAME is 4.
  - [RECOMMENDED] Core Rules C5 / D.10 cut predicates: [main][godot-specialist][performance-analyst][gameplay-programmer] P_pan, P_lag and P_jump have no legal trigger from player movement at MVP (4 ticks x 3 px = 12 px < 48).   - [RECOMMENDED] Core Rules C3 / spike step 12 (avatar wobble): [main][gameplay-programmer] Under exponential follow the avatar's screen offset toggles by 1 px, which is structural. Step 12 has no pass/fail threshold, and the GDD does not say which follow ships if the threshold is missed.

  - [BLOCKING] Pipeline D.14b (L596-613), PR-6 C4/C11, Interactions row 3 (L819), OQ 18, AC L1001-L1002; player-controller-input.md PC-5 (L139), D.7 (L441-456), AC L989: [main review, confirmed by creative-director spot-check] The two GDDs specify different mouse-aim mappings for the game's main verb. Pipeline D.14b: cursor_world_aim = p + cursor_off, aim measured from floor(chest), called through mouse_to_world_aim. PC-5: cursor_aim_world = f_q + (cursor_vp - picture_centre)/k_eff, measured from a fixed AIM_ORIGIN = floor(pos_curr) + (0, -35), reading f_q, which the pipeline never publishes. The pipeline's closed-loop AC (L1001: 'with the avatar running at v_run, aim is constant') holds for p and fails for f_q, which lags by up to 32 px. The lint (L1002) names a function PC-5 does not call. The aim pillar of a horror game in which 'the beam is the pointer' (PC, HUD HS-52: the OS cursor is hidden, with no reticle) cannot carry two definitions. [creative-director] Creative ruling on the anchor: the avatar-anchored p is better for player experience. With the cursor hidden, the player's only model is 'my hand moves the lamp relative to me', so aim has to be rigid with the avatar. With f_q the beam swings by itself while the player runs with a still mouse, and a dread-first game must not create that unexplained motion. Use PC-5's fixed reference AIM_ORIGIN (-35), not D.14b's per-facing floor(chest). The fixed origin is what removes the facing/sheet flip limit cycle, and the beam is still drawn from the true CHEST_POINT.
  - [RECOMMENDED] D.8 example; Edge Case (look-ahead plus lag); AC L997; AC L1009: [main review, confirmed by creative-director] The jump direction is wrong. With y down, a 40 px northward jump and L = (0,-72) gives |c.y - target.y| = |40 - 72| = 32, so the inner box never engages. AC L997 therefore fails a correct solver, and L1009's '47 px northward ... pins c at 108' is impossible. The worst-case invariant (32.4 + 72 = 104.4 < 108) is correct.
  - [RECOMMENDED] C8 / States CLAMPED / D.8-D.9 / Edge Case 'detach moves limits' / AC L1018: [main review] The limits clamp exists only in prose. Its order against the inner-box clamp is unspecified, which makes either the hull limits or D.8's 'avatar stays in the central 60%' guarantee false at hull edges. 'Eases within 0.54 s, zero overshoot' contradicts C8's direct clamp of c.
  - [RECOMMENDED] C3 / D.6 / OQ 12 / AC L1006: [main review] By the GDD's own arithmetic, exponential follow misses its wobble threshold at 90 and 144 fps, and AC L1006 then says 'the build ships rigid follow'. The rigid variant has no formula, settle rule, inner-box or lag invariant, or ACs, so the likely shipping branch is unspecified. [creative-director] Not raised to BLOCKING only because the A/B outcome comes from spike step 12. The rigid spec must be in the GDD before the camera-solver story is marked ready, because sub-pixel world shimmer while walking is a false 'something moved' signal in a game where Pillar 2 trains players to read small changes as tells.
  - [RECOMMENDED] C3 / D.6-D.7 settle / Game Feel 'Stillness' / Edge Case 'avatar and aim stop' / AC L1000: [main review] t_settle of about 0.75 s covers only the follow term. After a full aim reversal the look-ahead term (144 px/s slew, then tau 0.40 s) settles in about 2.5 s, so the 'Stillness' promise and AC L1000's +/-1 frame bound are false in that case.
  - [RECOMMENDED] D.7 / D.9 / Player Fantasy design test 2: [main review; creative-director endorses with pillar weight] L_target follows raw mouse aim, so a resting hand's 1-screen-px tremor can step the whole world frame by 1 base px. That breaks 'when the ship is still, the screen is still', the stillness horror presentation depends on (Pillar 2).
