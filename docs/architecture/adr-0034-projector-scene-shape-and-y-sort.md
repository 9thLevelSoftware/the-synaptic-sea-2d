## Summary
The two PROJECTOR subscribers (the Layout projector and `body.projector`) must turn `layout.state`, `body.state` and the frozen section templates into one engine scene in which walls, doors, props, actors and horrors sort by `(sort_y, class_rank, entity_id)`, in which a weld or cut changes which body a section belongs to without a visible frame, and from which the camera solver receives a limits rectangle; the GDDs left the shape to a spike (SP-YSORT-1), which has not run. This ADR decides the shape from probes on the editor binary: one `y_sort_enabled` translation-only root per live body inside one `y_sort_enabled` world node (nested Y-sort nodes sort as one merged group, so a per-body root does not break the single sort scope), seven z-band groups per body root with the sorted ones in a fixed rank order, one `TileMapLayer` per section per layer kind (section offsets sit on a 24 px grid, so a merged per-body 48 px tile map cannot hold them) with exactly one atlas source each, weld and cut by **reparenting** each moved section's nodes and recomputing their positions from the current `section_offset` (no tile is re-authored on a weld; the engine rebuilds each moved `TileMapLayer`'s canvas items once, deferred, V10, and that rebuild is charged to the weld budget), a publisher-namespaced `entity_id` packing in `src/shared/` with append-only namespace bytes, and an integer `CameraLimits` raw hull rectangle published in stage `PROJECT` (the solver's effective rectangle and clamp rules are ADR-0008's). `Staging` is a data stage only: it does not pre-warm rendering. SP-YSORT-1 stays the acceptance gate for the release export, the Steam Deck, real atlases and the 8 ms weld figure; this ADR is Proposed and does not close it.

## Context

### Problem Statement
Five things were left to this ADR by the GDDs and by ADR-0008 and ADR-0009, and none can be decided inside a presenter story:

1. **Scene shape.** Body's GDD (BDY-33) says a PROJECTOR owns one translation-only root per live body, with one y-sorted actor and props layer per root, and reparents Presenter nodes on `BODY_TRANSFER`. Layout's GDD (LY-31) says the default shape reparents section nodes under that root on every weld, that this "sits badly" with the Pipeline's single Y-sort scope, and that a spike should try a no-reparent option B first. Neither text knows whether nested Y-sort nodes form one scope, whether a weld should reparent or rebuild, or whether a tile map is per body or per section.
2. **The Y-sort key.** PR-5 fixes `(sort_y, class_rank, entity_id)` and says the wall-face `y_sort_origin` "is set to the footprint depth, not 0". The engine's own key for a `TileMapLayer` cell is different (V3), the tie rule is tree order (V1), nothing registers the `entity_id` namespaces that make ids unique across blocks (Layout OQ-33), and a door's sort edge depends on a Graph value (TR-pxl-007).
3. **Weld, cut and arrival cost.** A weld must show its bead in the first frame (TR-assembly-045), cost at most 8 ms P99 (TR-shipbody-045, a working threshold, engine-side rebuild of moved layers included, V10) and leave no orphan node; an arrival must build the largest destination scene inside the settle window (TR-webmap-037); both are budgeted in `BUILD_TILES_PER_FRAME` units that no ADR has made precise. ADR-0009 OQ-I left the weld case to this ADR.
4. **The camera-limits rectangle.** ADR-0009 OQ-C reconciled that a PROJECTOR publishes the rectangle and never writes `Camera2D.limit_*`; no ADR has named the sink, the frame, or the rectangle.
5. **Draw bands and the fallback.** The z-band order is "the contract" and the numbers are "the ADR's" (PR-5); the per-row fallback is built only if it wins a measurement (TR-pxl-009).

### Constraints
- **Presentation never writes the simulation (kernel H4).** The PROJECTOR writes only engine-side derived objects its block owners' GDDs name, never creates `Light2D` or `LightOccluder2D` (the Layout projector; ADR-0009 § 1), and never writes `Camera2D.limit_*` (OQ-C).
- **Integer placement, one assignment point.** Every `Node2D.position` in presentation is written only through `Placement.put` (ADR-0009 § 4); canvas coordinates are integer-valued `float32` and exact for `|v| <= 2^24` base px (ADR-0008 § 6.2); body-frame and canvas offsets are bounded by ADR-0015 (`BODY_COORD_LIMIT`, at most 2^24, restore-checked and repeated by Layout in `can_attach`; and `WORLD_COORD_LIMIT`, lowered if needed so that `|world_a - world_b| + |pos| < 2^23` holds under `WEB_COORD_BUDGET_PX`, CT-24).
- **Rotation is never rendered inside (C2).** Every body root has rotation 0, scale (1, 1), skew 0.
- **`physics_interpolation` is off for all presentation (ADR-0009 § 5); `tick_alpha` is the one interpolator.**
- **Stage `PROJECT` (0) runs before `CAMERA_SOLVE` (1) in the same `_process` pass** (ADR-0009 § 3), so anything the projector publishes is consumed in the same frame. The registration order inside stage 0 is the layout projector, then `body.projector`, then Lighting's occluder builder (ADR-0009 § 3).
- **Presenters define no `_process` and no handler allocates or draws** (ADR-0009 § 2): the projectors mark dirty in the handler and build in `present`.
- **The PROJECTOR scripts live in `src/presentation/projector/`; `src/sim/**` is tree-free** (ADR-0010 § 1.2). Pure packing helpers that the simulation must also compute live in `src/shared/` (L0).
- **Section offsets are on the 24 px grid, not the 48 px grid** (ADR-0013 § 7, `GRID_24`; the registry's MVP socket pair gives an offset of 696 px on x, which is 14.5 tiles).
- **Walls project up-screen** (PR-5 convention): footprint rows `[y0, y0 + WALL_FOOTPRINT_DEPTH)`, a face of `WALL_FACE_PX` rising from the footprint's south edge, a cap of `WALL_FOOTPRINT_DEPTH` above the face.
- **Release-export performance is unmeasured (OQ-10); every wall-clock figure here is a proposal or margin evidence.**

### Requirements
- One tree shape that the weld, cut, pod hop, arrival, restore and salvage paths all produce identically (a test compares an incrementally updated projector with a fresh one fed `ALL`).
- A draw order that is a pure function of persisted ids and positions: identical on 10 runs and after a save and reload that reverses creation order (PR-5 acceptance).
- A weld frame that moves nodes and recomputes positions without re-authoring any tile (the engine's deferred rebuild of the moved layers is charged to the weld budget, V10); an arrival that builds its data in a declared number of frames and counts the unchunked mount rebuild separately.
- Named bands and a lint that dependents can use without writing a z number.
- A limits rectangle in integer base px, in the frame the solver works in, published before the solve.

### Binding stances respected (registry check, `docs/registry/architecture.yaml`)
No registered stance is contradicted. Stances this ADR builds on: `PresentationStage` constants and the PROJECT order (ADR-0009); `Placement.at` / `put` as the only position writer (ADR-0009 § 4); `camera_canvas_transform_write` (ADR-0008: the solver is the only clamp, `Camera2D.limit_*` untouched, no `Camera2D` in the world tree); canvas exactness to `2^24` (ADR-0008 § 6.2); the layer-first source tree with `src/presentation/projector/` (ADR-0010); ids are block-local and the kernel allocates none (ADR-0003 § 2). One registry-adjacent point is **extended**, not contradicted: the registered constant `LAYOUT_ID_NS` is "to be agreed" in `entities.yaml`; § 4 fixes it. ADR-0003's "entity ids are block-local" rule stands: the `entity_id` of this ADR is a **presentation sort-key composite**, never a block id and never persisted.

### 1. The decisions at a glance

|---|---|---|
| Per-body roots | **Yes.** One `y_sort_enabled`, translation-only `BodyRoot` per body in the `ProjectionSet`, under one `y_sort_enabled` `World`. The root, not each node, carries the canvas offset. | § 2 |
| Reparent versus rebuild | **Reparent and recompute positions** for every moved section's nodes on weld and cut; **no tile is re-authored** (no `set_cell`, no chunked build), but **the engine rebuilds each moved `TileMapLayer`'s canvas items once, deferred** (V10), and that cost is charged to the weld budget. Re-authoring (chunked, staged, atomic) happens only on first build, arrival, restore, `ALL`, and a section whose template or discard state changed. `Staging` is a data stage only and does not pre-warm rendering. A fresh-build path stays the reference: a signature test requires both paths to give equal scenes, child order included. | § 7 |
| Per-body versus per-section `TileMapLayer` | **Per section**, one layer per layer kind (floor, wall face, mounted, cap), **exactly one `TileSetAtlasSource` each**. | § 5 |
| Y-sort key | `(sort_y, class_rank, entity_id)` realised as: engine key = integer node position (sprites) or `cell_top + tile_h/2 + origins` (tiles); class rank = group order; `entity_id` = child order of the sorted layers. Door and wall sort edges as in § 3. | § 3 |
| `entity_id` namespaces | `EntityId.pack(ns, local)` in `src/shared/`; namespace bytes **LAYOUT 1, BODY 2, INTERACTION 3, HORROR 4, SUIT 5, WEB 6, TRAIL 7, LIGHTING 8** (a registration key for attached lights, never a sort key), 9 to 127 reserved; the table is append-only with a golden test and is not an acceptance condition; Layout's local part as LY-31. | § 4 |

| SP-YSORT-1 | Confirms; does not choose. | § 11 |

### 2. The scene tree

The tree in the diagram is the contract. Rules, each lint- or boot-checked (§ Validation):

- **`World` and every `BodyRoot` have `y_sort_enabled = true`.** That is what makes the sort scope one merged group across bodies (V2). A `BodyRoot` is never made non-sorting: a non-sorting intermediate sorts its whole subtree as a unit (V2, P4), which would turn cross-body ordering into root order.
- **`BodyRoot` is translation only**: `rotation == 0`, `scale == (1, 1)`, `skew == 0` every frame (TR-pxl-018, C2 consequence (i)); only `Placement.put` writes `position`. A detached section keeps rotation 0 and simply gets its own root (TR-pxl-018 "detached sections translate without rotation").
- **Seven groups per root, in the order drawn above, created with the root and freed with it.** `Faces`, `Mounted` and `PropsActors` are the only sorting groups. `Floor`, `Marks`, `Caps` and `Dust` have `y_sort_enabled = false`; their z band keeps them out of the sort (V4). The PR-5 lint "the cap `TileMapLayer` is not a child of the Y-sort node" is therefore restated by band, not by ancestry (GDD sync).
- **`z_index` is set once, on the group, from `ZBand` names; `z_as_relative` stays at its default `true` and every ancestor of a group has z 0**, so the group's z is its absolute z. No other node writes `z_index`, and no presenter writes a z number (lint `PJT-03`).
- **Groups and `LIGHTING` attachments.** `Light2D` nodes that a presenter built and attached through `BodyScenes.attach_light` are direct children of the `BodyRoot`, not of a band group (§ 7.1); the projectors still create no `Light2D` (their declared classes do not include it), and a `Light2D` is never inside a sorted group.
- **The `World` node is the only Y-sort scope for the interior.** Exterior and transit layers (parallax, silhouettes, the pod in transit) are the camera host's and the Web Map presenter's and are not under `World`; the projector creates no exterior layer (TR-pxl-018, owned by ADR-0008).

**The z bands (names are the contract, TR-pxl-008).**

| Name | z | Sorted | Group | Contents |
|---|---|---|---|---|
| `ZBand.FLOOR` | 0 | never | `Floor` | floor `TileMapLayer`s; grates and drains |
| `ZBand.MARKS` | +1 | never | `Marks` | floor trails, stains, footprints (foreign, Trail); drawn flat, authoring order |
| `ZBand.YSORT` | +10 | yes | `Faces`, `Mounted`, `PropsActors` | wall faces; wall-mounted items and wall trails; doors, props, machinery, actors, horrors, deployables, empty suits, off-floor web pieces |
| `ZBand.CAPS` | +20 | never | `Caps` | cap `TileMapLayer`s; free-hanging housings |
| `ZBand.DUST` | +30 | never | `Dust` | `GPUParticles2D` (foreign) |

Floor marks and wall trails keep the PR-5 assignment: floor trails at `MARKS` and never sorted; wall trails in `Mounted` at their host face's sort origin (TR-ftrail-017); "no trail uses z 0 or +20" holds because a trail node can only be attached to `MARKS`, `Mounted` or `Dust` and the projector, not the trail, sets z. All five values sit inside the default `Light2D` range of -1024 to 1024, which is inclusive and was probed (V6); Lighting (ADR-0028) must set every light's `range_z_min <= ZBand.FLOOR` and `range_z_max >= ZBand.DUST`, and the fallback table of § 10 raises the largest value to 910, still inside. The numeric values live in one file, `src/presentation/projector/z_band.gd`, and dependents lint names, never numbers.

**Caps-above safety (TR-pxl-008).** Caps draw above the sorted band, which is correct iff no item flush against a wall has a face taller than `WALL_FACE_PX`. This is a kit rule; the debug tree-walk keeps the GDD's `diag.cap_overlap` (a prop whose drawn height exceeds the face) and `diag.actor_in_footprint` (a foot row inside a wall footprint) as dev and test checks in `ProjectorAudit`.

### 3. The Y-sort key, as built

The contract key is `(sort_y, class_rank, entity_id)` with class ranks 0 wall-face tiles, 1 wall-mounted items, 2 doors, props, machinery, deployables, empty suits and off-floor web pieces, 3 actors and horrors. Godot gives us the first term and the tree order; the other two are realised by structure:

| Term | Realised by |
|---|---|
| `sort_y` | The engine key: a node's accumulated y for a `Node2D`; for a `TileMapLayer` cell, `cell_top + tile_size.y / 2 + TileData.y_sort_origin + TileMapLayer.y_sort_origin + layer.position.y` (V3). All terms are integers. |
| `class_rank` | The order of the sorted groups under a body root (`Faces` before `Mounted` before `PropsActors`) plus, inside `PropsActors`, rank 2 children before rank 3 children. An equal key ties by tree order (V1), so the earlier group draws first. |
| `entity_id` | The child order of a sorted layer. Children are kept in ascending `(class_rank, entity_id)` by `SortedLayer` (§ 3.3), so an equal key and rank resolve by `entity_id` ascending, never by `x` and never by creation order. |

**3.1 Sort origins (integer base px, TR-pxl-006).**
- **Actors and horrors**: the foot row. The Presenter writes the node `position` to the integer `(p.x, p.y)` (BDY-33 (e)), so the key is `y_foot`, already floored by `Placement.at`; an actor at 239.6 sorts as 239.
- **Walls, doors, props, machinery nodes**: the south edge of the footprint.
- **Anything mounted on a wall face** (pipes, fittings, seams, gauges, the emissive overlay, wall trails, bead, plate, scar): its host face's sort origin, drawn after the face by group order.
- **Doors and doorways (TR-pxl-007).** `sort_y = y_0` (the footprint's north edge) when the doorway is open, and `sort_y = y_0 + WALL_FOOTPRINT_DEPTH` when it is closed (a closed door sorts as a wall). The projector computes it in `DoorSort.sort_y(y0, open_extent_px)` (a pure function) from Layout's `door_passage_into(section_id, via_id, out)` record (`open_extent_px`, ADR-0013 § 8 and § 11), and writes the leaf sprite's placement (the rule below) through `Placement.put` when it re-reads the leaf on a `LEAF/<section_id>` key (ADR-0013 § 8 marks LEAF whenever a leaf rect changes, and `area` leaving zero changes the leaf rect). Reading the Layout record, not the Graph, means the Layout projector subscribes to `layout.state` alone (the Graph dirties keys every step and would wake stage 0 needlessly) and needs no edge-id reverse lookup; for a mated hatch the record is read once per section, so both leaves agree. **Equivalence with `area > 0`:** D.5 defines `open_extent_px = gap(area)`, which is 0 when closed and positive for every `area >= 1` provided the authored `area_max` does not exceed the doorway width in px; a larger `area_max` would draw a barely-open leaf at its closed edge, so ADR-0013 carries the template BOOT invariant `area_max <= doorway width in px` (`CONTENT_INVARIANT`, ruling CT-14; OQ-E closed). The leaf sprite's drawn extent equals the leaf rect with no tween (TR-section-013).

**Sprite placement rule (T8).** A sprite is placed by `position = (x0, sort_y)` through `Placement.put` (body frame: `section_offset(section_id) + local_origin`, § 5), `centered = false`, and `offset = (0, y0_rect - sort_y)`, **both written in the same `present` call**. `y0_rect` is the top of the sprite's rect, so the drawn texture covers exactly the rect (TR-section-013) while the node's position carries the sort key. When a door opens or closes, `sort_y` moves by `WALL_FOOTPRINT_DEPTH`; because `offset` is rewritten in the same present, the drawn rect does not change (no 24 px jump for a frame). Test: toggle a door, assert the drawn rect (`position + offset`) is unchanged while `sort_y` moved by `WALL_FOOTPRINT_DEPTH`.

**3.2 The tile convention (a GDD-sync item, PR-5).** The engine measures `y_sort_origin` from the **cell centre**, not the cell top (V3). The GDD text "set to the footprint depth, not 0" is therefore right only for one cell convention. This ADR pins it: **wall-face and wall-mounted `TileMapLayer`s use a cell height of `WALL_FOOTPRINT_DEPTH`** (one 24-row GRID_24 row; the cell width is the art bible's cell rule and does not enter the key), `TileData.y_sort_origin = 0` on every tile, and the **layer's** `y_sort_origin = WALL_FOOTPRINT_DEPTH / 2` (one value per layer; boot invariant `WALL_FOOTPRINT_DEPTH` is even). A wall whose footprint is rows `[y0, y0 + WALL_FOOTPRINT_DEPTH)` sits in cell row `y0 / WALL_FOOTPRINT_DEPTH` (GRID_24), so its key is `y0 + depth / 2 + depth / 2 = y0 + depth`, the south edge, and the PR-5 acceptance example (footprint rows 240 to 264, key 264) holds. The 72 px face and 24 px cap art is taller than the cell and hangs up-screen through the tile's `texture_origin`, which does not enter the key (V3). The floor and cap layers are never sorted, so they need no origin.

**3.3 `SortedLayer`: how `(class_rank, entity_id)` order is kept.**

```gdscript
# src/presentation/projector/sorted_layer.gd
class_name SortedLayer extends RefCounted
## Wraps one sorted group node. Sprite children are kept in ascending (class_rank, entity_id); the parallel arrays hold the order.
## The group's TileMapLayer children are a PREFIX of its child list (LayerOrder below); every child index here is `layers.count() + array index`.
var _nodes: Array[Node2D]
var _rank: PackedByteArray
var _eid: PackedInt64Array
var layers: LayerOrder                                               ## the group's tile-layer prefix; its count() is the index base
func insert(node: Node2D, class_rank: int, entity_id: int) -> int   ## OK or ERR_DUPLICATE_ID; binary search, add_child, move_child to layers.count() + index
func remove(node: Node2D) -> bool                                     ## removes from the parallel arrays; does not free
func merge_from(other: SortedLayer) -> void                           ## one pass: both inputs are sorted, so compute final indices (base layers.count()), then move_child once per node
func count() -> int

# src/presentation/projector/layer_order.gd
class_name LayerOrder extends RefCounted
## The TileMapLayers of one band group, kept as the first children in ascending section_id. Used for all four layer-bearing groups (Floor, Faces, Mounted, Caps).
var _layers: Array[TileMapLayer]
var _sid: PackedInt32Array
func add(layer: TileMapLayer, section_id: int) -> void   ## add_child (or after SceneMove.to), then move_child(layer, rank among layers)
func remove(layer: TileMapLayer) -> void                 ## does not free
func count() -> int
```
`insert` finds the index by binary search over `(rank, eid)`, calls `add_child` and then `move_child(node, layers.count() + index)`; a duplicate `(class_rank, entity_id)` is refused (counted as `diag.sort_id_collision`, which must stay zero) rather than silently ordered by tree position. `merge_from` serves the weld: the survivor's and the absorbed body's `PropsActors` are each already sorted, so the merged order is one linear pass followed by one `move_child` per node (V9: 100 moves cost 0.05 ms on the dev machine).

**The order guarantee covers TileMapLayer children too (E2, T4).** `reparent(p, false)` appends the moved node as the **last** child (V5), so after a weld a moved section's layers would sit after the existing sprites and `move_child` indexes in `SortedLayer`'s array would be off by the number of layer children; and two sections' layers at an equal key would tie by weld history, not by `section_id`, which changes after a save and reload (a reload rebuilds in ascending `section_id`). The **LayerOrder step** therefore runs in `SceneMove`'s caller (`body.projector`) after every mount, move and removal: the group's `TileMapLayer`s are `move_child`-ed to the front, ordered by ascending `section_id`, and `SortedLayer`'s index base is `layers.count()` (the tile layers are a prefix of the child list, then the sprites). In `Mounted` this realises "rank-1 tiles first, then rank-1 sprites"; in `Floor`, `Faces` and `Caps` it makes cross-section layer order a function of the persisted `section_id`. Ties **inside** one layer are the engine's own and are deterministic: same-row cells tie by x, higher x on top, independent of `set_cell` order and unchanged by a reparent (V10, review probe). **Tiles carry no `entity_id`**; the cross-layer and layer-versus-sprite ties resolve by `section_id` (layers) and then `(class_rank, entity_id)` (sprites), never by mount order. `ProjectorAudit` checks this with a tree walk (the merged boot walk: layers precede sprites in every group, layers ascending by `section_id`) and `rebuild_signature()` includes the **ordered child list per group** (§ 7).

**3.4 Cross-body equal keys (a stated exception).** Within a body the order is exactly the contract. Across two bodies whose interiors are both drawn (docked, WM-19) an equal key with overlapping sprites falls to `BodyRoot` order, ascending `body_id`, which the projector maintains with `move_child`. For Layout pieces that coincides with ascending `entity_id` whenever section ids and body ids were allocated in the same order, which holds for the MVP builds (`init_world` builds home first); it is not guaranteed after cuts. The region where this can occur is the mating seam of two docked hulls. It is tested as a bounded exception (AC-123 (b) is run within one body; the cross-body case is a recorded SP-YSORT-1 observation, § 11) and listed in Risks.

### 4. `entity_id` and its namespaces

`entity_id` is **a presentation sort-key composite**, not a block id. It is a pure function of persisted ids, so it is identical in a live build and a restored one and is never stored. ADR-0003's rule (ids are block-local, cross-block references are `(block_id, entity_id)`) is unchanged.

```gdscript
# src/shared/entity_id.gd (L0: pure ints, no engine types; sim modules and presentation both may call it)
class_name EntityId extends RefCounted
const NS_SHIFT: int = 56
const LOCAL_MASK: int = (1 << 56) - 1
static func pack(ns: int, local: int) -> int           ## (ns << 56) | local; ns in 1..127; local in 0..LOCAL_MASK; asserts in debug, returns 0 (invalid) otherwise
static func ns_of(id: int) -> int
static func local_of(id: int) -> int
static func layout_local(section_id: int, kind_ordinal: int, idx: int) -> int   ## (section_id << 24) | (kind_ordinal << 16) | idx
# src/shared/entity_ns.gd : the namespace table (append-only; a golden test pins it)
class_name EntityNs extends RefCounted
const LAYOUT: int = 1       # door leaf, jamb, prop, machinery, bead, plate, scar sprites
const BODY: int = 2         # actors (local = actor_id)
const INTERACTION: int = 3  # loose items, deployables (local = item_id)
const HORROR: int = 4       # horror rigs (local = horror entity_id)
const SUIT: int = 5         # empty suits and carried-and-dropped suit props
const WEB: int = 6          # off-floor web pieces
const TRAIL: int = 7        # trail sprites (local = the Graph subject key)
const LIGHTING: int = 8     # attached lights: a registration key for BodyScenes.attach_light (local = the seat's beam id); never a sort key
# 9..127: reserved, append-only (no renumbering, ever; a golden test pins the table)
```
- **The sign.** A namespace byte of 1 to 127 keeps every id positive in GDScript's signed 64-bit `int`, so ids compare as plain integers (the Pipeline never needs an unsigned compare). `0` is invalid.
- **Layout's local part** is LY-31's: `section_id` below `2^20` (ADR-0013 § 3 guarantees it), `kind_ordinal` in 8 bits, `idx` in 16 bits (the rect `idx` or the template placement index, below the rect stride, ADR-0013 § 13). **`kind_ordinal` ownership split (ruling CT-14).** ADR-0013 § 13 owns *which kinds* are in the closed vocabulary (door leaf, jamb, prop, machinery, bead, plate, scar: it adds `JAMB`); this ADR owns the *numbers*, assigned append-only by this section: `DOOR_LEAF 1`, `PROP 2`, `MACHINE 3`, `BEAD 4`, `PLATE 5`, `SCAR 6`, `JAMB 7` (TR-assembly-045 requires jambs; OQ-C closed). Class ranks: `BEAD`, `PLATE`, `SCAR` are rank 1 (the wall-mounted layer, LY-33); `DOOR_LEAF`, `JAMB`, `PROP`, `MACHINE` are rank 2. **Local `idx` of bead and scar sprites (T9d):** they come from `welds[]`, not from a template placement, and the seam is shared by two sections, so the rule is fixed: a bead or a scar uses the **reserved PLATE slot `idx` of the socket on the lower `section_id` side** of the seam, and **only that side's `SectionScene` builds it**. Two beads or a duplicate-id refusal therefore cannot occur; the other side builds none.
- **Other publishers' local parts** are their own persisted ids: Body's `actor_id` (an `int64` counter, asserted below `2^56`), Interaction's `item_id`, Horror's `entity_id`. Each publisher calls `EntityId.pack` itself; Layout exports no helper (ADR-0013 § 13), so the Layout projector packs, using only persisted ids.
- **Ordering consequence.** At an equal key and rank, namespaces order ascending: a Layout prop draws before an Interaction item, a Body actor before a horror. That is deterministic and save-stable; it is a convention, not a design claim.
- **Guard.** `SortedLayer.insert` refuses a duplicate `(class_rank, entity_id)`; a golden test pins the namespace table (append-only: a later ADR adopts its byte or requests an append, never a renumber, T6); a lint forbids `EntityId.pack` with a literal namespace outside `entity_ns.gd` (`PJT-08`). Registration of an attached node in `BodyScenes` is keyed by `(ns, local)` for every namespace; only the sorted groups use it as a sort key.

### 5. Section scenes: per-section layers, one atlas each

**Per-section `TileMapLayer`, decided by arithmetic.** Section offsets lie on the 24 px grid and welded sections are placed by `offset_b = offset_a + pos_a - pos_b` (ADR-0013 § 7). The registry's MVP pair gives a 696 px offset, which is 14.5 floor tiles, so the cells of two welded sections do not share one 48 px cell grid and **no single per-body tile map can hold both**. Each section therefore owns its own layers, positioned at its integer `section_offset`. Other reasons point the same way and are secondary: a `SEC` change, a discard (LM4) or a dormancy change rebuilds or frees one section only; the maintained and `_worn` atlases (DA-5) differ per section, so a merged layer would mix two atlas sources (a draw-call cost, V8, but not the basis of this decision: the 24 px grid argument above settles it alone).

**The layers per section** (up to four `TileMapLayer`s, each `tile_set` shared across sections of the same atlas set and layer kind through a `TileSetCache` keyed `(atlas_set, layer_kind)`):

| Layer kind | Group | Sorted | Cell | `y_sort_origin` |
|---|---|---|---|---|
| floor | `Floor` | no | `TILE_PX` square, `rendering_quadrant_size` 16 (ADR-0008 § 7.1) | n/a |
| wall face | `Faces` | yes (`y_sort_enabled`) | height `WALL_FOOTPRINT_DEPTH` | `WALL_FOOTPRINT_DEPTH / 2` on the layer |
| wall mounted | `Mounted` | yes | height `WALL_FOOTPRINT_DEPTH` | same |
| cap | `Caps` | no | 48 x 24 slices (PR-5 z-band table) | n/a |

**One atlas source per layer (a production rule, T10).** Each `TileSet` used by a layer holds exactly one `TileSetAtlasSource`. The narrow rationale: batching follows texture runs along the draw order (V8), and a layer that alternates two sources by row is the worst case for those runs (440 calls in the **unsorted** probe, 23 when the same layer was y-sorted); with one source per layer a layer contributes at most one run per contiguous stretch. Sprites use `AtlasTexture` regions of the same sheet so they batch with it; a `_worn` section uses the `_worn` sheet, so a draw-call boundary appears at the section boundary only. This rule does **not** bound `D_ysort`: actors, items, horror rigs and trails use other sheets, and the number of distinct textures per row across `Faces`, `Mounted` and `PropsActors` is the real driver (§ 10, R4). It is a production rule for the asset spec (art bible 8.4 to 8.6) and a boot check in the `TileSetCache`.

**Atlas selection by template (TR-derelict-028, DA-5).** A presentation table `assets/data/presentation/atlas_map.json` (a new data domain for ADR-0007; integer-only, closed schema, manifest-listed) maps `template_id` to `atlas_set` in `{MAINTAINED, WORN}`. The projector selects the sheet by `template_id` read from `layout.state` and the map; **no Layout field carries wear** and the kit manifest rows name no template, so procgen can reuse them. Boot lints: `ATLAS_MAP_TEMPLATE_UNKNOWN` and `ATLAS_MAP_MISSING` (every catalog template has exactly one row). The table is not persisted and has no ledger.

**Sprites** (door leaves, jambs, props, machinery nodes, bead, plate, scar pieces) are built from the rect table and the template's visual rows (kit-piece ids and layers, the `visual_hash` part of the frozen template, ADR-0013 § 4), not from tiles. Each carries `entity_id = EntityId.pack(EntityNs.LAYOUT, layout_local(section_id, kind_ordinal, idx))` and its class rank from § 4. Socket-state sprites (PLATE, JAMB, LEAF, bead, scar) are rebuilt from `welds[]` and the socket rows on `SEC`, `SEAM` and `LEAF` keys.

**The rect read and the frame rule (T1, ruling CT-18).** The projector calls ADR-0014's real signature, `section_rects_into(section_id, mask, out)` (`mask` is the caller's `RectFlags` mask). Rows are in the **body frame** and are **occupied spans**: `(x0, y0, x1 - 1, y1 - 1)`, so a sprite's width is `span + 1` (using the span as a half-open rect would leave every sprite 1 px short and break TR-section-013); each row carries `key = section_id * RECT_KEY_STRIDE + idx` and a flags byte, and `idx = OccluderSource.idx_of_key(key)` (ADR-0014 adds the read because `/` and `%` are banned outside `IntMath`; `idx` is not a column). A row whose current extent is empty is omitted, so the consumer **hides** that sprite. The kind (JAMB, PLATE, LEAF and so on) is derived from the reserved `idx` ranges of ADR-0013 § 5. **Each `SectionScene` converts to section-local px once, at build, by subtracting `section_offset_x/_y(section_id)`, and stores every sprite's section-local rect** (`sprite_local`: four ints per sprite). Thereafter a sprite's body-frame position is **never** moved by adding a delta: on build, mount, weld, cut and re-base, `body.projector` writes `position = section_offset(section_id) + local_origin` through `Placement.put`, **recomputed from the current offset** (`local_origin` from the stored local rect and the placement rule of § 3.1). A sprite built before a weld and one built in the same frame as the weld therefore get the same position as a fresh `ALL` build. A **staged** scene whose section received a `BODY` or `SEC` key during its build recomputes every position at commit, so a chunked build that straddles a weld, cut or re-base cannot commit sprites in the old frame.

**Two projectors, one handoff (rulings CT-34, CT-55).** The two PROJECTOR subscribers are one pair with a declared same-stage handoff object, the `SectionScene` (a Foundation amendment to ADR-0009 § 1, listed under Depends On): `LayoutProjector` registers `PresenterDescriptor(name = &"layout_projector", stage = PROJECT, reads = [], after = [])` and `BodyProjector` registers `(name = &"body_projector", stage = PROJECT, reads = [], after = [&"layout_projector"])` (`reads` lists earlier stages, and the handoff is same-stage, hence the amendment rather than a `reads` entry). **The rule:** the Layout projector creates nodes **only in `Staging` or through `SectionScene` methods**; **all parenting and `SortedLayer` insertion under a body root goes through `body.projector`**, which may be invoked through the `SectionScene`. ADR-0009 registers the layout projector first, then `body.projector`, which would force a body root to exist before the Layout projector could parent into it; that is avoided by having the Layout projector build **into the hidden `Staging` holder** and never into a body root. A `SectionScene` exposes `mount(...)`, `unmount()`, `swap_in(...)` and `add_sprite(...)` and `body.projector` executes them: when the Layout projector builds a replacement layer or a new socket-state sprite for a scene that is already mounted, it hands it to the scene (`stage_swap`, `add_sprite` queue the node in `Staging`), and `body.projector`, which runs second in the same stage-0 pass, performs the parenting, the `LayerOrder`/`SortedLayer` insertion and the position write in its own pass. The registration order of ADR-0009 is therefore unchanged and sufficient.

```gdscript
# src/presentation/projector/section_scene.gd

var complete: bool                # all work units done and committed (data only: nothing has rendered, V10 f)
## Called by body.projector only (the Layout projector may invoke them through the scene, which forwards to body.projector's pass):
func mount(body_root: Node2D, groups: BandGroups, section_offset: Vector2i) -> void   ## LayerOrder.add the four layers, insert sprites, recompute positions
func unmount() -> void                                                                ## moves everything back to Staging; frees nothing
```

### 6. Building: work units, staging, atomic commit, readiness

**Work unit.** One `TileMapLayer.set_cell` call or one sprite node created and configured is one **work unit**. The knob `BUILD_TILES_PER_FRAME` (a Layout GDD tuning knob, read from the frozen `LayoutTuning` table, ADR-0007 § 1.5; the module source carries no literal) is the units per `present` call. The unit is named after tiles because tiles dominate (the GDD's tile counts for the MVP world and for the largest destination scene are its sizing basis); sprites are counted in it so that "builds N tiles in at most M frames" (TR-section-024) remains true with sprites included. The number of frames for a build of `U` units is `ceil(U / BUILD_TILES_PER_FRAME)`, plus one if the final commit needs its own `present`. **`U` counts data work only.** `BUILD_TILES_PER_FRAME` bounds `set_cell` and node configuration; it does **not** bound the engine's canvas-item build of a layer, which happens in one unchunked deferred burst when a layer first becomes visible in the tree, i.e. at mount (V10 f). That burst is the **mount term `R_mount`** (about 0.9 us per cell on the dev machine, unmeasured for Deck). It is declared **unchunked and counted in frames, not in units**: scenes are mounted **one scene per `present` call** in ascending `section_id`, so an arrival or restore of `S` scenes takes `ceil(U / BUILD_TILES_PER_FRAME) + S` frames at most (the mounts may overlap the tail of the data build), and `ARRIVE_SETTLE_TICKS` is sized to that count (GDD Sync). The per-scene burst is bounded by that scene's cell count and is measured by SP-YSORT-1 (V9').

**Order, inside one section.** Floor cells, wall-face cells, mounted cells, cap cells, then sprites in ascending `(kind_ordinal, idx)`. Sections build in ascending `section_id`. A chunk may end at any unit.

**Staging and atomic commit.** A new or rebuilt section builds under the `Staging` holder (in the tree, `visible = false`, so the orphan delta stays zero in the editor and debug runner, V7) and `complete` flips only on the last unit. **`Staging` is a data stage only:** the engine builds nothing for a layer that is not visible in the tree (V10 f), so staging does not pre-warm rendering and chunking does not hide the real build, which lands at mount. `body.projector` mounts a scene only when `complete`, in one pass, so no frame draws half a section (the mount's own rebuild is the unchunked burst `R_mount` of the work-unit paragraph above). A rebuild of an already mounted section (a salvage that changes its template-visible state) builds a second set in `Staging`, keeps drawing the old set until the last chunk, then swaps (`swap_in`, executed by `body.projector`) in one apply; the same "old complete state keeps drawing" rule ADR-0009 § 2 states for the PROJECTOR. For a **restore, new game or `ALL`** the rule is satisfied differently (§ 7): the roots are rebuilt under ADR-0008's load hold, which is held until `ProjectorReadiness.is_ready()`, so no partial interior is ever visible. This ADR adds no exemption to the chunk budget for the Layout projector or `body.projector`: the single-chunk in-reach exemption in ADR-0009 § 1 belongs to Lighting's occluder builder only.

**What is not chunked.** Anything a weld or cut needs in the first frame: reparenting nodes and recomputing their positions (§ 7), the engine's deferred rebuild of the reparented layers (`R_weld`, charged to the weld budget), the socket-state sprites (bead, jambs, leaf, plate, scar: a handful of sprites, not tiles), root creation and freeing, a `BodyRoot.visible` flip (`R_flip`, § 8), the limits publish. These run in the stage-0 call that follows the notification, so the bead is drawn in the first rendered frame whose committed tick is at least the apply tick (TR-assembly-045); no bead sprite exists while `welds[]` has no row because the sprite set is built from `welds[]` and nothing else. The "last-projected cache" of the door leaf (ADR-0013 § 8) is read, not written, by the projector.

**Readiness.**

```gdscript
# src/presentation/projector/projector_readiness.gd (value-like; written by the two projectors, read by PipelineRoot)
class_name ProjectorReadiness extends RefCounted
var scene_epoch: int          # +1 on every complete commit or mount change
var pending_units: int        # work units still queued, all bodies in the ProjectionSet
var late_count: int           # ARRIVE_SCENE_LATE occurrences (DIAGNOSTIC only, never a SIM notification)
func is_ready() -> bool       # pending_units == 0 and every ProjectionSet section is complete and mounted
```
`PipelineRoot` reads `is_ready()` for the TRANSIT_HOLD latch (WM-14: "the Pipeline may cut to the avatar once its own projector latch also holds") **and for the load hold (CT-33): ADR-0008 shows the `HoldLayer` while the kernel is `LOADING` and is asked to keep it until `ProjectorReadiness.is_ready()`**, not until `RUNNING`; this covers cold loads from the title screen, where no old roots exist, and costs one condition in ADR-0008 (the Foundation side is a requested amendment, listed under Depends On). When `DERELICT_LOADED` (or the arrival's `pod_settle`) is delivered while `is_ready()` is false, the projector increments `late_count`, logs `ARRIVE_SCENE_LATE`, and keeps building; the simulation is never delayed (E-19, TR-webmap-037). The arrival's worst-case build is the largest destination scene, home plus the welded derelict; its frame count is `ceil(U / BUILD_TILES_PER_FRAME) + S` with `U` counted from the real sections (a test builds it through `build_section`, not a hand sum) and `S` the number of scenes mounted one per `present`, and `ARRIVE_SETTLE_TICKS` must cover it by the Web Map lint formula, whose numerator becomes the projector's work-unit count (tiles plus sprites) of the largest destination scene plus the mount frames `S`, not tiles alone (GDD Sync). The wall-time of each mount burst (`R_mount`) is UNVERIFIED on Deck.

**The projection set.** Scenes exist exactly for the sections the `ProjectionSet` names: the avatar's body (so the pod interior exists during a leg), the loaded set, and the arrival target while `ARRIVING` (it is still dormant then, WM-14). `body.projector` reads the avatar's body as `body_of_actor(actor_of_seat(local_seat))` from `BodyView` (the seat is injected at `setup()`), and the rest from a Web Map read (an assumption on ADR-0026: `web.view` publishes `projection_sections_into(out: PackedInt32Array) -> int`, ascending, including the arriving target). A section leaving the set is **freed** at the end of the next stage-0 pass, not hidden (a departed destination is rebuilt on return, which is the case the GDD sizes `ARRIVE_SETTLE_TICKS` for); retaining hidden scenes is a possible later knob, not built. **Before any scene or root is freed** (a `ProjectionSet` exit, a dissolved or dead body, a restore, `ALL`), `body.projector` runs the **parking step** of § 7.2: every foreign attachment of the section or body is parked in `Staging` and keeps its registration, and an attachment whose section or body no longer exists is told so through its `on_orphaned` notification.

### 7. Weld, cut, pod hop, restore: reparent and shift, rebuild as the reference

**Decision.** On a weld or cut the projector **moves** the affected sections' existing nodes to their new body root and recomputes their positions from the current `section_offset` (§ 5); it **re-authors no tile** (no `set_cell`, no chunked build). It does not follow that nothing is rebuilt: on 4.7.2 reparenting a `TileMapLayer` makes the engine rebuild every cell once, in the deferred internal update that follows (V10), so a weld costs about 0.9 us per cell per moved layer on the dev machine (453 sorted cells about 0.4 ms), unchunked and unmeasured for Deck. That engine rebuild is the weld budget term `R_weld` (§ 11). Re-authoring the whole destination scene on every weld was rejected (Alternative 4): it spends a chunked build **and** the same engine rebuild, shows a frame boundary, makes two code paths for the same tree anyway, and gives no benefit because a moved section's geometry does not change. A zero-rebuild alternative (a permanent per-section parent, Alternative 10) is recorded as the remedy if `R_weld` is measured over budget.

**The primitive.**

```gdscript
# src/presentation/projector/scene_move.gd
class_name SceneMove extends RefCounted
## The one way to change a presentation node's parent. Local position is kept (reparent(p, false), probed; remove_child + add_child is equivalent). Never the one-argument reparent.
static func to(node: Node, new_parent: Node) -> void:
	node.reparent(new_parent, false)
```
`Node.reparent(p)` with its default `keep_global_transform = true` rewrites the local position (V5), which would put a moved sprite at the wrong place, so it is banned outside this helper (`PJT-04`); TR-shipbody-032's "without using global-transform-preserving `Node.reparent`" is satisfied literally. The primitive is `reparent(p, false)`, the sanction ADR-0009 is asked to reword (it said "without `Node.reparent`", CT-35). After a move the node is the last child of its new parent; `LayerOrder` (for tile layers) and `SortedLayer` (for sprites) re-establish order. For a `TileMapLayer` the call also costs the engine's deferred cell rebuild (V10), which is why a layer is moved only on a weld, a cut or a mount and never speculatively.

**Weld (`AttachResult`, ADR-0013 § 7; `BODY_TRANSFER{weld}` and `BODY_DOCK_CONTACT`, ADR-0015).** In the stage-0 call that follows the notification, `body.projector`:
1. Reads the new `bodies[]` and `section_offset` of each section (Layout views); the weld carries **one** frame shift per weld (`AttachResult.frame_shift_x/_y`, ADR-0013), but no step below needs it, because positions are recomputed from the offsets. For every `SectionScene` whose `mounted_body_id` differs from `body_of(section_id)`, `new_offset = section_offset(section_id)`.
2. Moves the scene's four layer nodes to the matching group of the survivor root with `SceneMove.to`, writes each layer's `position = new_offset` with `Placement.put`, and runs the **LayerOrder step** (§ 3.3) on each affected group so the layers are again a prefix in ascending `section_id` (the engine rebuild of these layers is `R_weld`).
3. Moves the scene's `layout_sprites` to the survivor's `Mounted` or `PropsActors` `SortedLayer` according to class rank (index base `layers.count()`), using `merge_from` so order is one pass, and writes each sprite `position = new_offset + local_origin` with `Placement.put` (recomputed from the stored `sprite_local`, **never** `position + delta`, so a sprite built before or in the same frame as the weld ends at the same place as in a fresh `ALL` build, T1).
4. Moves every **foreign attachment** whose registered `section_id` is a moved section with `SceneMove.to`, and every attached Presenter and `LIGHTING` node whose actor has a `BODY_TRANSFER` record to the destination (§ 8, the BODY_TRANSFER pass). Position ownership: actor-following nodes and Horror rigs are rewritten by their **owning presenter** in the same frame before draw (stages 2 to 7 run after stage 0); the projector writes none of them. Section-bound static attachments (Trail marks, dropped items, suit props, off-floor web pieces), whose owners write only on their own dirty keys, are re-placed by the projector with `Placement.put` as `new_offset - old_offset + position` (a shift of the node by the section's offset change; the one stated exception to "the projector writes no foreign position", an ADR-0009 write-list request in Open Questions).
5. **Socket-state sprites** (bead, jambs, leaf, plate, scar) the weld changed were built by the Layout projector earlier in the same stage-0 pass (it runs first, § 5), unchunked, from `welds[]`, the socket rows and `section_rects_into`, **as nodes created in `Staging` and handed to the `SectionScene` through `add_sprite`/`stage_swap`**: the Layout projector parents and inserts nothing under a body root. `body.projector` drains `pending_sprites` here, after steps 2 and 3, inserts them into the post-weld `SortedLayer`s and writes their positions from the current offset. The bead and scar are built by the lower-`section_id` side only (§ 4).
6. Frees the dissolved body's root after the **parking step** (§ 7.2) confirmed no foreign attachment is still a descendant (its groups are empty by now; a non-empty group is a defect, counted `PJT_ROOT_NOT_EMPTY`), recomputes and publishes `CameraLimits` (§ 9), updates every root's canvas offset (the canvas origin is now the survivor's frame), and bumps `scene_epoch`.

The weld frame's cost is therefore proportional to nodes moved and cells re-rendered: the reparent and `move_child` calls, plus the engine's deferred rebuild of each moved layer's cells (V10), which is the term V9's call-only timing omitted. The node count after a weld equals the count before minus one root (checked by the tree-walk `ProjectorAudit.enumerate_into` on every build, and as an orphan-monitor **delta** in the editor or debug runner only, V7, AC-BDY-92). The sort order of any sprite relative to a wall is unchanged because every key shifts by the same constant (the canvas origin change) and within-body relations are preserved; exact equal-key ties across the two bodies are the § 3.4 exception.

**Cut (`DetachResult`, ADR-0013 § 7).** The mirror: a new `BodyRoot` for the new `body_id`, the moved components' scenes and foreign attachments moved by the same steps 2 to 5 (positions recomputed from the re-based `section_offset`, never `position + delta`; the one frame shift of the `DetachResult` is not needed), `BODY_TRANSFER{detach}` actors and `LIGHTING` nodes moved, limits recomputed for the avatar's body, and the new body's interior is hidden unless the avatar is on it (WM-19; hiding costs nothing and the later show is the `R_flip` rebuild, § 8). The engine rebuild of the moved layers is `R_weld` again.

**Pod hop.** Nothing is built or moved (a pod hop builds nothing, Web Map CF-LY); `BODY_TRANSFER{pod}` moves only the actor's Presenter node and its `LIGHTING` nodes (the BODY_TRANSFER pass, § 8), and the camera cuts (ADR-0008 § 6.1). The canvas origin changes to the new avatar body, so every root's canvas offset is rewritten.

**Restore, new game, `ALL` (CT-33).** `on_discontinuity(RESTORE)` first runs the **parking step** (§ 7.2), then frees every scene and root, then rebuilds from the views through the same build path (staged, chunked, atomic, mounted one scene per `present`), and re-mounts each parked attachment when its body or section is mounted again. The roots are rebuilt **under the pipeline's load hold, which ADR-0008 releases only when `ProjectorReadiness.is_ready()`**: the interior is never drawn partially, which is the intent of ADR-0009 § 2 (keeping the old roots drawing was rejected: it does not cover a cold load, where no old roots exist). `snap_baseline` has made previous equal current, so nothing interpolates across the break. A scripted weld, cut and pod sequence through an incrementally updated projector and a fresh projector fed `ALL` must give equal `rebuild_signature()` values, **which include the ordered child list of every band group** (layers by `section_id`, then sprites by `(class_rank, entity_id)`, T4), compared as an ordered list and not as a multiset (the AC-121 multiset check alone cannot see an order difference). This is the ADR-0009 § 2 safety net, mandatory here: the projector is the first key-level incremental presenter whose two paths differ in kind.

**7.2 Parking foreign attachments (CT-33, T2).** Freeing a `BodyRoot` also frees every node attached under it, including the Avatar Presenter, Trail, Interaction, Horror and Suit nodes, which contradicts the rule that the projector never frees a node another presenter attached. So **before any root or scene is freed** (restore, `ALL`, a `ProjectionSet` exit, a dissolved or dead body), `body.projector` **parks** every foreign attachment of what is about to be freed in `Staging` with `SceneMove.to`, and **keeps its registration** `(body_id, section_id, rank, entity_id)`. When the attachment's body or section is mounted again, the projector re-mounts it into the correct group (`LayerOrder`/`SortedLayer` order restored; the owner rewrites an actor-following node's position in the same frame). For a parked attachment whose body or section **no longer exists** (a section discarded, a body dissolved or dead), the projector calls the attachment's declared `on_orphaned` notification (set at `attach`, a `Callable` taking the node), after which the owner decides to re-attach or free; a parked node with no owner response for a frame is counted `PJT_ATTACH_ORPHANED`, never freed by the projector. A parked node sits in the hidden `Staging` holder, which is in the tree, so it adds no orphan.

**7.1 The attach API (generalising `attach_presenter`).** Other presenters need a sanctioned way into the projector's tree so that reparent-on-weld is uniform. `BodyScenes` is declared a **mutation facade** under the ADR-0009 exception (CT-34): later-stage presenters (stages 2 to 7) may call exactly `attach`, `attach_presenter`, `attach_light`, `detach` and `rebind` on this stage-0 product, and it exposes **no getter of the projector's private state**. (Recorded as an accepted widening, not drift: ruling CT-34 named "attach, detach, rebind only"; `attach_light` follows CT-32 and `attach_presenter` follows ADR-0019, so the facade is five calls.) **Ruling R8 (2026-10-29): this § 7.1 owns the `BodyScenes` call list (`attach`, `attach_presenter`, `attach_light`, `detach`, `rebind`); the ADR-0009 amendment and every other ADR cite it and do not restate it.**

### 8. Body roots: canvas offset and visibility

**Canvas offset (the formula ADR-0015 hands to this ADR).** For every body root, with `avatar_body` the avatar's current body, `off_curr(b) = world(b) - world(avatar_body)` and `off_prev(b) = world_prev(b) - world_prev(avatar_body)` using the **current** avatar body for both terms (so a body switch never interpolates across two reference frames), and `position = Placement.at(off_prev, off_curr, frame.alpha)`, written with `Placement.put` in stage 0 (`world`, `world_prev`, `vel` come from `BodyView`; `world` is exterior-only and bounded by `WORLD_COORD_LIMIT`, so every offset is within `2^23` and exact in `float32` under ADR-0015's published bounds: `BODY_COORD_LIMIT` (at most 2^24, restore-checked, repeated in Layout's `can_attach`) and `|world_a - world_b| + |pos| < 2^23` under `WEB_COORD_BUDGET_PX`, otherwise `WORLD_COORD_LIMIT` is lowered, CT-24). The avatar's body root is at (0, 0). A root whose offset did not change costs one skipped write.

**The BODY_TRANSFER pass (rulings CT-32, T7).** In stage 0, **before stage `AVATAR` (2)**, for each `BODY_TRANSFER` record `body.projector` reparents, in one pass and through `SceneMove` (`reparent(p, false)`), the actor's Presenter node **and every `LIGHTING` node of that actor** (keyed by the seat's beam id) to the translation-only `BodyRoot` of `BodyView.body_of_actor(actor)`. `reparent` would preserve the global transform by default (V5); `keep_global_transform = false` keeps the local position instead, and **the projector writes no actor-following node's position**: the position owner rewrites the position from `BodyView.pos_x/pos_y` in the same frame, before draw: the Avatar Presenter at stage `AVATAR` 2, which writes its own node with `Placement.put` and the beam `Light2D` with `Placement.put_light_origin` (ADR-0018 § 4.1); the Lighting presenter at stage `LIGHTING` 6 builds, attaches (`attach_light`) and frees the beam node but writes neither its `position` nor its `rotation` (it writes `offset`), and both stages run after stage 0. A **dev assertion** (`projector_reparented_not_rewritten`, checked at the last presenter stage) requires that every node reparented this frame received an owner position write before draw: `Placement.put` for a Presenter or other non-light node, `Placement.put_light_origin` for a `LIGHTING` node (the beam position is never written through `Placement.put`). The beam `Light2D`'s parent is therefore always `BodyRoot(body_of_actor(actor))` (ADR-0018 SHO-04 asserts it on every dev frame; ADR-0015 V8 is answered by this probe: `keep_global_transform` false, owner rewrites position). A mobile owner calls `BodyScenes.rebind` when its own section changes (§ 7.1).

**Visibility (WM-19, defence in depth).** `BodyRoot.visible = InteriorDrawRule.visible(b, avatar_body, ...)`: true for the avatar's body and for a body docked or welded to it; false for a body drawn only as an exterior silhouette (those are not this tree). The rule is a pure function with injected inputs so it is unit-testable; its docked input is a Web Map read (an assumption on ADR-0026). Hiding a root hides its subtree and its lights' occluders are Lighting's concern. **Decision: WM-19 uses `BodyRoot.visible`; the projection set does not free and rebuild on a flip.** Cost, per V10 (e): hiding costs 0 rebuilds, but **every false-to-true flip rebuilds every cell under that root** in one unchunked deferred burst (`R_flip`, about 0.9 us per cell on the dev machine, unmeasured for Deck), and a root first shown after being hidden pays a full build. Flips happen on dock, undock and arrival events, never per frame; each is charged to the arrival or dock budget and SP-YSORT-1 measures `R_flip` for the largest root (V9'). If `R_flip` is over budget the remedy is Alternative 10 together with retaining hidden scenes (OQ-F).

### 9. The camera-limit rectangle

- **The split (CT-56, T5).** `body.projector` publishes the **raw hull rectangle** (`CameraLimits`) and is its **only writer**. `PipelineRoot` or `CameraSolver` (ADR-0008 § 3.2 RESCALING step 3, which already re-derives the camera limits rectangle the solver consumes) derives the **effective rectangle** `rect_eff` (viewport-size inflation, easing) from `CameraLimits` and `RenderLayout`. **ADR-0008 owns the clamp rules**: the inner-box-first order, `CLAMPED`, the JOLT rule and `world_to_hud` never offset while clamped; this ADR is asked to have ADR-0008 take them explicitly, because the traceability row for TR-pxl-017 currently attributes them to this ADR and nobody writes them. How `CameraLimits` reaches the solver (a `SolverInput` field, which would change a Foundation type that is the C1 enforcement, or the existing limits path of RESCALING step 3) is ADR-0008's to decide; this ADR does not change `SolverInput`.
- **Value.** `CameraLimits` is a `RefCounted` with `valid`, `min_x`, `min_y`, `max_x`, `max_y` (integers, base px, half-open on the max side), `body_id` and `epoch`. `Camera2D.limit_*` is never written (OQ-C closed, TR-pxl-017).
- **Frame.** The canvas is the avatar's body frame with the avatar's body at the origin (C2), so the rectangle is expressed in the avatar's body frame, which is also the canvas frame.
- **Rectangle.** The **bounding box** of the sections' rects: over `sections_of(avatar_body)`, the per-axis min of the offsets and max of `section_offset + size_tiles x TILE_PX` (the template's `size_tiles`), grown on the **north** edge by `LIMITS_NORTH_OVERHANG = WALL_FACE_PX + WALL_FOOTPRINT_DEPTH` (a derived constant from two registered names; it lets the camera reach the top of the north wall's face and cap, which project up-screen above the footprint, PR-5). The three other edges are the hull envelope: "the void beyond a hull is honest black". No authored rect means `valid = false` and no clamp. The rectangle is **integer base px**.
- **When.** Published in stage `PROJECT` on weld, cut, load, `ALL`, any `BODY`/`SEC` key of the avatar's body, and on a `BODY_TRANSFER` that changes the avatar's body; `epoch` increments on every change so the solver eases a changed rectangle and never pops it, except on a camera cut. Because stage 0 runs before stage 1, the solver consumes the new rectangle in the same frame as the `BODY_TRANSFER` rebase, in the new body's frame.
- **Clamp consequences owned elsewhere.** `CLAMPED` state, `world_to_hud` never offset while clamped, `rect_eff` and the JOLT rule (at most `JOLT_PX`'s range, default 0, P1 events only, inside the viewport, never a container offset) are ADR-0008's; this ADR only guarantees that the projector never moves the camera and never offsets the canvas for a limit.

### 10. The per-row z-band fallback (TR-pxl-009): specified, not built

At MVP the sorted band is the single scope of § 2 and **the fallback is not built**. The reason is a probe-backed expectation, not a measurement: draw calls follow texture runs along the sorted order (V8), and the real driver of `D_ysort` is the **number of distinct textures per row across `Faces`, `Mounted` and `PropsActors`**: actors, items, horror rigs and trails use other sheets, so one atlas per layer does **not** bound it. "A handful of runs per row" is an expectation that needs measuring, not something V8 shows; the GDD's own 50 to 300 estimate is "NOT SOURCEABLE until the spike". SP-YSORT-1 therefore reports **distinct textures per row in the sorted band alongside `D_ysort`**. The decision rule is the GDD's, made explicit:

- **Trigger.** `D_ysort` (the world viewport's draw calls attributable to `Faces`, `Mounted` and `PropsActors`, measured in a dev harness and read as `RENDER_INFO_DRAW_CALLS_IN_FRAME` per viewport) exceeds about 300 on a release export at the default field or at the largest ladder field. **Measurement rules (E4, CT-56):** hiding or showing a group rebuilds its layers (V10 e), so a naive hide/show diff mixes rebuild frames with steady-state frames; the harness reads the count only **after the show has settled for at least 2 frames**, or diffs against a dev flag that skips adding the groups instead of toggling `visible`. Whether `get_render_info` is populated on a release export is **UNVERIFIED** and gated on SP-YSORT-1; ADR-0008 owns the draw-call table.
- **Go/no-go.** The fallback is built only if, in the spike room with the flag on versus off, **both** the world viewport's draw calls **and** frame CPU time are lower and the two pictures are bit-identical outside declared animating-source rectangles; otherwise it is withdrawn and the Pipeline's per-field draw caps (ADR-0008 § 7) apply. This ADR does not decide the measurement; SP-YSORT-1 and the Pipeline story do.
- **Shape if built.** A `ZBandMode.ROW_BANDED` variant of the same builder: the `Faces` and `Mounted` groups and the sprites become per-band `Node2D`s with `z_index = Z_WIN_LO + band` in the window 10 to 899 (`band = floor(sort_y / BAND_H) - band_0`, `BAND_H` the wall footprint depth, `band_0` from the union rectangle of every body drawn, recomputed on dock, weld and detach), with `Caps` and `Dust` moving to 900 and 910. Dependents are unaffected because they use band names; the largest value (910) is inside the default light range (V6). `diag.zband_overflow` and `diag.zband_negative` stay as the GDD defines them.

### Implementation Guidelines
- **Must** keep `World` and every `BodyRoot` `y_sort_enabled = true` and translation only; **must never** make a body root non-sorting, rotate, scale or skew it, or write its position anywhere but `Placement.put`.
- **Must** set a layer's `y_sort_origin` at the **layer** with `TileData.y_sort_origin = 0`, from the cell-centre formula of § 3.2; **must never** copy "24" from the GDD text without the cell height.
- **Must** use exactly one `TileSetAtlasSource` per `TileSet`, one `TileSet` per `(atlas_set, layer_kind)`, and preload them in `BOOTING`; **must never** `load()` or build a `TileSet` inside stage `PROJECT`.
- **Must** build under `Staging` (in the tree, hidden, a data stage only) and commit on the last unit; **must never** leave a half-built section visible, and **must never** have the Layout projector create nodes anywhere but `Staging` or through `SectionScene` methods, nor parent or insert under a body root (all of that is `body.projector`'s).
- **Must** move nodes only with `SceneMove.to`; **must never** call `Node.reparent` with one argument, **must never** free a node another presenter attached, and **must** park every foreign attachment in `Staging` before freeing a root or scene (§ 7.2).
- **Must** write a sprite's position as `section_offset(section_id) + local_origin` from the stored section-local rect, recomputed from the current offset on build, mount, weld, cut and re-base; **must never** add a delta to a sprite position, and **must never** treat `section_rects_into` rows as half-open or as section-local.
- **Must** run the `LayerOrder` step after every mount, move and removal so a group's tile layers are its first children in ascending `section_id`; **must never** let `SortedLayer` index without the layer-prefix base.
- **Must** keep `PropsActors` and the sprites of `Mounted` in `(class_rank, entity_id)` order through `SortedLayer`; **must never** tie-break by `x`, by creation order or by tree luck, and **must never** accept a duplicate `(class_rank, entity_id)`.
- **Must** compute `entity_id` only through `EntityId.pack` with a name from `EntityNs`; **must never** persist an `entity_id`, use a block-local id as one, or add a namespace byte in code outside `entity_ns.gd`.
- **Must** write `z_index` only in the group builder from `ZBand` names; **must never** write a z number or a `y_sort_enabled` value on a node outside the group and layer builders.
- **Must** publish `CameraLimits` in stage `PROJECT` and leave `Camera2D.limit_*` untouched; **must never** create a `Camera2D` under any body root.
- **Must** count work in units and respect `BUILD_TILES_PER_FRAME` from the frozen `LayoutTuning` table; **must never** hold a literal for it in code.
- **Must** build bead, jamb, leaf, plate and scar sprites unchunked in the frame the weld notification is processed; **must never** chunk a socket-state change.
- **Must** keep all projector scripts in `src/presentation/projector/` (and the packing helpers in `src/shared/`); **must never** name `Node2D`, `TileMapLayer` or `Sprite2D` under `src/sim/`.
- **Should** make every projector class constructible with stub views so the audit tests run without a scene tree where the logic is pure (`DoorSort`, `InteriorDrawRule`, the limits union, the namespace packing).

## Alternatives Considered

### Alternative 1: Option B, one Y-sort node and no per-body roots
- **Description**: Every section's nodes keep one parent under a single Y-sort node; each section's position is driven from the body's pose plus `section_offset` every tick, so a weld changes an offset and never a parent (LY-31 option B, tried first by the spike).
- **Pros**: no reparent at all; the PR-5 "ONE Y-sort `Node2D`" is literal; a weld is a data change.
- **Cons**: its only advantage was keeping one sort scope, which nested `y_sort_enabled` nodes already give (V2). It also moves every section node and every sprite, not one root, whenever a body's canvas offset changes; it needs a per-node body-offset add in every Presenter (an actor then needs its body's offset on every `Placement.put`), which spreads body knowledge into every presenter; BDY-33's per-body root and AC-BDY-92 would be rewritten; and the freed-root, node-count and "the root disappears after a weld" checks lose their meaning.
- **Rejection Reason**: The premise (single scope needs a single parent) is false on 4.7.2 by probe, and B costs more writes and more coupling for no gain. Kept as a recorded comparison for SP-YSORT-1, not as a fallback.

### Alternative 2: Band-first (class layers at world level, per-body translation sub-roots)
- **Description**: `World` holds the band groups; each band group holds one translation sub-root per body, so equal keys across bodies resolve by class rank everywhere.
- **Pros**: cross-body equal-key ties follow the contract exactly; PR-5's "ONE Y-sort node" stays closest to literal.
- **Cons**: the body offset is written once per band per body per frame (five to seven writes, mostly skipped by `Placement.put`); "one per-body root" in BDY-33 and TR-shipbody-032 becomes seven sub-roots that must be created, ordered and freed together; a weld must move sub-roots in every band; the visibility rule (WM-19) must toggle seven nodes.
- **Rejection Reason**: It buys exactness only in the docked-seam equal-key corner (§ 3.4) at the price of the registered "one root per body" shape. If SP-YSORT-1 observes a visible cross-body flip, this is the first remedy; the `BodyScenes` facade hides which shape is underneath, so the change would be local.

### Alternative 3: One `TileMapLayer` per body (sections merged)
- **Description**: A single tile map per layer kind per body, cells in body-frame coordinates.
- **Pros**: fewer nodes; one `update_internals` per body.
- **Cons**: impossible on the 24 px grid: welded sections can be offset by half a 48 px tile (the registry's MVP offset is 14.5 tiles), so cells cannot align; a salvage or discard rebuilds the whole body; the maintained and `_worn` atlases would share a layer, which is two atlas sources in one layer (a draw-call risk, V8; the 440 figure is from an unsorted layer, the same case read 23 when sorted, so it is not the basis of this rejection).
- **Rejection Reason**: Does not fit the 24 px grid geometry (the grid argument settles it alone). Per-section layers cost a few extra nodes and the engine rebuild of a moved layer on weld (V10).

### Alternative 4: Rebuild the body's scene on every weld and cut
- **Description**: Free the moved sections' nodes and re-author them under the new root through the same chunked path as a restore.
- **Pros**: one code path; the scene is always a fresh function of the views.
- **Cons**: spends a chunked build (`set_cell` work) **and the same engine canvas-item rebuild** that a reparent costs (V10; re-authoring does not avoid it) on a change that moves geometry but does not alter it; the first frame after a weld may show a gap or a stale scene (the old set must keep drawing, so two sets exist); the bead's same-frame rule (TR-assembly-045) conflicts with chunking; allocations per weld rise; foreign attachments (trails, items) would be orphaned by the free and need parking and re-attaching.
- **Rejection Reason**: Reparent and recompute positions re-authors no tile and has no gap; the engine rebuild is paid either way. The re-authoring path is kept as the reference for restore and as the equivalence oracle (§ 7).

### Alternative 5: `Node.reparent(parent)` with the default global-transform preservation
- **Description**: Let the engine rewrite the local position so the node stays visually still.
- **Pros**: no explicit shift arithmetic.
- **Cons**: the engine rewrites a float local position, bypassing `Placement.put`, and the shift is not the integer `frame_shift_px` Layout reports; TR-shipbody-032 forbids it by name; V5 shows the local position changes.
- **Rejection Reason**: Violates the single integer assignment point and the TR.

### Alternative 6: Build the per-row z-band fallback at MVP
- **Description**: Wall faces, mounted items and sprites in world-anchored 24-row z bands from the start (PR-5 fallback as the default).
- **Pros**: removes any dependence on Y-sort batching behaviour.
- **Cons**: one `TileMapLayer` per band, sprites reparented at every band crossing, a union rectangle over all drawn bodies recomputed on dock, weld and detach, and the GDD itself says it is built only if it lowers both draw calls and CPU; V8 suggests the single sorted scope may already be cheap with one atlas per layer.
- **Rejection Reason**: Pays a certain complexity for a speculative gain; the go/no-go rule of § 10 stands.

### Alternative 7: Tie-break by tree insertion order or by `x`
- **Description**: Let the engine's tie rule decide equal keys, or break ties by `x`.
- **Pros**: no ordering structure.
- **Cons**: tree order is not save-stable (a reload can reverse creation order); `x` makes an actor swap order with a prop as it walks along a row, which PR-5's acceptance forbids.
- **Rejection Reason**: Contradicts TR-pxl-006. The engine's tie rule is used, but only after `SortedLayer` has made the tree order equal the contract order.

### Alternative 8: Non-sorting body roots
- **Description**: Only the groups are sorted; the body roots are plain translation nodes.
- **Pros**: matches "the cap layer is not a child of a Y-sort node" literally; each body is its own sort unit.
- **Cons**: a non-sorting intermediate sorts its subtree as a unit (V2): the two docked bodies would be ordered by root order alone, so a sprite of one body would draw over or under the other as a block, which is wrong at the seam.
- **Rejection Reason**: Breaks LY-31 exit criterion (1) across two bodies. The cap and floor lints are restated by band instead.

### Alternative 9: The Layout projector parents directly under Body's root (no staging)
- **Description**: LY-31's text: Layout's PROJECTOR parents its section nodes under Body's root.
- **Pros**: no handoff object.
- **Cons**: ADR-0009 registers the layout projector before `body.projector`, so the root may not exist yet for a new body; reversing the order would alter ADR-0009 and the occluder builder's dependency; a half-built section would be visible under a live root.
- **Rejection Reason**: The staging handoff keeps ADR-0009's order and gives atomic commits. (The handoff is a same-stage read between two stage-0 presenters, which ADR-0009 must sanction; § 5.)

### Alternative 10: A permanent per-section parent (zero-rebuild on weld and cut)
- **Description**: Give each section a permanent `y_sort_enabled` `Node2D` under `World`, positioned at its body's canvas offset plus `section_offset`, holding that section's groups; a weld or cut never reparents a tile layer, it only rewrites the section parents' positions. V2 shows the merged sort scope does not need per-body parents, and a `position` write was probed to cost 0 rebuilds (V10 g).
- **Pros**: no engine rebuild on a weld or cut; no `LayerOrder` re-establishment of moved layers; the weld becomes a position write.
- **Cons**: it removes the per-body `BodyRoot` that BDY-33, AC-BDY-92 and the root-count and node-count checks are written against, so the BDY GDD wording changes; foreign attachments (actors, lights) must still be reparented to a body-level parent on `BODY_TRANSFER` (CT-32), so two parent shapes coexist; WM-19 visibility becomes a per-section toggle, and a `visible` flip still rebuilds the layers it shows (V10 e), so `R_flip` is not removed; the canvas offset is written per section, not per body.
- **Rejection Reason (for now)**: It removes only the weld half of the rebuild cost and changes a registered shape on an unmeasured term. `R_weld` is about 0.4 ms for the MVP's 453 sorted cells on the dev machine, far under the 8 ms working threshold. **Revisit trigger:** SP-YSORT-1 measures `R_weld` (reparent plus the following frame, real cell counts, release export, RM-DECK) over `PROJECTOR_WELD_BUDGET_MS`. The `BodyScenes` facade hides which shape is underneath, so the change would be local; if adopted, the ADR-0009 reparent sanction becomes unused but harmless (CT-35).

## Consequences

### Positive
- The weld and cut frames do work proportional to nodes moved and cells re-rendered, with no tile re-authored and no gap; the bead appears in the first frame.
- One merged sort scope, probed, keeps PR-5's draw order across docked bodies without a special case.
- `entity_id` is a pure function of persisted ids, so draw order is stable across save and reload; the namespace table closes Layout OQ-33 and the Pipeline's open registration.
- Foreign presenters (Trail, Avatar, Interaction, Horror) get one attach API, so reparenting on `BODY_TRANSFER` is uniform and no presenter writes a z number.
- Per-section layers localise rebuilds, free a departed destination cleanly and respect the 24 px grid.
- The camera-limits path is a plain integer value read in the same frame; ADR-0009 OQ-C and OQ-I are closed on the PROJECTOR side.

### Negative
- Several GDD texts need rewording (§ GDD Sync): the wall-face `y_sort_origin == 24` lint, the "cap layer is not a child of the Y-sort node" lint, BDY-33 (d) and LY-31's default shape.
- Cross-body equal-key ties follow body order, not the comparator (§ 3.4).
- `SortedLayer` costs O(n) `move_child` calls on a merge and a binary search per insert; fine at the MVP's hundreds of nodes, a measured assumption on Deck.
- The projector depends on reads that other ADRs have not yet published (`ProjectionSet`, the docked set, `idx_of_key`, `section_rects_into` in its real signature); each is listed. The `JAMB` ordinal and the `area_max` invariant are settled by ruling CT-14.
- A y-sorted `TileMapLayer` costs 0.39 ms to update 453 cells on the dev machine (V9), against 13 us unsorted; acceptable margin on a desktop, unproven on Deck.
- The engine rebuilds every cell of a `TileMapLayer` that is reparented or shown (V10): a weld or cut pays about 0.9 us per cell per moved layer, a mount pays a full unchunked build, and every WM-19 `BodyRoot.visible` flip to true pays a rebuild of the root's layers. `Staging` does not pre-warm rendering, so `BUILD_TILES_PER_FRAME` bounds only the data work of an arrival.
- The guard surface (lints, `ProjectorAudit`, the specified-not-built fallback, the cross-body exception) is heavy for a small team; the tree-walk checks are merged into one boot/test walk (Validation Criteria) so only the lexical lints stay separate.

## Risks
- **R1: Nested-sort and tie behaviour differs on a release export, on a 4.7 patch release, or under the project's pinned Vulkan Forward+ at scale.** The probes ran on the editor binary on one GPU. Mitigation: SP-YSORT-1 reruns V1 to V4 on RM-DESKTOP and RM-DECK release exports; the `ProjectorAudit` tree walk keeps the shape; Alternative 2 is the local fallback for cross-body order.
- **R2: The tile key formula (V3) is relied on and undocumented in the pinned reference.** Mitigation: a boot self-test builds a two-cell fixture and reads back the order; a mismatch fails boot with `PJT_TILE_KEY_FORMULA`; the formula is recorded in the registry so a patch-release change is a one-line fix.
- **R3: Cross-body equal-key flip at the docked seam (§ 3.4).** Mitigation: ordered by `body_id`; recorded in SP-YSORT-1; remedy Alternative 2.
- **R4: `D_ysort` exceeds the budget with real art (96 px faces break texture runs per row).** The driver is the number of distinct textures per row across `Faces`, `Mounted` and `PropsActors` (actors, items, horror rigs and trails use other sheets), which one atlas per layer does not bound. Mitigation: SP-YSORT-1 reports distinct textures per row alongside `D_ysort`; the § 10 rule; per-field draw caps in ADR-0008 § 7; the fallback is specified.
- **R5: The weld frame or an arrival exceeds budget on Deck.** The weld re-authors no tile, but the engine rebuilds the moved layers once, deferred (V10), unchunked, proportional to cells moved and unmeasured for Deck; a mount and a WM-19 show pay the same. Mitigation: the unit is data (`BUILD_TILES_PER_FRAME`), `R_weld`, `R_mount` and `R_flip` are measured by SP-YSORT-1 (V9'), a hitch is bounded by `WELD_FRAME_HITCH_MAX_MS`, `ARRIVE_SETTLE_TICKS` includes the mount frames, and the remedy is Alternative 10 (a permanent per-section parent) plus retained hidden scenes (OQ-F); a further rung is to move the position writes of far sprites into the next frame, which the equal-key rule tolerates only within a body.
- **R6: A presenter attaches a node and frees it behind the projector's back.** Mitigation: `is_instance_valid` sweep, `PJT_ATTACH_DEAD` counter, lint `PJT-06` on `queue_free` of an attached node.
- **R7: The `ProjectionSet` or docked inputs are not published as assumed (ADR-0026).** Mitigation: a default implementation uses the avatar's body only and logs; Open Questions OQ-A and OQ-B.
- **R8: Wall cell width and wall tile art are not specified.** The sort key does not depend on cell width, but the tile pitch on the x axis must hold 24 px footprints for side walls. Mitigation: routed to the asset spec; Open Question OQ-D.
- **R9: Orphan noise, and the false comfort of staging.** A staged subtree outside the tree counts as orphans in the editor and debug runner (V7), so `Staging` is in the tree and hidden; but a layer built under a hidden parent builds nothing (V10 f), so staging pre-builds data only and the real build lands at mount. The orphan monitor is unverified on a release export; the release-safe check is the `ProjectorAudit.enumerate_into` tree walk.
- **R10: Float32 exactness of body offsets.** Offsets are bounded by ADR-0015's `BODY_COORD_LIMIT` (at most 2^24) and the canvas bound `|world_a - world_b| + |pos| < 2^23` under `WEB_COORD_BUDGET_PX` (otherwise `WORLD_COORD_LIMIT` is lowered), CT-24; the release-export probe is ADR-0008's.
- **R11: A parked attachment is never re-mounted or told it is orphaned.** Mitigation: the parking step keeps the registration, `on_orphaned` is mandatory-callable at `attach`, `PJT_ATTACH_ORPHANED` counts unanswered parks, and the restore validation row checks every attachment's parent.
- **R12: A mobile owner forgets `rebind`.** The node is moved with the wrong component after a cut until the owner rebinds. Mitigation: obligation recorded on ADR-0023, ADR-0020 and ADR-0027; the `projector_stale_binding` dev counter; the owner's same-frame write makes the error invisible, not absent.

## Performance Implications
- **CPU**: steady state, stage `PROJECT` does nothing but skipped `Placement.put` calls for body roots whose offset is unchanged and a dirty check; proposal 0.1 ms P99. A weld does O(nodes moved) work (reparent, position recompute, merge) plus a handful of sprite builds **plus the engine's deferred rebuild of every moved layer's cells** (about 0.9 us per cell, V10); a cut is the mirror; a build or arrival is `ceil(U / BUILD_TILES_PER_FRAME)` data frames of at most one budget of units, plus one unchunked mount burst per scene (`R_mount`), and each WM-19 show is an `R_flip` burst. Dev-machine margin is far below the 8 ms working threshold (453 sorted cells about 0.4 ms); release-export and Deck figures are UNVERIFIED.
- **Memory**: the MVP world's tiles and sprites are a few hundred nodes; a staged rebuild holds a second set of one section transiently (data only until mounted); parked attachments sit in `Staging`; `TileSet` and atlas textures are shared across sections of the same atlas set. No per-frame allocation in steady state (CNT counters, ADR-0010).
- **Load Time**: preloading `TileSet`s and sheets happens in `BOOTING`, not in stage 0; an arrival builds the destination in the frames counted above under the black plate, and a restore under the load hold released by `ProjectorReadiness.is_ready()`.
- **Network**: none at MVP; the projector is a local derived object (REPLICATION is dormant until VS-B).

## Validation Criteria
- **Order (auto, headless where pure):** `SortedLayer` property test: random inserts and merges give `(class_rank, entity_id)` order with the `LayerOrder` prefix base; the order is identical on 10 runs and after a rebuild that reverses creation order (PR-5 acceptance; AC-123 (b) within one body); a duplicate id is refused and counted. **Order signature (T4):** incremental weld, cut and pod sequences versus a fresh `ALL` build, compared as an **ordered child list per group** (tile layers ascending by `section_id`, then sprites by `(class_rank, entity_id)`), including after a save and reload that reverses build order.
- **Key formula (auto, windowed):** boot self-test of the tile key formula (R2); the PR-5 example (footprint rows 240 to 264, key 264; an actor at 232 sorts before, at 264 after) on the real layers.
- **Weld, cut, pod (integration with a scene harness, AC-BDY-92, AC-BDY-92b):** exactly one root per live body; after a weld the absorbed root is gone and the **tree-walk node count** (`ProjectorAudit.enumerate_into`, the release-safe check) equals the pre-weld count minus one; in the editor or debug runner (gdUnit4) the `OBJECT_ORPHAN_NODE_COUNT` **delta** is zero (the monitor is never a release-export gate and its release availability is UNVERIFIED, V7); the Presenter's parent is the destination `PropsActors` in the same tick; draw order for an actor one pixel south and north of a wall edge before, on and after each transfer is unchanged. **Weld test (T1):** a socket sprite built in the same frame as the weld has the same position as in a fresh `ALL` build; no sprite is displaced twice.
- **Restore (integration, CT-33):** after a restore, every foreign attachment (Avatar Presenter, Trail, Interaction, Horror, Suit) is under the right body root (tree walk), `OBJECT_ORPHAN_NODE_COUNT` delta is zero in the editor or debug runner, the tree-walk node count equals a fresh build plus the attachments, no frame draws a partial interior (the load hold lasts until `ProjectorReadiness.is_ready()`), and an attachment whose section no longer exists received `on_orphaned`.
- **BODY_TRANSFER pass (integration, CT-32):** a pod hop and a weld re-base leave zero frames in which a beam `Light2D`'s parent is not `BodyRoot(body_of_actor(actor))` and zero reparented nodes without an owner position write before draw; `rebind` of a mobile non-actor attachment moves it to the new body in the same frame.
- **Sprite placement (T8):** toggling a door leaves the drawn rect (`position + offset`) unchanged while `sort_y` moves by `WALL_FOOTPRINT_DEPTH`.
- **Equivalence (auto):** a scripted weld, cut and pod sequence through an incremental projector and a fresh one fed `ALL` give equal `rebuild_signature()` (AC-121: the multiset of `(entity_id, kind_ordinal, position, size)` equals a live build, **and** the ordered child list per group is equal).
- **No forbidden classes (auto, AC-122):** zero `CollisionShape2D`, `CollisionPolygon2D`, tile-set physics layer, `NavigationRegion2D`, `LightOccluder2D`, and no `Light2D` created or parented by the projectors except nodes attached through `attach_light`; no `Camera2D` anywhere under `World`; no `Camera2D.limit_*` write.
- **Limits (auto):** the rectangle equals the bounding-box formula for one, two and three sections, grows north by `LIMITS_NORTH_OVERHANG`, is republished on weld, cut, load and `BODY_TRANSFER`, and the solver consumes it in the same frame.
- **Build rate (auto + perf):** the arrival scene builds its data in exactly `ceil(U / BUILD_TILES_PER_FRAME)` frames with `U` counted from real `build_section` output, then mounts one scene per `present` (`+ S` frames); `ARRIVE_SCENE_LATE` fires when the latch is false at `DERELICT_LOADED`; the simulation tick count is unchanged by a late projector.
- **Atlas (auto, BOOT):** every catalog template has one `atlas_map` row; every `TileSet` has exactly one atlas source; no Layout field mentions wear.
- **Performance (perf, release export, RM-DESKTOP and RM-DECK):** weld frame P99 at most the 8 ms working threshold over 100 welds, measured as `R_weld` (reparent plus the following frame or `update_internals()`, real cell counts, windowed), with `R_mount` and `R_flip` reported; steady-state stage-0 proposal; `D_ysort` and distinct textures per row reported per viewport with the fallback trigger of § 10, read after a 2-frame settle; `get_render_info` and the orphan monitor availability on a release export reported as found (UNVERIFIED until then).
- **Audit and lint pack (ADR-0010 owns the tool and the tier; proposed here, T11):** the structural checks that a tree can answer are **one `ProjectorAudit` boot or test tree walk**, formerly `PJT-01`, `-02`, `-05`, `-07` and `-10`: body roots and `World` are `y_sort_enabled` and translation only; the group set and order under a body root, and in each group the tile layers precede the sprites and are ascending by `section_id`; no `LightOccluder2D`, collision or navigation node, and no `Light2D` outside `attach_light`; `Camera2D` absent under `World`; every `TileSet` built by `TileSetCache` has one atlas source. The **lexical lints** that a tree walk cannot see stay: `PJT-03` `z_index` written only in the group builder, no z literal; `PJT-04` no one-argument `.reparent(`, parent changes only through `SceneMove`; `PJT-06` no `queue_free`/`free` of an attached node by its owner without `detach`; `PJT-08` `EntityId.pack` takes a name from `EntityNs`, never a literal; `PJT-09` no `load(` / `preload(` inside a `present` callable.
